# 2026-10-02（续）· 网格左右贴边

用户：「一行 6 个文件，第一个 margin-left 为 0、最后一个 margin-right 为 0」。
详细记录 `docs/CHANGES-2026-10-02.md` §五，探针 `docs/probes/grid-6col/`。

## 根因（静态）

`.image-box-item` 是 **"margin 撑间距 + 宽度补偿回来"** 的算法：
`width: calc(100%/6 − 10px)` + 左右 margin 5px = **恰好占 100%/6** ⇒ 一行正好 6 个。
代价：**容器左右边缘各被吃掉 5px** ⇒ 整片网格比 `.header-bar` 内缩 5px。

## 做法：`.image-box` 加 `margin-left/right: -5px`（2 行）

**被否掉的两条路（都是踩过的坑）**

1. **删首/末格的 margin（`nth-child`）** —— 补丁，且**在这里会算错**：
   格子宽度是按"margin 会被补偿"设计的，只删首尾 ⇒ 每行右端空 5px、左右不对称。
   且列数在断点里会变（6/5/3/2/1），写死 `6n` 的式子窄窗必失效。
2. **换 `gap`** —— 方向对（边缘天然为 0），但必须**同步重算 `--item-width` 在 5 个断点里的每一个值**
   （gap 不占格子宽度、margin 占）⇒ 把"改一个百分比改列数"变成"每个断点改两个数字"。

⇒ 负 margin 是唯一"**只碰一处、断点和 item 算法一个字不动**"的解法。
判据（用户给的）：**以后新增同类场景还会不会复发** —— 负 margin 与列数/格数/断点全部无关 ✓

## 实测（`probes/grid-6col/out.txt`，3 档 × 前后对照，15/15 ✅）

```
              头部          网格容器      首格左 · 末格右
改动前 @1280  10…1270     10…1270      15 · 1265      ← 左右各缩 5px
改动后 @1280  10…1270      5…1275      10 · 1270      ← 与头部严丝合缝
```
一行**仍是 6 个**（按渲染结果数的，不是按公式推）。

## ⚠️ 新发现（之前不知道）

- `.image-box-item` 有 **5 个响应式断点**（≤600px→5 列、≤400px→3 列、≤300px→2 列、≤200px→1 列）。
  但主窗口 `minWidth: 1024` ⇒ **这几档实际触不到**（潜在死代码，未删，属另一件事）。
- item 还有 `padding: 0 2px` + 1px 透明边框 ⇒ 图片距容器边仍差 ~3px。
  用户只说 **margin**，故未动，已在汇报里问他要不要一起去。
- **探针的媒体查询盲区**：`@media (max-width)` 看的是 **viewport**，改 `#stage.style.width`
  **不会触发**。以前用 `stage.style.width` 测过的探针都不涉及断点，这次才暴露这条：
  要测断点必须 `win.setSize()`。

# 2026-10-02（续二）· 分析：文件夹为什么不显示 size（**只分析，没改代码**）

用户问「好不好实现、改动大不大」= **认知需求**。产出 `docs/ANALYSIS-folder-size-2026-10-02.md`
+ 探针 `docs/probes/folder-size/`（真库实测）。

## 根因（不是"接口没返回"）

`readFolder` 里 `size: stat.size` —— **Windows 上 `fs.stat()` 对目录返回的 size 是 0**
（NTFS 目录项不记字节数）。`formatBytes(0)` → `—`。字段一直在、类型也对，是值恒为 0。

**真正的问题形态**：在 Windows 上**没有任何一次系统调用能给出目录大小** ⇒ 必须自己算。
所以是"这份数据得自己算"，不是"漏了个字段"。

→ 也解释了"为什么有些文件夹反而有"：**收敛成封面的条目**走 `handleCover`，
size 是遍历子文件累加的（`size += stat.size`）⇒ 有值。

## 唯一不读盘的解法：查缓存聚合

每条缓存记录隐含"这一层的文件字节总量"：`loadMeta` 的 `withBytes` = `data.reduce(Σ size)`。
（目录条目 size=0，所以求和恰好只算文件 ⇒ 语义刚好对。）

目录的**子树总量** = Σ{ bytes(m) | serial 同 且 relPath 在该目录子树内 }

⚠️ 前缀匹配必须按路径边界（`root + '/'`），不能裸 `startsWith`（`a` 会吃掉 `ab`）。
⚠️ **分隔符实测确认是 `/`**（211 条含 `/`、0 条含 `\`）—— 猜错会让深层目录全不命中、
命中率虚高、结论直接错。第一版差点这么过去。

## 实测（真库，`probes/folder-size/out.txt`）

- 单次 `loadMeta({withBytes})` 中位 **0.82 ms**；最坏 O(n²) 213² = **2.3 ms**
- ⭐ **子文件夹维度：208 个里 205 个能算出大小（99%）** ← 这才是用户会看到的命中率
  （"缓存记录维度 99%" 是另一个数，会让人误判功能价值 —— 第一版只有那个）

## 改动量（估算，未实测）

**服务端 `readFolder` 约 20-25 行；前端 0 行；类型 0 行**
（`item.size` 和 `getSize()` 早就接好了）。热路径 +0.9 ms/次。

## 手法（可复用）

esbuild 打 `electron/server/nedb.ts` → 纯 Node 跑，**不需要 electron 替身**
（唯一的项目内依赖是 `import type`，被擦除）。两条硬约束：
① 库**拷到临时目录 + 改 `USERPROFILE`**（`loadDatabase()` 会整库重写，不能碰真库）；
② bundle 要落 `node_modules/.cache/`（`packages: 'external'` 时临时目录找不到 node_modules）。

# 2026-10-02（续三）· ✅ 已实现：文件夹条目显示大小

用户批准（"利用缓存就是要接受延迟的，最小改动实现、用正确的方式而不是打补丁"）。
改动记录 `CHANGES-2026-10-02.md` §六，验证 `probes/folder-size/verify.mjs`（**15/15**）。

## 落了什么

| 文件 | 改什么 |
|---|---|
| `electron/server/nedb.ts` | 新增 `loadSubtreeBytes()`（取数）+ `mergeSubtreeBytes()`（**纯函数**，归并） |
| `electron/server/index.ts` · `readFolder` | 进目录聚合一次，给 `type:'folder'` 的条目补 `size` |
| 前端 | **0 行**（`getSize(item.size)` 早就接好了） |

## 关键决策（都是"正确"而非"最小"的取舍）

- **抽纯函数** `mergeSubtreeBytes`：理由不是整洁，是它有 3 条容易 quietly 写错的边界，
  必须能喂构造数据单独验证（真库数据覆盖不到）。
- **一次遍历归并 O(n)**，不是"每个子目录各扫一遍库 O(K×n)"（单层最多 104 个子目录）。
- **降级纪律**：整段 `try/catch`。`readFolder` 原来不依赖缓存库，加了就有依赖，
  而 `loadMeta` 在库坏/还原中会抛 ⇒ 不兜住的话会从"没有大小"退化成"什么都看不到"。

## ⚠️ 差点交付的 bug（自己抓到的）

查表最初写 `subBytes.get(getFilename(file))`。但 `getFilename()` 是**去掉最后一个扩展名**的
（给文件条目拆 name/ext 用），而库里 `relPath` 段是 `readdir` 的**原样名字** ⇒
目录名带点（`v1.2`）查不到。改成 `subBytes.get(file)`。

**证据等级要说清**：实测库里带点目录条目 **0 个**（208 个目录）⇒ 这条分叉**未被真实数据覆盖**；
"必须用原始名"是**按契约推出来的**（静态事实：库里键 = readdir 原始名），**不是实测**。
⇒ 教训：**"当前数据恰好没有" ≠ "这个问题不存在"**（正是 §十二 自检问句那条：判据落在事实还是快照上）。

## 🔍 顺带发现（**未动**，报给用户定）

`item.name = getFilename(file)` ⇒ 目录名带点时**网格显示会少一截**（`v1.2` 显示成 `v1`），
且 `filterByName` 搜 `v1.2` 也搜不到。当前库里 0 例、**未发作**；属既有问题，按"特性神圣"只报告。

# 2026-10-02（续四）· ⚠️ 上面那版**落点错了**，已修正

**用户实测打回**："重启服务，hover 还是 `—`"。这是本轮最有价值的一次打回。

## 根因（我的错，而且撞在项目自己立的规矩上）

`openFolderController` 有**两条取数路径**：

```ts
const cached = noCache ? null : await findCache(serial, relPath, mode);
const doc = cached ?? (await scanAndCache(serial, drive, relPath, mode));
```

**浏览已缓存的目录走 `findCache` 短路，压根不经过 `readFolder`** ⇒
我把聚合补在 `readFolder` 里，只有"点刷新（`noCache=true`）"才生效。

**第二个更坏的后果**（当时没意识到）：`readFolder` 的返回值会被 `scanAndCache`
**写进缓存** ⇒ 目录的 size 以"子树总量"进了库 ⇒ 与 `bytes` 的 `data.reduce(Σ size)`
**双算** ⇒ 缓存面板大小列会整体失真。`probes/cache-panel-*` 当初实测过"双算 = 0"，差点打破。

## 正确落点：`wire()`

项目自己在 `wire()` 上面的注释早就立了规矩：
「**所有**下发路径都必须过这里，且只留这一处……**出口只有一个**，谁都不需要记得自己清一遍」
（那次是缩略图登记漏了一路，**同型的坑**）。我违反的正是这条。

⇒ 聚合挪进 `wire(items, serial, relPath)`（改 async）；`toWire`/`toAnchor` 改 async 并透传；
**构造新对象**补 size（绝不原地改 `items[i].size` —— 那是 nedb 内存里的文档）；
`readFolder` 里的聚合**撤掉**，并留下"别在这一层补、会双算"的注释。

## 新增 `diskNameOf()`

查表键来自库里 `relPath` 段名（`readdir` 原样名），而 `item.name` 削过扩展名 ⇒
拼回 `ext` 才算真名。与渲染层的 `fileNameOf` 同构。

## 验证：**17/17**（`verify.mjs` 新增 ⑥ 段）

⭐ ⑥ 就是**针对这次失效模式**补的端到端验证：拿真库里每条记录的 `data`
（= `cached.data` 的样子）**模拟 `wire()` 那一步**，验证"条目名 → 子树表键"对得上。
结果：**208 个目录条目 100% 查得到，205 个 size > 0** ✓

## 教训（值得记住）

1. **改"下发/输出"类逻辑前，先找"唯一出口"**（本项目：`wire()` / `apiUrl()` / `route()`）。
   注释里写着"所有路径都必须过这里"的东西，就是正确的落点。
2. **验收必须覆盖用户的真实操作路径**（这里是"浏览已缓存目录"），
   而不是我自己顺手的那条（`readFolder`）。我上一轮的"15/15"全绿，
   却**一条也没碰到缓存命中路径** —— 测试覆盖的路径 ≠ 用户走的路径。
3. **改"存储态"和"下发态"要分清**：存储态写库（会被聚合、被统计），
   下发态是副本（改它无害）。补展示字段一律在下发态。
