## 一、最高优先级
**减少对移动硬盘的读写。** 冲突时以此为准。

## 二、协作方式（用户有 ADHD + 阅读障碍）
- 交付：**正文 ≤10 行 + 优先一张图 + 需要他做的动作一行**；过程/根因/验证数据一律落 `docs/`
- 他问「还有哪些没做」→ **只给剩余清单**，别复盘
- ⚠️ 先判提问类型：问「X 不能吗 / 有没有 / 怎么用」= **认知需求**（讲机制 + 给能自己跑的实验），
  **不许**在结尾追加"要我执行吗"式催办
- 改主进程代码后必须**重启 dev**；改了扫描逻辑后按**刷新（↻）**重建那条缓存

## 三、铁律（跨会话必须遵守）
1. **特性默认神圣**：用户声明的便捷设计一律不动，只有我判断真有问题才**提交讨论**，通过才改。
2. 其余问题：**多视角交叉验证 + 确认没理解错 + 确认真要修**，然后**用正确的方式修，不许打补丁**。
   判据 =「以后新增同类场景还会不会复发」。结论里**标证据等级**（静态/推理/实测）；没实测的写"未实测"。
3. **`grep` 计数只能证明"源码里有一份"，不能证明"运行时渲染出一份"** ——
   2026-09-24 就因为这一步误判过一次（真因见 §五-2）。
4. **不要在 `n-space` 里放过会增减的子元素**（naive-ui 2.45.3 每个子项 key 都是 `1`）。
5. 缓存层：**永不自动删**；条目一律按白名单重建（`wire()` 唯一出口）；`CACHE_VERSION=2` 非必要不升；
   `CACHE_KEY`/`CACHE_IV` **永不可改**（改成确定性加密的代价是索引全废）。
