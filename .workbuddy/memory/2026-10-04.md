## 「离线盘封面为什么糊」—— 机制 + 三条对策（未动手，等他选）
- 机制（静态可复算）：只读层的地址是**锚点**（`#序列号/…`），而 `/raw` 只认盘符路径 ⇒ 服务端直接拒（`electron/server/index.ts:703-704`）⇒ `previewSrcOf` 降级成 `thumbUrl(item.thumb)`。**是刻意的**（宁可看小图，不报错、不碰一块不在的盘）。
- 尺度：缩略图固定 **480px 宽 / JPEG q82**（`electron/utils/thumbnail.ts:24-27`；`git log -S "THUMB_WIDTH = "` 确认自建立起没变过 ⇒ 整库都是这个尺寸，**不是"老缓存更小"**）。预览**铺满视口** ⇒ 480px 被插值 **≈3.8 倍**（`probes/preview-fill` 实测 480×270 → 1833×1031）。

## 「缓存里为什么没有原图」—— 分析（主人质疑，等他裁决；未动手）
- 主人的话：**"缓存里居然没有原图，那能叫缓存吗？每次都去读盘？"** —— 他的指向是对的，先把事实摆准：
  - 扫盘时封面原图**已经整张读过**：`electron/utils/thumbnail.ts:44` 的 `nativeImage.createFromPath(filepath)` 是"读文件 + 解码 + 缩放"，缩到 480px 之后**原图字节当场丢弃**。
  - 看大图时 `/raw` **再读一次**（`electron/server/index.ts:928-960`，原注释自己写着"对移动硬盘的额外负担可以忽略"）⇒ 不是"每次都读全量"，是"**每次看大图读一次，而这一次本来不必发生**"（字节到手过）。
  - 视频档：抽帧只读一帧，原片 5–7GB 存不了 ⇒ 只能"抽更大的帧"，不可能存原图。
- 根因：480px 是**库体积**换来的（103MB→12MB 那次重构）⇒ 只做了"覆盖全库的小图"，缺"按需的大图"这一层。
- ⚠️ **新硬约束（之前没记过）**：缓存库**不能再长大了** —— `nedb.ts` 是**每行 AES 加密**的 JSON-lines（`:128-154`），且 `loadDatabase()` **末尾无条件整库重写**（`:280-281`）⇒ 库越大，每次启动的"读+解密+加密+写"越慢，还全量进内存。⇒ 原图/大图**必须放独立文件目录**，塞进库是不可行的。
- 方案 A（推荐）：扫盘时把原图一并留下 —— 图片存**原始字节**（不重编码）、视频抽帧 480→~1280；**额外读盘 0**。渲染层靠 `wire()` 新下发的 `origKey` 走 `/orig?k=` 取（照 `thumb`/`avatar` 的既有模式）。旧条目**懒补**（第一次看那张时顺手存），**不必全盘重扫**；`CACHE_VERSION` 不必升（旧记录缺字段 = 没有缓存原图）。
- 待他拍：① 原图放独立文件目录（推荐）vs 塞库（**否决**，理由见上）；② 那个目录要不要纳入加密备份/还原（不纳入 ⇒ 还原后封面又糊）；③ 视频抽帧提到多少（480→1280 的磁盘占用）。

## 缓存大图 —— 设计已定稿（`docs/DESIGN-PREVIEW-CACHE-2026-10-04.md`，等主人点头）
- 主人拍板：**要存**（"原图大部分 100 多 KB、最大几 MB"）+ **纳入加密备份**（"分离存储则导出结构要调整"）。
- 关键事实（可复算）：`thumbnail.ts:42-51` `nativeImage.createFromPath` = **读整张 + 解码** ⇒ 原图字节**到过手里**；`server/index.ts:181-183` 记着"封面中位 800×538、base64 均值 161 KB"；**库不能长大**（`nedb.ts:110-154` 每行 AES + `:280-281` `loadDatabase()` 末尾整库重写 + 全量进内存）⇒ 大图**必须**独立文件。
- 方案：① 一次解码出两产物（480 网格 + **长边 2048** 预览，视频同一帧两产物，**零额外读**）；② 大图放 `<数据目录>/.file-finder/previews/<key>.enc`，**逐文件 AES + 随机 IV**；<key> = `sha1(序列号|dir|盘上真名|srcMtime)` —— 与既有复用闸门**同源判据**（`index.ts:505-510` 先例），扫盘态/读缓存态算出来**必然一致** ⇒ **库不加任何字段、不升 CACHE_VERSION**；③ 新出口 `/preview?k=&p=`：命中→0 读盘；没命中但有 `p`→读一次 + 建缓存（**懒补历史，不用重扫**）；④ 渲染层三级渐进（缩略图 → 停 300ms 探 /preview → 换）。
- 备份/还原/合并的**单位从"一个文件"升级为"数据目录"**（延续 `main/index.ts:199-205`、`server/index.ts:1205-1213` 的既有原则：不加包装格式）；UI 三个对话框改成选文件夹；老 `.db` 备份丢进数据目录仍可用。

## 主人实测撞到：离线盘补全后点开仍糊（404 `/preview`）—— 根因与三处修复
- 现象：补全 → 拔盘 → 点开，`/preview?k=p-….enc&t=….enc`（`t` 是 token，来自 `utils/request.ts:33`）**404**。
- 根因链（三条，缺一不可）：
  1. 「补全这一片」**不带 noCache** ⇒ 已缓存的层**只回缓存、不碰盘**（省读盘的设计，`index.vue` 注释写着）⇒ 不会重出大图；
  2. 出库迁移只能搬库里已有的**480px 缩略图** ⇒ 迁移来的层"缩略图在、大图不在"；
  3. **我的守卫写错了**：原实现"只有指纹对得上才落盘"，而迁移记录的指纹锚在**缩略图**字节上 ⇒ 在线点开生成的大图指纹不同 ⇒ **永远存不下来**（这一条是真 bug）。
- 三处修复（`server/index.ts` + `index.vue`）：
  1. `/preview` 指纹对不上 ⇒ **按它本来的名字存 + 302 重定向过去**（Location **必须带 token**，否则被鉴权挡掉）；记录里的指纹下次扫描自然改正。
  2. `wire(..., live)`：**离线层与视频条目不再下发 `preview` 名字** ⇒ 界面上不再出现"注定 404 的请求"，缩略图就是最终答案。
  3. **扫描闸门多问一句"大图在不在"**（三处抽帧路径都改了）⇒ 任何一次真扫都会补齐大图，补过之后不再重出。
  4. 「补全这一片」新增一手：某层若有"有图但没大图"的条目，**为它真扫一次**（每层只补一次，扫过就 `previewReady`），并在收尾刷新当前屏。
- 他现在能做的：**插上盘 → 对那一层按「补全这一片」或「重读这一片」**（或干脆点开那张封面一次，302 那条路会把它存下）⇒ 拔盘后清晰。

## 交付后自查（第二轮）—— 抓到 3 处真缺陷，2 处是我自己引入的
主人体验后问"有没有遗漏"。逐条实测判定，不复述已做的：
- **⚠️ 命名不变式被破坏（我引入的）**：实测遍历真 bin 仓 1349 个文件、解密比对"名字指纹 vs 内容 sha1" ⇒ `t-` **1205 正确 / 72 不符**，`p-` 72 全对。根因：`makeRenditions` 把 sig 锚在**大图**上，而一条记录只有**一个** sig 却要命名**两个**尺寸 ⇒ 缩略图存成 `t-<大图指纹>`，名字不含自己的内容。修法：sig 锚回**缩略图**，`t-<sig>`/`p-<sig>` = 「同一源的两个尺寸」，且**与出库迁移完全一致** ⇒ 1205 个文件继续有效、零重出。⚠️ 用一个字段命名两个尺寸 = 我第一版的偷懒。
- **⚠️ 懒生成不幂等 ⇒ 每次点开都重读源（我引入的）**：上轮"另存成内容指纹名 + 302"**根本解决不了** —— 请求的名字来自**库**，不因重定向而变 ⇒ 下一屏还是 404、还是读盘。修法：`/preview` **按请求名存**（缓存槽位语义），**302 分支整个删掉**。
- **⚠️ 备份会静默丢图**：`binStoreFailed()` 时 `listBinNames()` 为空 ⇒ 打出只有库的 zip 还回 "ok"。修法：响亮拒绝。

## 性能：逐条实测（第三轮，探针 `docs/probes/perf-tick/`）
- **取图没问题、不加内存缓存**：一屏 216 张各取一次共 **160ms**、单张最坏 **1.6ms**（远小于一帧 16ms）⇒ 同步读+AES 解密不掉帧。旧实现是内存 Map，现在按需读本地文件 —— 取舍成立（省几十 MB 常驻）。
- **扫盘：写盘占一半，已优化**。实测 216 条目：CPU（解码+缩放+两次 JPEG 编码）**1.49s** vs 写 bin（432 次 write+rename）**1.39s** —— 同量级，不是可忽略项。改法：`makeRenditions` 只登记写盘 promise 不自己等，`readFolder`（收敛封面 `handleCover` **共用同一袋**）在 return 前 `await flushRenditions(pending)` ⇒ 写盘与解码重叠。**A/B 7 轮中位 333ms → 154ms（2.16×）**，产出明文逐字节一致；分布也窄得多（152-165 vs 330-360）⇒ 更可预测。⚠️ 收益只在**真扫盘**时刻（首扫/重读/补全），日常开缓存不扫盘。
- **加密不是瓶颈**：只加密 0.041ms/张（200 次共 10.6ms）；写 23KB 要 3.1ms ⇒ 瓶颈在文件系统/Defender，不在 AES。
- **面板统计**：`binStats` 1349 个 `stat` = 15.5ms（只在打开面板算一次，可接受）；启动 `readdir` 1.2ms ⇒ "等 bin 就绪再 listen" 的代价可忽略。
- **缩略图 384 够用，不动**：dpr 1.25、6 列 ⇒ 窗口 1920~2048（他当前）时一格 400~427 设备像素 = **1.04~1.11× 插值（看不出）**；只有拉到 **2560 全屏**才 1.39×。⚠️ 换档的隐藏代价：**闸门不看尺寸** ⇒ 改常量只对新扫生效，全库升级必须**重扫一遍盘**（读盘 5 块）。448=28KB/全库 37MB，512=34KB/45MB。
- **探针三个坑**（已写进 README）：① `app.exit()` 吞 stdout ⇒ 结果一律写 `out-*.txt`；② 沙箱无 GPU，用 `app.whenReady()` 会让 GPU 进程崩 ⇒ 必须加 `--disable-gpu --disable-gpu-compositing --disable-software-rasterizer --no-sandbox`；③ **判据不能落在密文上**（随机 IV ⇒ 同明文两次密文不同）⇒ 比"产出一致"要先解密再哈希明文。
- ⚠️ **单次测量是噪声**：同一改动 A 两次量到 683ms / 363ms（差 2×）⇒ 探针固定 7 轮交替取分布。**别用单次数字下结论**（这条与"拍脑袋定性能结论"是同一个教训）。
- 方案的弱项（不粉饰）：备份包 ≈55MB 且**压不动**（密文高熵 + JPEG 已压缩）；bin 只增不减；迁移来的层大图要等扫到才补；一个 sig 命名两个尺寸（极小概率共用大图）；`/preview` 懒生成时同步解码卡十几 ms。

**探针** `docs/probes/preview-outside/`（8/8，真 Chromium + `elementFromPoint` 命中测试）。④④b 两条直接对应"缩小也关不掉"。

## 预览图「占满可视区且不超」—— 实现（探针 13/13）
**诉求**（用户）：预览打开时图尽可能占满可视区，但不能超过。
⚠️ 上一轮「先看真机」时我说「最大化做不了」，**这次做到了** —— 上轮结论只覆盖 CSS 那条路（`max-*`只缩小不放大），没算到底。
**两条不能碰的机制**（查naive-ui 行号为证）：
 ① `width/height:100%` → 图铺满 ⇒ `pointer-events:all` 的图盖死唯一关闭入口 overlay（`ImagePreview.mjs:510`）
 ② `transform:scale()` 放大 → `derivePreviewStyle` 每次缩放/拖动**重写整个 `style.cssText`**（`:317`）⇒ 写的被抹掉；它算好的比例只在 `resizeToOrignalImageSize()`（`:332`）用，而**该方法未对外暴露**（`exposedMethods` 只有 `setThumbnailEl`）
**办法**：把尺寸写成 `width/height`（`fitToViewport`：`min(可视区宽/图宽, 可视区高/图高)` 取较小者⇒ 必然不超 + 至少一边贴边）。同一 `cssText` 里 `width/height` 与 `transform` **叠加**（`:314` 先写我的、`:316` 追加它的）⇒ 缩放/拖动/旋转全归它，两套机制不打架。
**三个坑**：
 ① **`clientWidth/clientHeight` 给的是含 padding 的外框，不是内容盒**（实测 1602×903，而真可视区 = 903−16−64 = 823）⇒ 拿它算会让图撑出内容盒 80px 且比例歪。**必须自己减 padding**。这个坑探针先量出来了（★a/★c FAIL）才修对。
 ② `naturalWidth` 只有**图加载完**才有值 ⇒ 必须做成响应式由 `load` 事件**推**进去（computed 自己去读 DOM 只会算一次、永远停在「量不到」那支）。且 `<img>` 的 `key` 就是 `src`（`:560`）⇒ 换条目/升级大图都是新元素，**不可缓存**。
 ③ 触发点挂 `watch(previewSrcList)`（显示中那张图 src 的**唯一产出点**）⇒ 首开/←→/升级大图三条路径收在一处，将来加第四条不漏。
**探针** `docs/probes/preview-outside/`扩到 **13/13**：竖图 317×823（贴高）、横图 1570×471（贴宽）、都不超、比例 0.385=0.385、点图外仍命中 overlay、缩小后仍可关。
⚠️ **又犯了注释膨胀**：新增 148 行里 93 行注释（63%）⇒ 压到 70 行（56%）。**仍未达标**，下次新增前先问「判据是什么」而不是「我怎么想出来的」。

## 预览「缩略图→大图」升级时画面跳动（业主真机报）
**现象**：先出缩略图、后换原图，换的那一瞬图会**缩一下再跳回**。
**根因（我的逻辑缺陷，非浏览器行为）**：换 src ⇒ `<img>` 的 `key=src`（`ImagePreview.mjs:560`）⇒ **新元素**，`naturalWidth` 短暂为 0 ⇒ 旧代码 `feed()` 把 `previewImgNatural` 置 `null` ⇒ `previewedImgProps` 掉回「`max-width`+`auto`」档 ⇒ 图缩回原始尺寸；大图加载完再撑满 ⇒ **跳一下**。
**修法**：`previewImgNatural` 连「**属于哪一条**」一起存（`{key,w,h}`）。没加载完那一瞬：
 · **同一条**（缩略图→大图这档升级）⇒ **沿用旧值**。同一张源图 ⇒ 撑满后的目标尺寸本来一样 ⇒ 零副作用、不跳。
 · **换了一条**（←→）⇒ 必须清掉，否则新图会先按上一条的尺寸显示一瞬（歪）。
 判据用 **key 而不是比例** —— 那一刻 `naturalWidth=0`，**比不出比例**（我第一版想用比例，是错的）。
 另在 computed 里加一道保险：`nat?.key === previewKey` 才用。
⚠️ 注释里写 `max-*/auto` 会**提前结束注释块**（`*/` 是注释终止符）⇒ 整段语法崩。写"max-width + auto"这类含 `*/` 的字面量务必改写。
**⚠️ 探针 ⑦抓不到这个缺陷（诚实记录）**：大图在探针里是 data URL（**同步可用**，`naturalWidth` 立刻有值、complete=true）⇒ 根本走不到「未加载完」那一支；我试过强制 `naturalWidth=0` + 异步换 src 两次，**回退修复后依然 PASS** ⇒ 该断言无效，**不能当证据**。真实环境大图走 HTTP 有延迟才会出现那一瞬。判据要真测得靠真机或给探针架一个真 HTTP 延迟。
⇒ **按刹车纪律：同一处读 2 遍没结论就停**。这条已停，改为「静态推理 + 真机目视」验证。

## 预览「第一次打开先小后大」（业主真机报·我的解释先错了一轮）
**业主原话**：「第一次打开会从小图切换大图，后面就不会了」。
⚠️ **我第一轮的解释是错的**（以为是「/preview 首次要读盘生成、第二次走缓存」—— 那解释的是**清晰度**，不是**大小**）。业主当场反问「第二次后也是先糊再原图，并没有小变大的情况啊」⇒ 说明**两次比例相同、尺寸本该一样**。他的反问是对的。
**真根因**：`previewImgNatural` 是 `ref(null)`（`usePreview.ts:291`）⇒ **冷启动时为null** ⇒ 首次打开走**回退档** `width/height: auto` = **原尺寸**（实测首帧 `100×260`）⇒ 一帧后量到尺寸才撑满（`317×823`）⇒ **先小后大**。第二次打开时该ref 已有值且 key 匹配 ⇒ 压根不走回退档 ⇒ 不复现。**跟 `/preview` 缓存、与清晰度都无关。**
**修法**：回退档也撑满 —— `height: '100%'`（不是 `auto`）。竖图贴满高、横图由 `max-width` 收着 ⇒ 两方向都不超。
**探针** `docs/probes/preview-outside/` 加 ⓪（**冷启动**模拟：显式 `resetNatural()`把状态清空再开）⇒ 现 **14/14**。
⚠️ **A/B 有效性已验**：回退档改回 `auto` ⇒ ⓪ **FAIL**（`✗ 首帧 100×260 → 稳定后 317×823（变大了）`）⇒ 判据真抓得到。
⚠️ 探针教训（第 2 次）：**上一版 ⓪ 没清状态 ⇒ 复用了上次量到的值 ⇒ 假 PASS**。凡验「冷启动/首次」类缺陷，**必须把状态显式清空**，否则测的是复用路径。
**记忆判据**：`ref(null)` 初始化 + 「回退档」= 首次必闪一次 —— 这类模式要主动问「冷启动那一次是什么样」。

## 网格方向键导航 + 回车确认（方案已出· 待主人批准后实施）
主人要求：网格（文件/视频渲染区）也加方向键，`Enter` 打开/确认；选择器**常驻**；
鼠标与方向键的尺度要统一；预览的定位高亮改成与选择器一致（最多多个闪烁反馈）；
**最小改动 / 模块化 / 不堆主文件**。方案全文 = `docs/DESIGN-GRID-CURSOR-2026-10-04.md`（**尚未写任何代码**）。

**核心判断（省掉一整类改动）**：`usePreview.previewKey`（「正在看哪一条」）**本来就是一个选择器**，

⇒ 解法：新增**独立** `cursorKey`，只在「打开预览」「定位」两个动作上**单向**同步

**三条刻意的"不统一"（防将来被当bug 改掉）**：

- 定位闪烁 蓝→**琥珀 #f0a020**（原来也用蓝，与焦点撞色）；`opening` 蓝→**中性深灰**（它有遮罩+转圈，不该抢注意力）。

  ⇒ 鼠标停在焦点格上时焦点环**整个消失**（鼠标操作时最需要看见焦点的时候）。提一级权重解决。

### ③ 焦点框重做 —— PS5 那套（我前两轮的根因都猜错了）
⚠️⚠️ **我上一轮说"双线框（外蓝+内黑）"是丑的根因，错了**。截图显示真正的根因是

**处处圆角**，唯独 `.image-box-item` 是**直角** ⇒ 焦点环跟着直角 ⇒ 像贴了 Excel 单元格边框。

**依据（PS5 官方 UI 的观察，设计评论者 firstlook 记录）**：
*"Most of the tiles and cards in the PS5 UI have **rounded corners**… There are some
outliers, though: all tiles in the Official News section, game tiles in the PlayStation
Store, and all tiles we were shown in the **Explore** section. …My Hail Mary guess is
that **tiles with sharp corners navigate you to a new screen.**"*
⇒ **直角 = "这是内容"，圆角 = "这是入口"**。我们网格里每格都是双击/回车进去的入口，
用直角表达错了语义。**这不是审美偏好，是与 PS5 官方 UI 对齐同一套规则。**
（那个 design system 文档也记了 PS5 的招牌动作：hover 时"fill 换青 + 2px 白边 +
外圈蓝 ring + 整体 scale 1.2×" —— "power-on" 那一���。）

**改法**：
- 卡片 `border-radius: 8px`（`box-shadow` 会**自动跟随** border-radius ⇒ 环与卡片同形）
- 焦点环 = **内白线** `rgba(255,255,255,.92)` + **外主色环** `#2080f0`（不透明）
  ⚠️ 内层**换成白的**是被数据推着走的：实测内白 vs 中灰图 **3.85:1**，
  而上一版的内黑只有 **2.70:1**（黑线在**深色封面**上才显形，而我们深色封面不少）。
  内白在**白底卡片**上是 1.00:1（等于没有）—— 那是**分工**：白底靠外环认（3.56:1）。
- `transform: scale(1.02)` = PS5 的"抬起来"。⚠️ **transform 只影响绘制不参与布局**
  ⇒ 6 列宽度算法零影响（这正是用 transform 而非改 width 的唯一优势）。
- `transition` 从 `all .1s` 拆开：颜色/阴影仍 .1s（跟手），`transform .18s cubic-bezier(.2,.9,.3,1.1)`
  （"亮一下再稳"）。`all` 也去掉 —— 它让transform 与未来任何属性共用同一时长，调试看不出谁在动。

⛔ **关键约束（三个方案都不能违反）**：**不能加 `overflow: hidden`** ——
它会**裁掉外扩的 box-shadow 焦点环**（两者互斥，已实测：加了环就消失）。
⇒ 只加 `border-radius` 不裁图：图片四角露一点直角是现状固有样子，不算退化。

### 核实：完全正确，且**推翻了我前两轮修的方向**

⇒ 我那守卫 `t !== document.body` **恒为真** ⇒ 方向键永久被挡

⇒ **记忆判据：键盘"没反应"这类症状，先问「焦点现在在哪个元素上」**，
   再问「它是谁放上去的」——本例是 `FocusTrap.returnFocusOnDeactivated` 这个**默认值**。

### 修法：判据从「焦点在不在 body」换成「焦点在不在**会吃方向键的东西**上」
| 焦点在哪 | 方向键被谁吃 | 放行 |
|---|---|---|
| body / 网格卡片 | 没人（要接管）| ✅ |
| **按钮**（本项目 11 个 `n-button`）| **没人**（只吃 Enter/Space）| ✅ ← 修的就是这条 |
| `input`/`textarea`/`select`/`contenteditable` | 输入法光标 | ❌ |
| `role=combobox/listbox/slider/spinbutton/tree/grid` | 那些控件 | ❌ |
⇒ **白名单**（列出要挡的）而不是黑名单：黑名单要穷举"什么会吃方向键"，
  那个列表是**开放的**（将来加 slider / 树选择 / 数字框都会进来）⇒ 漏一个就是
  "那个控件里方向键失灵"这种**极难定位**的 bug。
⚠️ 仍**不用**"弹层开没开"当判据（tooltip 就是 popover、关闭后 DOM 还在 ⇒ 永久失灵）。
