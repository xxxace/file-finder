# 备份包（导出 zip）还能不能更小？—— 实测结论 2026-11-15

> 问题：`backupToFile` 导出的 zip 是否还有压缩空间？极致压缩能不能再压？
> 判据分三层：**压缩算法** / **入包字节** / **容器开销**。逐层实测。

## 一、结论（先看这个）

| 层 | 现状 | 还能压多少 | 判据 |
|---|---|---|---|
| 压缩算法（deflate / brotli / zstd） | 图片 store、库 deflate | **0%** | 实测，见 §二 |
| 入包字节（哪些该进包） | 全量 `bin/` 无过滤 | **−23.6%（−59.4 MB）** | 实测，见 §三 |
| 容器开销（ZIP 头 + 名字） | 4304 条目 | −0.5 MB（0.2%） | 推算，见 §四 |
| 换编码（WebP / JPEG XL） | JPEG q78/q82 | −19% ~ −36%，但**有损或需重编 + 慢** | 见 §五 |

**一句话**：算法这条路确实到顶了（连明文 JPEG 都压不动），但**包里塞了 23.6% 的孤儿图**——那不是「压不动」，是「根本不该带」。

## 二、压缩算法：真的没空间（实测）

用真实缓存文件跑，不是估算：

| 对象 | 样本 | deflate -9 | brotli q11 |
|---|---|---|---|
| `.enc` 密文（现状入包形态） | 12 个（t-/p- 各 6） | **100.03%** | **100.01%** |
| 解密后的 JPEG 明文（p-） | 8 个 | **99.73%** | 99.76% |
| 解密后的 JPEG 明文（t-） | 8 个 | 99.84% | **99.41%** |

两重原因叠加，任一就足以封死：

1. **AES-256-CBC**（`cacheCrypto.ts`）：密文熵 ≈ 8 bit/byte，压缩算法只能吃噪声，吃不动。
2. **JPEG 本身已熵编码**：即使解密成明文，DCT 系数 + Huffman 之后已无冗余，brotli 最好也就 0.6%。

⇒ 换 zstd / lz4 / 7z 的 LZMA2 结论一样（熵已满，任何通用压缩器都出不了活）。
⇒ 唯一能榨的是「JPEG 自身的编码效率」，见 §五，而那已不属于「压缩」范畴。

已经在做的两件正确的事（2026-10-05 那轮改的），**不要回退**：

- 库：磁盘上是逐行 base64 密文，包内**解成明文 JSON 再 deflate**（≈442 KB → 81 KB，−82%）。密文直接 deflate 只 −26%。
- 图片：保持 store。实测 deflate 反而 +0.03%（见上表第一行），多压一遍纯粹浪费导出时间。

## 三、真正的大头：孤儿图 23.6%（零代价）

`backupToFile` 用的是 `listBinNames()` ⇒ **`bin/` 里有什么就打包什么**，不做引用过滤。
但 `bin/` 是**只增不减**的（缓存层永不自动删），换封面 / 重扫 / 换盘都会留下旧图。

实测（本机当前数据）：

| 项 | 数量 | 体积 |
|---|---|---|
| `bin/` 合计 | 4304 | 251.7 MB |
| `t-` 缩略图 | 2731 | 79.5 MB |
| `p-` 大图 | 1573 | 172.3 MB |
| **其中孤儿 `t-`** | **1290** | **46.9 MB** |
| **其中孤儿 `p-`** | **138** | **12.5 MB** |
| **孤儿合计** | 1428 | **59.4 MB（23.6%）** |

引用来源必须**两个都查**（少一个就会误删别人的图）：

1. `searchCache.db` 的 `data[].sig` → 1441 个 sig 中的 1427 个；
2. `playlists.json` 里的 `sig` 字段 → 追加 14 个（`playlist.ts` 也在存 sig）。

只查 searchCache 的话，会把收藏夹正在用的 14 张图当孤儿丢掉（还原后收藏夹卡片白框）。

- **导出后体积**：252 MB → **192 MB**
- **代价**：零。库已在内存（`exportSnapshotPlain`），`bin/` 只 `stat` 不读内容 ⇒ 无额外读盘
- **无损**：孤儿本来就不被任何记录引用，还原后表现**逐像素一致**
- ⚠️ **只过滤入包，不动磁盘**。`bin/` 一个文件都不删（「零引用 ≠ 该删」，孤儿可能是将来要复用的）

实现落点（`electron/server/index.ts:1665`）：

```
const binNames = listBinNames();   // ← 改为按引用集合过滤
```

过滤集合 = `exportSnapshotPlain()` 里出现过的 `sig` ∪ `playlists.json` 里的 `sig`，
然后取 `thumbNameOf(sig)` / `previewNameOf(sig)` 且在 `hasBin()` 里命中的名字。
**不要**自己拼 `t-${sig}.enc`（`binStore.ts:119` 是唯一构造点，已经在注释里强调过）。

## 四、容器开销：0.2%，顺手可省

4304 个条目 × (30 本地头 + 46 中央目录 + 49 字节名字 `bin/p-<40hex>.enc`) ≈ **0.53 MB**。

省法只能是「名字改短 + manifest 里放映射表」，收益 0.2%，**建议不动**——
为一个 0.2% 引入一张名字映射表，换来的是一份以后必须维护的格式复杂度。违反奥卡姆。

## 五、换编码：能省 19%~36%，但都不是免费的

同机实测（8 张大图，解密后重编码）：

| 方案 | 相对 JPEG | 性质 | 代价 |
|---|---|---|---|
| WebP q82 | **64.4%**（−35.6%） | **有损二次编码** | 需引入 webp 编码路径 + 导出/导入各转一遍 |
| JPEG XL 无损重压缩 | 约 −19%（业界实测 10%~36%） | **无损、可字节还原原 JPEG** | 需引 libjxl 二进制；每张 ~0.4 s ⇒ 4304 张 ≈ 数分钟~半小时 |
| jpegtran `-optimize -progressive` | −3%~−6%（业界实测；已优化过的 <1%） | 无损 | 需引 jpegtran；导出多花约 2 分钟 |

**三条都有同一个拦路虎：`sig` 是 sha1（缩略图字节）。** 改字节 ⇒ sig 变 ⇒ 文件名变 ⇒
必须额外在 manifest 里存「原 sig → 新文件名」映射，导入时按原名写回，才能保住缓存索引。
这不是压缩问题，是格式演进问题。

判断（**不建议做**，除非将来重扫代价归零）：

- **WebP**：备份包的第一属性是「原样还原」，为省 70 MB 给封面做二次有损编码，方向错了。
- **JPEG XL**：技术上是这题最优解（无损 −19%，Chrome 155 起自带解码），但收益 36 MB < 孤儿过滤的 59 MB，而工程量是它的十倍。**先做 §三，再谈它。**
- **jpegtran**：收益取决于现有 JPEG 是否已优化过。本机缩略图走 `nativeImage.toJPEG`（libjpeg-turbo 默认表），大概率能吃到 3%~6%；但 2 分钟导出时间 + 一个新二进制，换 6~15 MB，性价比低于 §三。

**未实测**：jpegtran 在本机真实样本上的具体百分比（未引入该二进制）。上表 −3%~−6% 是业界数据，不是本机数据。

## 六、被判死的方向（不要再试）

| 方向 | 判据 |
|---|---|
| 密文再压一遍（deflate/brotli/zstd/7z） | 实测 100.03%，纯浪费 CPU 与导出时间 |
| 用 brotli 替掉库的 deflate | 库只有 110 KB 量级，最好也就再省几 KB |
| 加密前先压（`deflate → AES`） | 顺序对但对象错：JPEG 已无可压冗余（§二 第二行） |
| 把 `t-` 从 `p-` 重建以省 79.5 MB | **结构上不成立**：sig 锚在缩略图字节 ⇒ 重建缩略图 = 重建 sig = 全部 p- 改名 + 全缓存索引失效（`binStore.ts:20`）。且 1158 个条目根本没有 `p-` |
| 降低缩略图质量/分辨率 | 有损且改 sig ⇒ 全量重扫移动硬盘（违反最高优先级：减少读盘） |

## 七、建议顺序

1. **P0 · 导出按引用过滤**（−59.4 MB / −23.6%，零风险零读盘）—— 只有这一件事值得现在做
2. P3 · jpegtran 无损优化 / JPEG XL —— 等进行完 P0 再评估，届时基数已从 252 MB 降到 192 MB
3. 不做 · 任何通用压缩算法 —— 已实测封死
