## 1. 三条设计原则（先立原则，再谈组件）

**原则 A：门槛 ∝ 不可逆性 × 波及面，不 ∝ 点按频率。** `[推测，但由 F3/F4 直接推出]`
- 为什么：用户是 ADHD。若按"危险"给所有会覆盖的动作都加弹窗，`F5` 一天按几十次 → 点"确定"点到肌肉记忆，真正危险那次反而会被顺手点掉（警报疲劳）。所以弹窗**只留给波及面最大的那一个**（重扫整片），其余靠"可撤销 + 数据层修复"兜底。

**原则 B：能"可撤销"就不要"先确认"。** `[推测]`
- 为什么：确认弹窗是**拦截**（打断心流、每次都要做决定）；自动快照是**保险**（用户不被打断，出事能回滚）。F7 已给出零读盘的快照原语 → 把"不可逆"降级成"可恢复"的性价比极高，且不违反"减少读盘"硬要求。

**原则 C：数据层修复优先于任何界面门槛。** `[事实驱动]`
- 为什么：F3+F4 说明"点对了也可能毁数据"。UI 能防手滑，防不住一次 `readdir` 抖动。所以 **P0 第一项永远是修 `readFolder`/`scanAndCache`**；任何刷新/重扫的视觉设计都必须建立在它之上（输入文档 §2.3 结论）。

## 2. 动作危险分级表（后面所有设计的依据）

| 动作 | 读盘量 | 会覆盖已有缓存？ | 可逆性 | 波及面 | 危险级 | 门槛 |
|---|---|---|---|---|---|---|
| 打开目录 | 命中缓存=不读；未命中=读一层 | 否（只写缺失） | 可逆 | 1 层 | 低 | 无 |
| 刷新（↻ / F5） | 1 层强制读 | **是（单层）** | 修复后≈可逆，否则不可逆 | 1 层 | 中 | 无弹窗 + 可撤销 |
| 补全（递归） | 只读未缓存部分 | 否（有缓存跳过） | 可逆 | 整片 | 中（耗盘/耗电，非数据） | 无弹窗 + 进度/取消 |
| **重扫整片** | **每层强制读** | **是（整片）** | 修复前**不可逆** | 整片 | **高** | **确认 + 自动快照** |

> `[事实]`「补全不覆盖」由 `findCache` 命中即回缓存保证（`index.ts:616-617`）；「重扫每层 noCache」由 `startScan(true)` 保证（`index.vue:585,626`）。

**危险级只看两件事：会不会覆盖 × 覆盖多大范围。** 为什么：读盘量大只伤硬件（可用进度/取消缓解），覆盖才伤数据（不可逆）。

## 4. 五项交付

### 4.1 防误触方案（刷新 / 重扫这类会覆盖缓存的动作）

采用**四层防御**，从里到外：

**第 1 层（P0-1，数据层）**：读盘失败**不写缓存**。
- 为什么：这是唯一能防住"点对了也毁数据"的一层（§2.3）。没有它，下面三层都只是止疼药。

**第 2 层（P0-2，可撤销）**：重扫整片前自动快照一次缓存库（复用 `/backup`，纯本地拷贝，零读盘）。
- 为什么：把"不可逆"降级为"可恢复"，用户无需被打断做决定（原则 B）。
- `[推测]` 注意：`cacheBackup()` 文件名按天（`-YYYYMMDD`），**同一天多次会互相覆盖**。要做"动作前快照"需给它一个不被日常备份顶掉的槽位（例如单独一份 `searchCache-prescan.db`）。这是后端要补的小改动。

**第 3 层（P0-4，确认门）**：**只给「重扫整片」** 加 `n-popconfirm`，**不给刷新加**。
- 为什么：见 §2 表——重扫是唯一"高"危（整片覆盖 + 每层强制读）。刷新只波及 1 层，且频繁使用，加弹窗=噪音（原则 A）。
- 为什么用 `n-popconfirm` 而非 `n-modal`：popconfirm 是**就地一行问答 + 两个按钮**，不遮挡网格、不需第二个操作面；modal 太重，对 ADHD 是额外负担。只有"无限波及 + 无法快照"类操作（如将来做"清空缓存"）才配 `n-modal`。

**第 4 层（P1，入口降权）**：`F5` 与 ↻ 保持"刷新单层"语义（§四 神圣，不动），但**视觉上与重扫拉开等级差**：
- 重扫不放主按钮行同权重处，且触发器改 **click**（不用 `hover`，见 §三.2）。
- 为什么：§三 已点出"危险等级没有体现"。同级并列会让手滑成本变零。

**关于「延迟执行」的取舍（明确不做）** `[推测]`
- 为什么不做：延迟执行（点完倒数几秒再执行）只适合"瞬时且可撤销"的写。重扫本身要跑很久，延迟毫无意义，倒计时还会制造焦虑。**用"快照可撤销"代替"延迟"**。

**关于长按 / 双击确认（明确不做）** `[推测]`
- 为什么：不可见、不可发现，对有阅读障碍者尤其不友好；且和"双击格子打开"的神圣交互冲突。

### 4.2 三种状态可区分（盘不在 / 读不到 / 空目录）

> **现状事实**：三者都返回 `[]` + HTTP 200，前端**根本无从区分**（F3/F5）。所以"可区分"的前提是先给一个**判别信号**。这属于 P0-3。

**契约要求（需后端配合，非代码）** `[事实推导]`
- `/openFolder` 需在响应里携带一个判别位，取值四选一：`ok` / `empty` / `unreadable` / `offline`。
- 推荐形态：沿用本仓库既有惯例的信封（多数接口已是 `{code,...}`），把裸数组包成 `{ code:200, status, items }`；或最小侵入地在响应头带 `X-FF-Read`（但 `request.ts` 目前不透出 header，取信封更省事）。
- 为什么必须由服务端给：只有服务端知道 `readdir` 是"成功返回 0"还是"抛错"，也只有它知道 `findDriveByLetter` 是否返回 null（F5）。前端拿 `[]` 是**物理上无法**分辨的。

**三态在界面上的呈现（严守 §四：空状态只有一行浅灰小字，失败时不显示）**

| 状态 | 表面（Surface） | 组件 | 文案（≤6 字） | 网格内容 | 为什么 |
|---|---|---|---|---|---|
| 空目录 | **空状态**（灰色小字，原有形态） | 复用现有 `.empty-tip` | `空的` | 空 | 真的空 → 这是唯一该显示"空状态"的情况（§四） |
| 盘不在 | **顶部横幅** | `n-alert type="warning"` | `盘没插上` | **保留上一次内容** | 见下 |
| 读不到 | **顶部横幅** | `n-alert type="error"` | `读不到，稍后再试` | 保留上一次内容 | 与盘不在靠 类型色 + 措辞 区分 |

- **为什么失败用横幅而不是空状态**：§四 规定"空状态只有一行浅灰小字，**失败时不显示**"。横幅是**另一个表面**（工具条与网格之间），不是"空状态"元素——因此既满足"三态可区分"，又不破坏神圣约束。
- **为什么失败时保留网格不清空** `[推测]`：F5 场景（拔盘→刷新）里缓存其实**还在**（§2.2），清空会让用户以为数据丢了。保留 + 横幅 = "你看到的还是缓存，只是盘现在不在"。这也天然把"失败"和"真空"区分开（真空是空白，失败是有内容+横幅）。
- **盘不在怎么判定** `[事实]`：直接复用 `/getDisks` 的 `online`/`offlineSerials`（F8），无需新读盘。
- **读不到怎么判定** `[事实]`：靠 P0-3 的信封 `status==='unreadable'`。
- 为什么文案这么短：ADHD + 阅读障碍（§一要求），且横幅是一行小字的延伸，不制造第二块"要读的东西"。

### 4.3 进度与取消

**现状（保留）** `[事实]`：扫描开始时，工具条那个按钮**就地**换成「已扫 n / 待扫 m」+「取消」（`index.vue:24→27-28`）。

**设计结论**

| 项 | 结论 | 组件 | 为什么 |
|---|---|---|---|
| 进度呈现 | **数字为主**，可选一条细进度条 | 文本 + `n-progress type="line"` `:show-indicator="false"` | `待扫 m` 是**动态**的（每展开一层就增长，F2）→ 任何"百分比"都是**假精确**；数字是唯一诚实的表达。进度条只作"在动"的动效，不给数字 |
| 取消按钮位置 | **原地**（就是原启动按钮的槽位） | `n-button size="small"` | 位置稳定 = 肌肉记忆：同一点位"开始/停止"切换，ADHD 用户无需搜索 |
| 点击取消后 | 按钮变灰 + 文案 `停止中…` | `n-button :disabled` + 文案替换 | F6：取消只在目录边界生效，慢目录可能还要数秒；不反馈的话用户会以为坏了而连点 |
| 扫描中锁 | 禁用 ↻ / 重扫 / 换目录 | `:disabled` | 硬要求：串行、一次一块盘；并发强制读盘会叠加 USB 供电峰值 |
| 完成提示 | `n-notification` 一行：`扫完 n 个` | `useNotification` / 现有 `notify` | 一行、可自动消失（默认 info/success） |
| 取消后提示 | `n-notification` 一行：`已停`（可带 n） | 同上 | 与"完成"措辞不同即可区分；网格始终不动（F2） |
| 取消后网格 | **不变** | — | F2：批量扫描绝不碰眼前网格，取消也不该例外 |

- **为什么不用全屏遮罩/模态进度**：会让"后台在扫"变成"界面被占用"，与 F2"绝不碰网格"的设计意图相悖。
- **为什么`待扫`不设进度百分比**：见上，动态分母 + 深搜 => 百分比会倒退（m 变大时进度回落），比不显示更糟。

### 4.4 危险动作的门槛（推荐 + 理由）

| 动作 | 门槛方案 | 组件 | 为什么 |
|---|---|---|---|
| 打开目录 | 无 | — | 最低危、最高频、命中缓存不读盘 |
| 刷新（↻/F5） | **无弹窗** + 自动快照/数据层修复使其安全 | — | 单层波及；F5 是神圣快捷键且高频，弹窗=警报疲劳（原则 A/B） |
| 补全（递归） | **无弹窗**；要有进度 + 取消 | `n-progress` + `n-button` | 只增不改（F1），最坏是耗时耗盘，不是数据风险 |
| **重扫整片** | **`n-popconfirm` 确认（明示范围）+ 自动快照（可撤销）** | `n-popconfirm` + `/backup` | 唯一高危：整片覆盖；范围必须写进 confirm 文案（见下） |
| 清空/删除类（如将来做） | **`n-modal`** + 输入确认或二次 | `n-modal` | 无限波及且难快照，属于最高级，才配 modal |

**`n-popconfirm` 文案（极短，一行 + 范围）** `[推测]`
- 标题式问句：`整片重读？`；补充一行：`约 n 层 / 会覆盖记录`。
- 按钮：`重读` / `算了`（替代默认 Yes/No 的英文感）。
- 为什么把范围数字放进 confirm：用户提的担忧就是"覆盖成空"（§一）。让他**在按下去之前**看到波及面，是防误触的核心，而不是弹窗本身。

**机制排序（推荐优先级）**
1. 修数据层（P0-1）——比任何 UI 门槛都重要；`[事实驱动]`
2. 自动快照 = 可撤销（P0-2）——优于确认弹窗；`[推测]`
3. 确认弹窗只给最重的一个动作（P0-4）；
4. **不做**延迟执行、长按、双击确认（理由见 §4.1）。

### 4.5 落地到 naive-ui 的具体组件选择

| 场景 | 组件（naive-ui 2.45.3） | 说明 / 注意 |
|---|---|---|
| 重扫整片确认 | `n-popconfirm` | `trigger="click"`；**不要 hover**（§三.2）。放 `n-button` 上，主按钮行内 |
| 「更多维护动作」收纳 | `n-dropdown` | **`trigger="click"`**（不用 hover，解决 §三.1"不可见"）。选项：重扫整片 / 恢复上次备份 / 打开数据目录 |
| 逐次确认（点击 dropdown 选项后） | 由选项再触发 `n-popconfirm` | dropdown 负责"可见"，popconfirm 负责"确认"，两层职责分开 |
| 失败横幅（盘不在 / 读不到） | `n-alert` | `type="warning"`（盘不在）/ `type="error"`（读不到）；`banner` 或 `:show-icon`。位置：工具条下方、网格上方 |
| 空目录提示 | 复用现有 `.empty-tip`（灰字 div） | 保持"一行浅灰小字"（§四），**不引入组件**以免变重 |
| 进度 | `n-progress type="line"` `:show-indicator="false"` + 文本 | 进度条只表"在动"；数字走旁边的文本；动态分母故不给百分比 |
| 取消 / 停止中 | `n-button size="small"` | 原位切换；停止中 `:disabled` + 文案替换 |
| 完成 / 取消提示 | `useNotification`（`n-notification`） | 一行，带 `action` 槽可选放「撤销」按钮（配合快照） |
| 撤销入口 | `n-notification` 的 `action` 槽 或维护 dropdown 的「恢复上次备份」 | P2，且需后端补 restore（现状**只有 backup，没有 restore**，见 §5） |
| 数量角标 | 现有 `n-badge` | 保留 |
| 盘在线/离线标识 | `n-tag` 或 `n-badge`(dot) | 用于缓存面板列出各盘状态（配合 F8） |
| 刷新语义提示（可选） | `n-tooltip` | P2；**慎用**：hover 才可见的说明对 ADHD 等于没有，不如靠视觉等级差 |

**⚠️ naive-ui `update` 单 handler 坑的适用点** `[事实，来自任务背景]`
- 本方案若在 dropdown/popconfirm 里使用任何**表单控件**（例如未来加"范围选择" `n-select`），**不能**同时写 `v-model:value` 和 `:on-update:value`——它们是同一个 prop，后者会顶掉前者。
- 本方案当前**不新增表单控件**，因此默认规避；如后续要加，只保留一个写入点。`[推测]`
- 另：`apiUrl()` 是唯一 URL 出口（F10），本文任何新增请求（含 `/backup`）都必须经它，避免口令 `?t=` 丢失。

## 5. 正面回答：§2.3「读盘失败 → 写空缓存」若一时修不了，界面还能做什么兜底？

**先给结论：兜底能"止血 + 止慌"，但都不能替代 P0-1 修复。** `[推测，但基于 F3/F4]`
原因：F4 的写入发生在**服务端**、且是"删旧插新"。前端**无法阻止**那次覆盖，最多只能（a）让被覆盖后还能找回，(b) 让用户不至于以为数据没了。分三级：

**兜底 A（最有效，P0）：动作前自动快照。**
- 做法：刷新/重扫**触发前**先调 `/backup`（F7：纯本地文件拷贝，**零读盘**，不违反硬要求）。
- 为什么有效：把"不可逆"变"可恢复"。即使底下的写空 bug 还在，数据也能回滚。这是**唯一真正能兜住数据**的界面侧手段。
- 前提：`[推测]` 现有 `cacheBackup` 按天命名，同一天会覆盖 → 需要一个专用的"动作前快照"槽位，且需要补一个 **restore**（现状**无** restore 接口，`nedb.ts` 只有 `cacheBackup`）。

**兜底 B（止慌，P1）：「原本非空 → 结果为空」时不清空网格。**
- 做法：刷新/重扫后若返回空、而此前网格非空，则**保留旧内容** + `n-alert` `读不到，稍后再试`。
- 为什么只能算止慌：它**不阻止**那次覆盖写入，只是不让用户面对一片空白而怀疑数据丢失（正是 §2.2 的痛点）。诚实定位：观感兜底。

**兜底 C（P2）：把数据目录/备份暴露给用户。**
- 维护 dropdown 里加「打开数据目录」「恢复上次备份」（缓存就是 `%USERPROFILE%\.file-finder\searchCache.db` 单文件）。
- 为什么放最后：对 ADHD 用户而言"手动改文件名恢复"太技术化，是穷尽手段，不是方案。

**一句话给总指挥**：兜底 A 值得做（便宜、不读盘、真能救数据）；B 顺手做（低成本、止慌）；C 可延后。**但正确顺序仍是先修 P0-1**——否则每次刷新都在赌 `readdir` 不抖。

## 7. 明确不做的（附理由）

| 不做 | 为什么 |
|---|---|
| 后台自动监控目录变化 | 硬要求否决：会增加读盘 |
| 给所有覆盖类动作都加确认弹窗 | 警报疲劳，反而漏掉真正危险那次（原则 A） |
| 延迟执行 / 长按 / 双击确认 | 不可见、与神圣交互冲突、对 ADHD 不友好 |
| 进度百分比 / 全屏进度遮罩 | 分母动态使百分比假精确；遮罩违背"绝不碰网格" |
| 用 hover 触发重扫/维护菜单 | §三.1/§三.2 已证实是问题源 |
| 空状态做成图标+按钮的"好看的空状态" | §四 神圣：只有一行浅灰小字 |
| 改动双击/封面收敛/快捷键/拼音/面包屑等 | §四 神圣，不动 |
