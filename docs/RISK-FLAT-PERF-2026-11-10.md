# 平铺（任意层级）性能与隐患体检 —— 2026-11-10

> 业主：**"毕竟我们是 flat 向下平铺开来，如果代码写不好可能会对硬件或运行内存占用大、损耗大。"**
>
> 结论先说：**服务端不慢**（6 万条 30ms），真正的风险在**渲染层：网格是裸 `v-for`、没有虚拟滚动**，
> 平铺把"一屏几十格"变成"整棵子树几千格"。另外查到**一处纯浪费**（已修）和**三处随库变大的放大项**（待裁决）。

## 1. 实测（`docs/probes/flat-subtree/bench.mjs`，纯函数、零读盘、构造数据）

| 库规模 | 盘根平铺耗时 | 结果条数 | JSON 体积 | 堆增长 |
|---|---|---|---|---|
| 511 目录 / 3 000 作品 | 1.5–2.8 ms | 3 000 | 0.32 MB | 2.7 MB |
| 2 041 目录 / 16 000 作品 | 5.8–7.0 ms | 16 000 | 1.78 MB | 4.9 MB |
| 6 121 目录 / 60 000 作品 | 23.6–31.2 ms | 60 000 | **6.77 MB** | **15.9 MB** |

- **中间层 / 叶子层平铺**：0.2–3.7 ms、6–10 条 —— 深层平铺本身极便宜。
- 现库实测基线（`5 盘 · 218 记录 · 1 471 条目`）⇒ 盘根平铺约 **1 ms / 0.16 MB**，无感。`[推理]` 线性外推。
- 耗时随**该盘缓存条目数**线性涨；与"从哪一层开始"无关（都只遍历该盘全部 docs）。

## 2. 隐患清单（按"会不会真咬人"排序）

### ① 网格无虚拟化 —— 唯一真风险 `[静态代码]` + `[实测推论]`
`index.vue` 的网格是裸 `v-for`（`fileList` 全量），只靠 `v-memo` 减少**重渲染**。
代码注释里已经写明"532 项时每次方向键都会把整列 vnode patch 一遍"。
平铺到 6 万条 ⇒ 6 万个卡片 vnode + 6 万个 `n-image` 组件实例 + 6 万个 `<img>`（`:lazy` 只省解码，不省 DOM）。
**这是内存与卡顿的正主**，不是服务端。

> **2026-11-10 业主裁决：短期不做虚拟滚动，只做"不改结构的渲染层优化"。已做的那一条：**
> 图片/视频封面从 `n-image` 换成**原生 `<img loading="lazy" decoding="async">`**
> —— 每张卡省掉一个 Vue 组件实例 + 一套 props/watch + 一个 `IntersectionObserver`，
> 懒加载语义不变（浏览器原生实现）。目录的脸仍是 `n-image`（它要 70%/100% 的 `transform` 语义，
> 而平铺结果里根本没有目录条目，换了零收益）。
> **刻意没做**：`content-visibility: auto` —— 它要求 `contain-intrinsic-size` 给一个高度，
> 而卡片高度是窗口宽度的函数（列宽 × `--ff-cover-ratio` + 标题两行），估错就会让
> **滚动条长度在滚动中跳**；更要命的是 `useGridCursor.probeLayout` 读的是**每张卡的
> `offsetTop`**，占位高度一变，分行与"哪一行在视口里"都可能偏。收益不抵这个风险。

### ② `wire()` 里那次全库 `loadMeta` —— 平铺时 100% 白干 `[静态代码]` → **已修**
`safeSubtreeBytes()` = `loadMeta({ withBytes: true })`，内部 `nedb.find({})` **克隆全库（所有盘）**，
再按 serial 归并出"子目录名 → 字节数"。而平铺下发**全是叶子、没有目录条目** ⇒ 那张表一个都用不上。
现改为"这批数据里有 folder 才去算"。普通目录屏不受影响（它确实需要目录大小）。

### ③ `nedb.find({serial, mode})` 每次平铺都克隆整盘文档 `[静态代码]`
`findSubtreeLeafItems` 每次都把该盘**全部缓存文档（含 data 数组）**取出来。
nedb 的 `find` 返回的是副本 ⇒ 6 万条规模下每次平铺多一次十几 MB 级的瞬时分配，连续点平铺/刷新会推高 GC。
> 可选修法：加一层"按 serial+relPath 的行缓存，缓存写入时失效"（中成本，要谨慎——本项目缓存层纪律：永不自动删）。

### ④ 无上限、无熔断 `[静态代码]`
`openFolder` 对 flat 结果没有条数上限。10 万条级别大概率白屏/卡死在渲染。
> 三档可选的"刹车"：截断 + 「只显示前 N 条，还有 M 条未显示」（小）／分块渲染（中）／虚拟滚动（大）。

### ⑤ 过滤热路径：`filterByName` 每个按键对 N 条各做一次拼音 `[实测]` → **已加缓存**
`usePinYin` 原来**没有缓存**，搜索词以字母开头时每条都要 `makePy(name.slice(0, len))`。
平铺后 N 从几十变几千 ⇒ 每敲一个字母的 CPU 涨 N 倍。
**已做**：按输入串缓存（上限 2048，满则整表丢弃重建，不做 LRU）。
实测（`docs/probes/pinyin-cache/bench.mjs`）：

| 条数 | 冷（≈没缓存时的每键成本） | 热（同一个键） |
|---|---|---|
| 3 000 | 0.4–1.0 ms | 0.3–0.6 ms |
| 16 000 | 1.6–3.6 ms | 1.6 ms |
| 60 000 | 5.8–12.6 ms | 5.8–6.9 ms |

**结论要如实说**：缓存把首拍砍掉一半左右，但**剩下的成本主要是 `toUpperCase() + includes()` 扫 N 个名字**，
不是拼音本身 —— 6 万条最坏 12.6 ms，仍在 16 ms 一帧之内。所以这条是"顺手变好"，
不是"救命的优化"。

### ⑦ 封面模糊底预置 CSS 变量 ⇒ **无视 lazy，一屏 500 张全部请求** `[实测·业主在 DevTools 数出来]` → **已修**
卡片底下那层"放大模糊的同一张图"（`--cover-src` → `.card-cover::before`）原来是**模板里直接写死**的
`:style="coverBackdrop(item)"`，也就是给**每一张卡**提前写上 `background-image: url(...)`。
**CSS 背景图没有 `loading="lazy"`** —— 样式一解析浏览器就发请求，不管它在不在视口里。
⇒ 平铺 500 条 = 打开瞬间 500 个 `/thumb`；`<img loading="lazy">` 省下的请求被这一行全部抵消，
而且那 500 张图还各占一份解码内存（虽然同一 URL 命中 HTTP 缓存，但请求与解码都发生了）。

**修法**：模板不再预置；改成 `<img @load="onCoverLoad">`（目录的脸走 `n-image` 的 `img-props.onLoad`），
在**这张图自己下载完之后**才 `style.setProperty('--cover-src', url(...))`。
字节已在 HTTP 缓存里 ⇒ **零额外请求**；没进视口的卡连 `<img>` 都不加载，自然没有模糊底（显示卡片底色，正确）。
走 DOM 直写而不是响应式：一屏几百张卡没必要各过一次重渲染，这个变量也没有第二个读者。
> ⚠️ 这条**在本次优化之前就存在**（`coverBackdrop` 是既有实现），只是过去一屏只有几十张卡，看不出来；
> 平铺把它放大成"打开就 500 个请求"。它也是我在 §2① 里说"n-image 有额外开销"之外，
> **真正让 lazy 失效的那一条**。

### ⑥ 注释与实现不符（原判断）→ **是注释错了，不是代码错了** `[已核实]`
`mergeSubtreeLeafItems` 的文档原写着"4. 排序：按 name 自然序升序"，**实现里没有排序**。
2026-11-10 业主核对语义：**平铺必须按每个目录自身的原有位置顺序、原地展开**（谁在盘上排第几，
摊出来还是第几），**不要**按名字重排 ⇒ 实现本来就是对的，已把那条注释改成事实。
