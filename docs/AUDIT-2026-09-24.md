## 一、Tier 1 · 真问题（建议修）

### 1-1 【磁盘写放大 + 启动成本】缓存库 append-only，日常路径上**永不压缩**

**证据（读取真实 DB 文件逐行分类）**

用真 nedb 加载同一文件确认：内存里**只有 5 条有效记录、0 组重复键** —— 说明 `removeCache` 逻辑本身是对的，**但被删记录的全部字节永远留在文件里**。

**机制**

- nedb 每次 `insert` / `remove` 都是往文件**尾部追加**，文件只增不减。
- `compact()` 在 `nedb.ts:130` 确实写了，但**只被 `dropLegacyRecords()` 调用**（`nedb.ts:171`）。
- 而 `dropLegacyRecords()` 只在「存在 `v !== 2` 的旧记录」时才走到 `compact()`（`nedb.ts:162` 提前 return）。**一旦全库都是 v2，这个函数每次启动都直接 return 0，`compact()` 从此永不可达 —— 它已经是死代码。**

**代价（三样，都在同一根链条上）**

1. **写盘**：`scanAndCache` 是「`removeCache` + 整份 `insertCache`」（`index.ts:339-340`）。`videos` 根目录的一条 cover 记录就是 **1302 KB**。也就是说**每扫一次这个目录，就往系统盘写 1.3 MB，而上一份 1.3 MB 立刻变成永久垃圾**。
   - 实测单条记录大小：`videos|cover` 1302.2 KB（91 条）、`videos/示例演员E|cover` 420.4 KB、`videos|folder` 22.6 KB。
2. **启动成本**：nedb 的 `loadDatabase()` 会把**整个文件**读进内存解析。文件里 64% 是无用字节，等于**每次启动都白读、白解析 64%**。历史上这个文件到过 107 MB —— 那意味着启动要解析 107 MB。
3. **查询**：`loadMeta()` / `findOne` 都在这份持续膨胀的集合上跑。

**为什么现在只是 2.68 MB 而不是 107 MB**  
缩略图从「原图 base64」改成「480px base64」后体积小了约 8 倍。**新设计本身是对的**，问题只剩「一半字节收不回」。

**最小修法（三选一，我倾向 A）**

- **A. 按垃圾比例自动压缩**：`scanAndCache` 结束后判断 `文件大小 / 有效字节`，超过阈值（如 2×）就跑一次 `compact()`。一次性、无需新状态。
- **B. 每 N 次写入 compact 一次**：需要新状态（计数器）。
- **C. 顺手修 `F5` 的双重删除**：`openFolderController:377` 在 noCache 时已经 `removeCache` 了一次，`scanAndCache:339` 又删一次 —— 一次 F5 产生 **2 条 `$$deleted` 标记 + 1 条新记录**。删掉其中一次即可（省不了大头，但消除冗余写）。

### 1-2 【伤盘 + 可能永久卡死】没有并发闸门，且 ffmpeg 抽帧**无超时**

**证据（代码级，无任何反例）**

```
electron/utils/thumbnail.ts  →  grep timeout|setTimeout|kill  →  0 处
electron/server/index.ts     →  grep limit|queue|semaphore|mutex|pending  →  0 处
 src/views/FileFinder/index.vue →  loading 守卫只在 2 处（:185 handleOpen、:311 onRefresh）
```

**两条后果**

**(a) 多个 ffmpeg 同时啃同一块移动硬盘。**  
缓存未命中时，每个 `/openFolder` 都独立走 `scanAndCache` → 串行 spawn 抽帧进程。实测一个 6.91 GB 的视频，一次抽帧 = **835 ms**（另有 ffprobe 210 ms）→ 35 个视频的目录约 **37 秒**。  
前端只有两条入口有 `loading` 守卫（双击格子、F5）。**没有守卫的入口**：`openHistory`（历史面板双击）→ `openFolderInCover` / `handleDirChange`；`handleJump`（面包屑标签）；`onBack`。  
→ 在历史面板里连点两个不同目录，就是**两个扫描并行**，两个 ffmpeg 进程同时随机读同一块盘，磁头来回抖。这才是「伤盘」的真实形态，不是顺序读。

**(b) 一个卡住的 ffmpeg 会让整个目录的扫描永不返回。**  
`extractFrame` 只在 `'end'` / `'error'` 时 resolve。若 ffmpeg 挂住（**读取中把移动硬盘拔掉**、坏文件、USB 掉线但句柄未失效），`resolve` 永不触发 → `await makeThumb` 永不返回 → `for...of` 卡住 → `scanAndCache` 卡住 → `/openFolder` 响应永不发出 → 前端 loading 永久转圈，只能重启应用。

**最小修法**

- `extractFrame` 加超时（如 15 s）→ `resolve(false)` 并 `kill()` 掉子进程。**这是最该做的一条**，因为它是「永久卡死」而不是「慢」。
- 服务端加一个「同一磁盘只允许一个扫描在跑」的闸门（后来者复用进行中的 Promise）。比限制并发数更简单，也正好命中「不要多个 ffmpeg 同时啃一块盘」。

### 1-3 【内存无界增长】缩略图内存索引只增不减

**证据**

```ts
// thumbStore.ts
const store = new Map<string, string>();          // 无上限、无淘汰
export function newThumbKey(serial: string) {
    return `${serial.slice(0, 4)}-${Date.now().toString(36)}-${Math.random().toString(36).slice(2, 8)}`;
}
```

- `getThumb` 只读，`putThumb` 只写。**全文件没有一处 `store.delete` / `clear`**。
- `wire()` 对每个带缩略图的条目调 `putThumb`。**缓存命中时 key 与上次相同**（key 是跟着 DB 记录走的），`Map.set` 同键不增长 ✓；  
  **但重扫（F5 / 缓存失效）会产生全新 key**（`Date.now()` + 随机），旧 key 永久留在 Map 里。
- 单个缩略图 480px JPEG ≈ 20 KB → base64 ≈ 27 KB。

**量化**：`videos` 根目录 cover 扫一次 = 91 个条目。按其中约一半带缩略图算，**一次重扫就往内存里多留约 1 MB，永不释放**。F5 一百次 = 100 MB 常驻。

**顺带纠正一处注释**：`thumbStore.ts:8` 写「内存开销为零：Map 里存的是 nedb 文档里那个字符串的**引用**，不是副本」。  
引用不等于不占内存 —— 正因为它持有了那个字符串，那个字符串才**不能被回收**。这个注释读起来像「零成本」，实际是「每张缩略图 27 KB 永久常驻」。**这句注释比代码更容易误导人。**

**最小修法**：加个上限（如 2000 条）并在超限时删掉最早插入的一批。安全性论证：`/thumb` 的响应带 `Cache-Control: immutable`，浏览器不会重复请求同一个 key；即使用户回退到某目录导致重新请求，渲染层会重新 `/openFolder`，命中缓存后 `wire()` 会把 key **重新登记**回来。所以淘汰是安全的。

所以这是**潜伏 BUG，不是正在发生的故障**。但它就是一行的事：

```ts
type: stat.isDirectory() ? 'folder' : getFileType(ext)
```

### 2-2 【静默半失败】两个 fetch 不检查响应

`HistoryTable/index.vue`

- `loadDisks()`（:176）与 `getHistrotyList()`（:194）：拿到响应直接 `res.json()`，**不检查 `res.ok`，也不检查 body 里的 `code`**。
- 而 `/getHistory` 出错时返回的是 **HTTP 200 + `{code:500, error}`**（`index.ts:525`）→ `data.records` 是 `undefined` → `tableData.value = undefined`、`model.value.total = undefined`。n-data-table 收到 `undefined`、分页器总数变成 `NaN`。

### 2-3 【正则字符类里混进了竖线】

`FileFinder/index.vue` 的 `filterByName`：`/^[a-z|A-Z]/`

字符类里的 `|` 是**字面量竖线**，不是在表达「或」。所以 `[a-z|A-Z]` = 小写字母 ∪ `|` ∪ 大写字母 —— 搜索词里出现 `|` 时会被当成字母参与判断。  
这段逻辑本身就是从别处原样搬过来的（要保留的存量逻辑），但 `/^[a-zA-Z]/` 才是本意。**两处出现**（`filterByName` 里 2 处）。

### 2-4 【可读任意文件 + 非法 Origin 不拦】

`index.ts:416-448 / 570-582`

- `/raw` 只校验「以盘符开头」和「不含 `..`」，**不限制扩展名** → 任何本机进程都能通过它读**任意文件**的完整内容（MIME 兜底 `application/octet-stream`）。
- `cors()` 对**非白名单 Origin 只是「不设响应头」**（:574-579），**服务端本身照读照回**。  
  → 恶意网页里的 `<img src="http://127.0.0.1:3060/raw?p=C:/...">` 是**简单请求**，不受 CORS 约束，**请求会真的到达服务端、真的读盘、真的返回字节**。浏览器侧读不到像素，但**硬盘已经被读了**。

这不在你之前定的「不做」范围内（当时讨论的是 `Access-Control-Allow-Origin: *` 那条，那条确实已经修好）。这里是我这次新查到的两个独立缺口。**两处都是 1～2 行**：

- `/raw`：只放行 `MIME` 表里有的扩展名，其余 403。
- `cors()`：`if (origin && !allowed) { 403; return }`。

## 四、明确**没问题**的部分（避免只列负面造成误判）

- `driveIdentity.ts` 的「盘符不是身份、序列号才是」：`findDriveByLetter` 每次都用一次 `stat` 复核当前盘符的主人，盘符被复用时会整表作废重扫 —— 设计正确，实现也对。
- `splitPath` / `toFullPath` / `joinRel` 三处路径拼接：盘根不产生前导斜杠、反斜杠统一成 `/`、下发时补当前盘符。逻辑自洽。
- `readFolder` 的逐项 `try/catch`（一项失败只跳过它自己，不会让整个目录变空）—— 这是对的，原来的「整循环包一个 try」才是错的。
- `wire()` / `toWire()` 收敛成单一出口：缓存命中与非缓存（UNC/网络路径）两条路都过 `wire()`。原来只有一条路走，另一条会导致 `/thumb` 全 404。
- `/thumb` 的 `Cache-Control: immutable` + 一次性 key：安全（内容确实永不变）。
- `rawController` 流式读、不把整张图攒进内存；`videoThumb` 的临时帧在 `finally` 里 `unlink`（且落在**系统盘**临时目录，不是移动硬盘），时序正确（`imageThumb(frame)` 是同步的，读完才删）。
- `cors()` 的白名单（`file://` 的 `Origin: null`、`localhost`、`127.0.0.1`）+ `Vary: Origin`：正确。
- `app.listen(3060, '127.0.0.1')` + `EADDRINUSE` 的 `error` 监听：对。
- 主进程 `openDirectory` 用异步版 `showOpenDialog`（同步版会按住事件循环，而同一进程里跑着 3060 服务）；`openFile` 用 `shell.openPath(win32.normalize(p))` 而不是拼命令行。方向正确。
- `fileList` 是 `computed`：`dataSource` 与搜索词两个写入口都被消掉，导航竞态在结构上无法发生。
- `onUnmounted` 在 setup 顶层（不是 `onMounted` 回调里）。

### 6-1 【结果错乱】导航没有任何竞态保护，谁后到谁覆盖

**证据**

```
grep -rn "AbortController|requestId|reqSeq|abort()" src/  →  0 处
```

`fetchFolder`（`index.vue:277-295`）是「发请求 → `.then(data => dataSource.value = data)`」，  
**没有序号、没有取消**。而 `openFolderInCover` 是**同步**推栈 + 异步取数：

```ts
openStack.value.push({ path, mode: 'cover', name });   // 立刻改面包屑
searchStack.value.push(searchText.value);
searchText.value = '';                                  // 立刻清搜索框
fetchFolder(path, 'cover');                             // 数据稍后才到
```

**可复现路径**

1. 打开历史面板，双击目录 A（里面 35 个视频 → 服务端要跑 35 次抽帧 ≈ **37 秒**）
2. 不等它回来，立刻双击目录 B（1 个文件，几十毫秒返回）
3. B 先返回 → `dataSource = B` ✓
4. 37 秒后 A 返回 → `dataSource = A` ✗

结果：**面包屑显示 B，网格里是 A 的内容**。两处状态来自不同的时刻，而且没有任何提示。

`handleJump`（点面包屑）、`onBack`（返回按钮）、`openHistory`（历史面板）**都没有 `loading` 守卫** ——  
全项目只有 `handleOpen`（双击格子）和 `onRefresh`（F5）两处有。  
所以上面这条路径不仅可能发生，而且**是唯一没有闸门的那几条路**。

**和 1-2(a) 的关系**：同一个根因（没有闸门）的两个面 ——  
伤盘的那个面是"两个 ffmpeg 同时啃一块盘"，交互的这个面是"结果错乱"。

**修法（分两级，注意别修出新问题）**

- **前端丢弃过期响应**（~10 行，必做）：`const seq = ++reqSeq;` … 响应回来时 `if (seq !== reqSeq) return;`。  
  只改一行判断，解决错乱。
- **服务端同盘串行**（~15 行，1-2(a) 要的）：**不能简单地"复用进行中的 Promise"** ——  
  用户点 B 会拿到 A 的数据，错乱反而固化。正确做法是**排队**（后来者等前面的跑完），  
  或**抢占**（新的来时 `kill` 掉旧的 ffmpeg 子进程）。排队会让 B 白等 37 秒，抢占才是对的体验。

### 6-2 【静默失败 + 内容说谎】导航失败不留任何文字提示，且保留旧内容

**证据**（`index.vue:284-294`）

```ts
return fetch(...).then(res => res.json())
    .then((data: FileInfo[]) => { dataSource.value = data; loadingBar.finish(); })
    .catch(err => {
        console.error('[openFolder] 请求失败:', err);
        loadingBar.error();          // ← 顶部进度条闪一下红，没有任何文字
    })
    .finally(() => { loading.value = false; });
```

三个问题叠在一起：

1. **不检查 `res.ok`** —— 同一个项目的 `src/utils/request.ts` 里 `assertOk` 已经在做这件事，  
   这里（以及 `HistoryTable` 的两处 fetch）是漏网。**同一件事有两个写法，才是最危险的**。
2. **失败没有 `notify`** —— 全文件 `notify` 只在 `openFile` 失败时调用一次（`index.vue:262`）。  
   打开文件失败会说"打开失败"，**导航失败却一声不吭**。
3. **`dataSource` 只在成功时被赋值** —— 失败时它保留着**上一个目录**的列表。  
   于是：面包屑已经切到新目录、loadingBar 红了一下、**格子显示的是上一个目录的内容**。  
   用户没有任何线索意识到"这不是这个目录的东西"。

这一条比 2-2（`HistoryTable`）更该修，因为它发生在**每次导航的主路径**上。

### 6-3 【三义性空白】空目录 / 搜索无结果 / 加载失败，界面完全一样

**证据**

```
grep -rn "n-empty|empty-text|无数据|没有找到|暂无" src/views/FileFinder/ src/components/HistoryTable/  →  0 处
```

模板里只有 `v-for`，没有任何空态分支。三件事在界面上长得**一模一样**（一片空白）：

| 实际情况               | 用户看到                                                |
| ------------------ | --------------------------------------------------- |
| 目录真的是空的（如 `示例演员D/`） | 空白                                                  |
| 搜索词没匹配到（如搜 "zzz"）  | 空白 + 角标消失（`:24` 的 `n-badge v-if="fileList.length"`） |
| 请求失败（见 6-2）        | 空白 + 进度条红了一下                                        |

唯一能区分的线索是**角标消失**，而那恰恰是最容易被忽略的位置。  
加一个 `n-empty`（Naive UI 自带，描述文案按 `searchText` / `loading` / 空目录 三态区分）就能分开。
