## 二、逐处改动

diff：`docs/P1-diff-2026-09-24.diff`（index.ts 的 diff 已剔掉 P0 的 hunk，见该文件头部说明）。

### 1) `electron/server/index.ts` —— 新增同主键写入链 `writeChains` / `queueCacheWrite`

**原因**：`scanAndCache` 的 `removeCache + insertCache` 是两步非原子的。P1 之前只是偶发
（要用户恰好点进正在扫的那个目录），加了批量扫描就变成**必然**。

判据是「以后新增同类场景会不会复发」，所以**不**给每个调用方加锁，而是把这两步收进
`scanAndCache` 内部 —— 它是这套缓存**唯一**的写入入口：

```ts
const writeChains = new Map<string, Promise<void>>();

function queueCacheWrite<T>(serial: string, relPath: string, mode: OpenMode, task: () => Promise<T>): Promise<T> {
    const key = `${serial}\u0000${relPath}\u0000${mode}`;
    const prev = writeChains.get(key) ?? Promise.resolve();
    const run = prev.then(task, task);              // 前一个失败也接着跑，链不会卡死
    const tail = run.then(() => undefined, () => undefined);   // 链上挂的尾巴不许 reject
    writeChains.set(key, tail);
    void tail.then(() => { if (writeChains.get(key) === tail) writeChains.delete(key); });  // 链跑空就收槽位
    return run;
}
```

- 键是 `(serial, relPath, mode)`：**不同目录之间不互相同步**，否则扫一整块盘会退化成"全库串行"。
- **读盘（`readFolder`）留在队列外面**：它慢，两个并发扫描各读各的没有危害；会互相破坏的只有"写"。
- 后写的整条覆盖先写的 —— 这正是想要的语义。

这和 `wire()` 是唯一下发出口、`apiUrl()` 是唯一 URL 出口、口令校验挂在唯一请求入口是同一个思路。

```ts

-
```

**它是多余的**：`noCache` 时 `cached` 必为 `null`，下面必然走 `scanAndCache`，而它自己就会

### 5) `src/views/FileFinder/index.vue` —— 脚本：新增一块（`SCAN_MODE` → `onScanSelect`）

| 名字 | 做什么 |
|---|---|
| `SCAN_MODE = 'cover'` | 界面三条入口都用 cover，扫描必须同模式，否则缓存键对不上 |
| `SCAN_BATCH = 20` | 每 20 个目录主动让出一次事件循环 |
| `scanning` / `scanDone` / `scanPending` | 渲染状态：进度「已扫 n / 待扫 m」 |
| `scanCancelled`（普通 `let`，不是 ref） | 取消标志；每个目录边界读一次 |
| `requestFolder(path, noCache)` | **批量扫描专用的取数**，只往返、不写任何界面状态 |
| `splitDrive` | `盘符:路径` → `{drive, relPath}`。渲染层不能 import `driveIdentity`（会拖进 `node:fs`），和 `VIDEO_EXT_RE` 重写一份同理 |
| `fetchScanContext` | `/getDisks` 拿盘符→序列号；`/getHistory` 分页取全 → `(serial, relPath)` 集合（小写） |
| `startScan(rescan)` | 队列主体 |
| `onScanCancel` / `scanMenu` / `onScanSelect` | 取消 + 下拉菜单 |

`startScan` 的骨架：

```ts
const queue: string[] = [root];            // 深度优先，队列里是**完整路径**
while (queue.length) {
    if (scanCancelled) break;              // 取消只在目录边界检查
    const dir = queue.shift()!;
    scanPending.value = queue.length + 1;  // +1 = 正在扫的这个也算"待扫"
    try {
        const items = await requestFolder(dir, rescan);   // rescan ⇒ noCache=true
        const key = keyOf(dir);
        if (rescan || key === null || !keys.has(key)) scanDone.value += 1;
        for (const item of items) {
            if (item.type === 'folder') queue.push(fullPathOf(item));
        }
    } catch (err) { console.error('[批量扫描] 目录失败:', dir, err); }   // 单个失败不中断整轮
    scanPending.value = queue.length;
    processed += 1;
    if (processed % SCAN_BATCH === 0) await new Promise(r => setTimeout(r, 0));
}
```

**两个模式的全部差别就是一个 `rescan`**（§16.1：「同一套队列多一个 flag」）：
不带 `noCache` = 服务端命中缓存就只回缓存、不碰盘；每层 `noCache=true` = 忽略缓存重读。

**进度语义**：`n` 只数**真扫过**的目录（缓存命中的不算，那种没碰盘）；`m` 是队列里还没扫的，
每展开一层就把新发现的子目录加进去，所以会**动态增长**。

## 四、偏离规格的地方（单列）

### 4.1 ⭐「已缓存」只跳过**重新扫它**，**不剪掉它的子树**（最重要的一条）

§16.1 的写法是「对每个目录 → 若在已缓存集合里 → **跳过**」，按字面实现就是**连子树一起剪**。
我**没有**照字面做，理由有两条，第一条是致命的：

1. **字面实现会让根目录永远无事发生。** 用户点按钮时他正在看这个目录，而对盘符路径来说
   "正在看"就意味着它**刚刚被 `/openFolder` 写过缓存**（缓存要有卷序列号，UNC / 网络位置那条路
   本来就不缓存，属于例外）—— 根目录**必定**在已缓存集合里。按字面实现，点一下 = 立刻结束。
2. **剪子树会在真实数据上留永久窟窿。** 已缓存的目录下面**仍然可能有没缓存的子目录**，
   而再次点击也补不回来（父目录永远已缓存）。用你的真库取一个实例：

   - `videos/示例演员E` **已缓存**（活库实测，`serial=BBBB2222`，`count=13`）；
   - 它本身是个**有子目录**的目录（§2.5 的注释：11 个视频 + 2 个子目录；`count=13` 与"13 个条目"自洽）；
   - 那 2 个子目录**一条缓存都没有**（活库 23 条里没有任何 `videos/示例演员E/...`）。

   → 从 `E:/sample/videos` 点「补全缓存」，字面实现会跳过 `示例演员E`，那 2 个子目录**永远不会被扫**。
   （证据边界：`示例演员E` 的缓存状态与"无子目录缓存"是我只读解析活库 `searchCache.db` 实测的；
   "2 个子目录"引用 §2.5 的探针输出 —— 我按约束**没有**去读 `F:/`。）

**我的实现**：缓存集合只用来把「已扫 n」数准；**"跳过真扫"由服务端那一个出口保证**
（`openFolder` 里的 `findCache` —— 命中就只回缓存、一字节都不读盘）。**这样解释才对得上 §16.1 第 2 条
原文「只扫没有缓存的目录」**：跳的是"扫"，不是"走"。

**代价**：已缓存的目录仍要发一次请求（几十 ms 级、不碰盘），换来的是"补全"真的补得全。
**这是本批唯一一处我按自己的判断改了语义的地方，请重点看。**

### 4.2 删掉了 `noCache` 分支那句孤立的 `removeCache`

§16.1 只说"把 `remove+insert` 收进唯一写入点"。但那句孤立的 `removeCache` **也是写同一主键的口**，
不收掉的话"唯一写入点"这句话就不成立。它本身是死代码（后面必然走 `scanAndCache`），见 §二.3。

### 4.3 按钮位置：放在**网格上方那条工具条的右侧组**，没有新加一行

§16.1 只说「网格上方」，并说"按钮位置和文案可按他的意见改"。
现有结构里，`header-bar` 就在网格正上方，且已经是"对当前这一层做什么"的按钮组（刷新/历史）。
新加一行会打破他原有的内联结构。**要挪一行很简单，说一声。**

### 4.4 递归用 `fullPathOf(item)`（带 `ext`），不是网格双击那种 `${dir}/${name}`

`handleOpen` 进目录用的是 `${item.dir}/${item.name}`，而目录名里的点会被 `getFilename` 吃掉
（`TST-001.2023` → `SSIS-001`）。`fullPathOf` 会把 `ext` 拼回去，是**无损**的。
所以我用 `fullPathOf` —— 也就是"和网格双击不完全一致"。**现有 `handleOpen` 那条路我没动**（那是用户的特性）。

### 4.5 「每批让一下」= 让出事件循环，不是电气停顿

实现是 `await new Promise(r => setTimeout(r, 0))`。
**它解决的是"取消按钮有没有机会响应"，不是给 USB 电气喘息** —— 那件事主要由**串行**（一次一个目录）保证。
要真停顿（比如每批歇 200ms）就改 `SCAN_BATCH` 附近那一行，说一声。

### 4.6 顺带一提：已缓存集合在"重扫"模式下不参与判断

`rescan=true` 时每层都 `noCache`，集合只用于计数（`scanned` 直接 +1）。这是必然的 ——
重扫的语义就是"别管路缓存里有什么"。

## 五、探针踩到的三个坑（记下来，别再犯）

| # | 坑 | 表现 | 处置 |
|---|---|---|---|
| 1 | **两个变体共用一棵夹具树** | 阶段 4 往 `A` 里写 `late.txt`，第二个变体的"阶段 1 播种"就带着它了 → "补全不该看到 late" 被判成**假 FAIL** | 每个变体一棵全新夹具树。**夹具是前置状态的一部分** —— 和 P0 的"探针可复算性 = 脚本 + 前置状态"是同一条教训 |

### 7.2 我补的一处加固（**新代码内的 3 行**，不在用户代码里）

**目录成环没有保护。** 原实现只按 `item.type === 'folder'` 入队，**没有 visited 集合**：
Windows 上 `stat` 会跟进重解析点，一个指回祖先的 junction/符号链接会让队列**无限增长** ——
手动点时最多是用户自己点晕，批量扫就变成**永不停机**（只能靠"取消"兜）。
按"正确的方式修"的标准，这类保护属于新功能自身的健壮性，不是打补丁，所以我直接加了：

```ts
const visited = new Set<string>([root.toLowerCase()]);   // 已入过队（小写归一化）
...
for (const item of items) {
    if (item.type !== 'folder') continue;
    const child = fullPathOf(item);
    const norm = child.toLowerCase();
    if (visited.has(norm)) continue;   // 成环保护
    visited.add(norm);
    queue.push(child);
}
```

加完重跑 `vue-tsc --noEmit` → **exit 0**。
副作用（可接受）：同一目录被两条路径指到也只会扫一次 —— 这正是想要的。

理由：重扫扫的恰好包含用户正在看的那一层，不刷新会被当成"按钮没生效"。
