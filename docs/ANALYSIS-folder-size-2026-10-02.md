# 分析 · 文件夹条目为什么不显示大小（以及要修的话怎么修）

> 2026-10-02 · 结论全部有实测支撑，证据在 `docs/probes/folder-size/out.txt`。
>
> ✅ **本文的分析已落地**（2026-10-02，用户批准后实现）。
> 实际改动、验证结果、以及实现时差点踩的坑，见 **`docs/CHANGES-2026-10-02.md` §六**；
> 验证探针 `docs/probes/folder-size/verify.mjs`（15/15）。本文保留为**分析原文**。

## 1. 根因：不是"接口没返回"，是**返回了 0**

`electron/server/index.ts` 的 `readFolder`：

```ts
const stat = await fsasync.stat(filepath);          // L247

const info: FileInfo = {
    dir: storeDir,
    name: getFilename(file),
    isDirectory: stat.isDirectory(),
    ext,
    type: stat.isDirectory() ? 'folder' : getFileType(ext),
    size: stat.size,                                 // L270  ← 问题在这
};
```

**Windows 上 `fs.stat()` 对目录返回的 `size` 是 0**（NTFS 不在目录项里记字节数，
不像 Linux 的 ext4 会给 4096）。所以：

```
目录  → stat.size = 0  → formatBytes(0) → '—'   ← 用户看到的"没有 size"
文件  → stat.size = N  → formatBytes(N) → '3.42 GB' ✓
```

字段**一直都在**、类型也对（`FileInfo.size: number`），只是值恒为 0。
`formatBytes` 的契约是 `0 / 空 → '—'`（`src/utils/index.ts:3`），所以渲染成破折号。

> 顺带：这**不是**"接口忘了返回"。真的要"返回目录大小"，在 Windows 上**没有任何
> 一次系统调用能直接给出来** —— 必须遍历目录累加。所以问题的本质是
> "**这份数据得自己算**"，而不是"漏了个字段"。

---

## 2. 为什么"有些文件夹反而有大小"

同一次遍历里，**收敛成封面的条目**走的是另一条路（`handleCover`，L346-398）：

```ts
let size = 0;
for (...) {
    size += stat.size;                        // L360  累加子文件
    files.push({ name: file, size: stat.size });
}
...
    size: size + stat.size,                   // L398  = 所有文件之和 + 封面图
```

⇒ 所以网格里长得像"一张封面"的那些卡片**有大小**（它是被算出来的），
而**普通目录**（`type: 'folder'`，双击下钻用的那种）是 `stat.size` = 0。
**这就是"同样是文件夹，有的有、有的没有"的来源。**

## 3. 要算目录大小，有两条路 —— 只有一条能走

| 做法 | 要不要读盘 | 可行性 |
|---|---|---|
| **递归遍历磁盘算总和** | ⚠️ **要**（读目录项 + 逐文件 stat） | ❌ 直接违背项目第一目标「减少对移动硬盘的读写」 |
| **查缓存库聚合**（已扫过的记录里就有每层的字节和） | ✅ **不要**（nedb 全库常驻内存） | ✅ 见下 |

缓存库那条路是可行的，因为**每一条缓存记录里已经隐含了"这一层的文件字节总量"**：

```ts
// electron/server/nedb.ts:430 —— loadMeta({ withBytes: true }) 里
bytes: data.reduce((n, it) => n + (it.size || 0), 0)
```

（`data` 就是那一层扫到的 `FileInfo[]`。目录条目的 `size` 是 0，所以求和出来的
**恰好就是"这一层的文件总量"** —— 语义刚好是我们想要的。）

于是：

```
某个目录的**子树总量** = Σ { bytes(m) | m.serial 相同 且 m.relPath 在该目录子树内 }
```

⚠️ 前缀匹配必须按**路径边界**（`root + '/'`），不能裸 `startsWith` ——
否则 `a` 会误吃掉 `ab` 的大小。
（实测确认：库里 `relPath` 用的是 `/`，211 条含 `/`、0 条含 `\`。）

## 4. 实测（真库，`docs/probes/folder-size/out.txt`）

手法：esbuild 把**真源文件** `electron/server/nedb.ts` 打成 bundle 在纯 Node 里跑；
库**拷一份到临时目录**再读（`loadDatabase()` 末尾会整库重写，不能碰正在用的真库）。

```
① 单次 loadMeta({withBytes})   中位 0.80~0.90 ms（9 次，最小 0.62 / 最大 2.08）
② 最坏情况 O(n²)：213 条记录各算一次子树总量   合计 2.2~2.4 ms（摊到每条 0.011 ms）

③ 缓存记录维度
   记录数 213 · 这一层有内容的 209（98%）· 子树能算出的 210（99%）

④ ⭐ 子文件夹维度（**这才是用户实际会看到的**）
   有子文件夹的层数 8 · 平均每层 26.0 个子文件夹
   子文件夹总数 208 · **能算出大小的 205（99%）** · 算不出的 3
```

**为什么 ④ 才是真指标**：③ 量的是"缓存记录本身能不能算出大小"，
而用户要的是"进到一个目录，网格里**那些子文件夹**各自多大" ——
取决于**那个子文件夹自己有没有被扫过**。实测 99% ⇒
他平时是**整片递归扫**的，所以子树基本都有记录。

**零读盘**：全过程只读 `searchCache.db`（本地文件）与内存，**不碰任何移动硬盘**。
全库合计 3.33 TB 与缓存面板显示的 3.35 TB 对得上（交叉验证 ✓）。

## 5. 真要做的话，改动长什么样

> ⚠️ **本节已订正**：下面表格里写的落点（`readFolder`）**是错的** ——
> 交付后用户实测"重启还是 `—`"，才发现浏览已缓存的目录走 `findCache` 短路、**不经过 `readFolder`**。
> 而且补在那一层还会让目录的 size 被写进缓存，与 `bytes` 的 `data.reduce(Σ size)` **双算**。
> **实际落点是 `wire()`**（下发态的唯一出口）。全过程见 `docs/CHANGES-2026-10-02.md` §六。
> 原文保留在下面，作为"这条推理链当时在哪一步断的"的记录。

| 文件 | 改什么 | 量级 |
|---|---|---|
| ~~`electron/server/index.ts` · `readFolder`~~ → **`wire()`** | 聚合一次"子目录 → 子树总量"的 Map，给 `type === 'folder'` 的条目补 `size` | **~25 行**（含注释）|
| `src/views/FileFinder/index.vue` | **0 行** —— `:title="item.name + ' ' + getSize(item.size)"` 已经写好了 | 0 |
| `electron/server/index.ts` · `FileInfo` | **0 行** —— `size: number` 早就有 | 0 |

**关键实现细节（决定是否"正确"而不是"打补丁"）**：

1. **一次聚合、N 次 O(1) 查** —— 不是给每个子目录各查一次库。
   即 `readFolder` 里调**一次** `loadMeta({withBytes:true})`，建一张
   `(serial, relPath) → 子树总量` 的表，然后每个 folder 条目查一次。实测这比朴素
   写法（每个子目录各遍历全库）省一个数量级。
2. **粒度按"子树"而不是"这一层"** —— 目录的价值就是它**里面**有多少东西。
   只算"这一层"会把 `演员名/` 这种目录显示成几百 KB（它自己那层只有封面图）。
3. **拿不到就保持 `—`** —— 没扫过的目录显示 `—`（实测只有 3 个），
   **不要**为了补齐它去读盘。这与缓存面板的语义一致：显示的是**上次扫到那一刻**的快照。
4. `readFolder` 是每次进目录都走的热路径 ⇒ 多 0.9 ms/次，可接受（一帧预算 16 ms）。

## 6. ⚠️ 实现时必须守住的一条：聚合失败要**降级**，不能连累列表

现在 `readFolder()` **完全不依赖缓存库** —— 缓存库坏了，目录照样列得出来。

加了聚合之后就有依赖了：`loadMeta()` 内部第一句是 `assertUsable()`，
**库加载失败 / 正在还原时它会抛**（`nedb.ts:195-202`，那两个状态是真实存在的：
加密密钥对不上、还原过程中的 `restoring`）。

⇒ 如果把聚合直接写在 `readFolder` 的主流程里，**缓存库一坏，整个目录就列不出来了** ——
从"没有大小"退化到"什么都看不到"，这比原缺陷严重得多。

**正确做法**：聚合整段 `try/catch` 包住，失败就当"这次算不出来"，
`size` 保持 0（渲染成 `—`），**照常返回目录列表**。
判据还是那条：**责任放在唯一的聚合点，且它的失败不能向上扩散**。

---

## 7. 限制（先说清楚，免得做完发现不对）

- **只对"被扫过"的目录生效**。没扫过的目录 hover 仍然是 `—`。
  实测当前命中率 99%，但**新插的盘 / 没扫过的目录**会是 `—`，这是设计使然。
- **是快照，不是实时**：显示的是"上次扫到那一刻"的大小，之后删/移文件不会更新。
  与缓存面板的 `bytes` 语义**完全一致**（注释里就是这么定义的）。
- **不是所有文件夹都变小**：如果某个子目录本身就在库里、但它是空的（0 字节），
  仍然显示 `—`。
- ⚠️ **未实测**：上面 1-5 条是**实测**；"改动 20-25 行"是**按现有代码结构估的行数**，
  不是写完之后数的。

## 8. 顺带：有个几乎零成本的选项

缓存记录的 `CacheMeta` 里**还冗余存着 `count`**（这一层的条目数，用于 `{ data: 0 }`
跳过 base64）。所以同一张表可以顺手带上条目数，hover 显示成：

```
示例作品标题   12 项 · 3.42 GB
```

信息量比一个裸大小更大，而**成本是同一份数据、同一张表**（`count` 不需要再聚合）。
既有测量里没单独量它，但它不需要碰 `data`，比 `bytes` 只会更便宜。
