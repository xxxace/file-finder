## 一、这个程序是什么

**本地移动硬盘封面浏览器**（面向影视/图片资源库）。

数据流：选文件夹 → 主进程 HTTP 服务（3060）读目录 → 给每个文件取封面（图片读原图、视频抽 1% 帧）→ 转 base64 → **整包 JSON 返回** → 渲染层铺网格 → **整包写进 nedb 缓存**。

## 二、你提的 5 个问题，逐条回答

### 问题 1：一次性返回全部、且是 base64 —— 方向对，但严重度我初判高了一档

**实测：单条 payload 中位 674 KB、最大 4.31 MB。** 回环 HTTP 下这不是灾难。**所以你怀疑的方向对，但它不是最痛的那一刀。**

真正被这一个设计连带出来的是三件事：

**(1) nedb 把图片当文档数据，100 MB 常驻内存**

`nedb` 在 `loadDatabase()` 时把**整个文件读进内存**，所有文档常驻。所以：

- 启动要 `JSON.parse` 101.6 MB 的 base64 → 实测 **361 ms，堆峰值 314 MB**
- 一个「看看硬盘上有什么封面」的小工具，主进程常驻 100 MB 以上，只为了 107 个目录的封面
- 渲染进程 `fetchCache`（`index.vue:109`）再存一份 base64 → 双份

**(2) nedb 是 append-only，而代码从不压缩 → 文件会无限膨胀**

已核对 `node_modules/nedb/lib/persistence.js:200`：`persistNewState` 走的是 **`storage.appendFile`**。

也就是说**每次 update 都往文件尾部追加一整条文档**（含全部 base64），只有调用 `compactDatafile()`（`persistence.js:148`）才会重写。

而你的代码里**从未调用过它**。后果：

> `updateDrive` 会给每条匹配记录 append 一条**含全部 base64** 的文档。
> 换一次盘符 = 往 103 MB 的库里再追加 103 MB。**文件先涨到 206 MB，下次启动加载翻倍。**

这是比 payload 大得多的隐患。

**(3) 换盘符要搬 100 MB**

`index.ts:349` `JSON.parse(JSON.stringify(cache))` —— 深拷贝整条含 base64 的记录，只为了改一个字符串前缀。见问题 4。

**结论**：base64 塞进 JSON 确实不合理，但**它真正的代价不在网络，在内存和 nedb 的使用方式上**。解法见第四节。

### 问题 2：懒加载 —— 形式上写了，实质上是假懒加载

**你没记错，代码里确实有**：`src/views/FileFinder/index.vue:47,48` 两个 `n-image` 都写了 `:lazy="true"`。

**但它一点用都没有**：

- `n-image` 的 `lazy` 靠 IntersectionObserver 延迟设置 `img.src`。而这里的 `src` 是 **base64 data URI**——数据早就在内存里了。懒加载只推迟了「解码」，没有省下任何一次磁盘 IO、任何一字节传输。
- 真实开销发生在更早：数据在网络层就传完了、在 `JSON.parse` 时就进内存了、在 Vue 响应式里被代理了。**这三笔账 lazy 一笔都省不掉。**

**另外**：

- `index.vue:44` `v-for="item in fileList"` **全量渲染 DOM，没有虚拟滚动**。1000 个文件 = 1000 个 `.image-box-item` + 1000 个 `n-image` 实例。
- `index.vue:46-49` 只有 folder 的 avatar 加了 `preview-disabled`，图片/视频的 `n-image` **都开着预览层**，每张都挂额外事件与 DOM。
- `index.vue:109` `fetchCache` 是普通对象，**无上限、永不清理**。

**真正的懒加载长什么样**：`<img src="http://127.0.0.1:3060/cover?path=...">` —— 浏览器原生并发（每域 6 连接）、原生磁盘缓存、进入视口才发请求、渐进式解码。见第四节 B 方案。

### 问题 4：缓存无法识别属于哪块硬盘 —— **解药已经在你的数据里**

每条缓存记录里都有 `dev` 字段。**`dev` 就是 NTFS 卷序列号。** 已核对 libuv 源码 `src/win/fs.c`：

```c
static void fs__stat_assign_statbuf(uv_stat_t* statbuf, FILE_STAT_BASIC_INFORMATION stat_info, ...) {
  statbuf->st_dev = stat_info.VolumeSerialNumber.LowPart;
```

序列号取自 `NtQueryVolumeInformationFile(FileFsVolumeInformation)`，**与盘符无关**：

| 场景 | 盘符 | 卷序列号 |
|---|---|---|
| 硬盘今天插上 | `H:` | `FE91E472` |
| 硬盘明天插上 | `K:` | `FE91E472`（同一个数，不变） |

而现在的实现（`index.ts:346-365`）是**按盘符字符串前缀替换**：

```js
newCache.path = cache.path.replace(from, to);                      // 只替换第一处出现
newCache.data.forEach(nc => { nc.dir = nc.dir.replace(from, to) });// 深拷贝含全部 base64
```

**结论**：把「盘符」从身份标识降级为「当前挂载点」。用 `dev` 作硬盘身份，启动时枚举盘符建 `序列号 → 盘符` 映射，自动重映射。**用户永远不用再点「盘符变更」。**

顺带：`dev` 已经在每条记录里，**存量缓存现在就能直接受益**，不需要重扫。

### 问题 5：服务接口写得乱七八糟 —— 诊断成立，但**我不建议砍掉 HTTP**

**先收回我初版的提议。** 你说「我想玩前后端分离，不走 IPC 那套，反而更简单」——这个理由是成立的，我初版推 IPC 是过度设计：

| 理由 | 判断 |
|---|---|
| 性能 | **不成立**。本地回环 + JSON 序列化的开销，在 payload 从 674 KB 降到 10 KB 之后完全无关紧要。性能瓶颈从来不在通信层 |
| 可观测性 | **成立**。DevTools Network 面板能逐条看请求、能 curl、能用浏览器直接开 `localhost:3060` 调试。IPC 没有这个窗口 |
| 可维护性 | **中性**。乱不是 HTTP 造成的，是下面 4 条造成的 |
| 本质问题 | 你的「前后端分离」是**形式上的**——server 跑在 main 进程里，生命周期完全绑定，拿不到独立部署的收益，却付了绕一圈的成本。但这是取舍不是错误，**不值得为此重写** |

**真正要修的是 4 条与协议无关的问题**：

1. **地址硬编码散落 5 处**：`index.vue:185,197,255`、`HistoryTable:146,217,246`、`DriveChanger:79`，且 `localhost` 与 `127.0.0.1` 混用。→ 收敛成一个 client + 一个 baseURL 常量。
2. **返回值 4 种形状**：`getHistory` 返 `{records,total}`、`openFolder` 返裸数组、`removeHistoryBatch` 返 `{code,message}`、`updateDrive` 出错也返 HTTP 200 + `{code:500}`。→ 统一 `{ code, data, message }`。
3. **`postAction` 不检查 `code`**（`request.ts:1-12`）→ `DriveChanger:80` 拿到 `{code:500}` 照样 `message.success(undefined)`：**界面提示成功、实际失败**。→ P0-4。
4. **错误处理几乎为零**：`app.listen` 无 `on('error')`（端口占用则**启动即崩**）；`JSON.parse(req.body)` 无 try/catch；`collectCodeList` 用同步 IO 且 `path` 为 null 时抛错无人接。→ 这三条都是**主进程崩溃**路径。

还有两条与「分离」无关但确实脏：`deletAction` 拼写错误且被用来调 `/backup`（备份用 DELETE 方法，语义错乱）；每个 handler 手写 3 行 `setHeader`，其中有 `'chartset'` 拼写错误（无害所以没人发现）。

## 四、解法

### 先回答你的问题：`file-docker` 这个设计好不好？→ **方向是对的，只是没做完整**

**第一性原理**：封面是从原图/原视频**派生**出来的，而原文件就明文躺在**同一块盘的同一个目录**里。

```
H:/新建文件夹/示例演员M/
  ├── TST-4519.mp4        ← 原始明文，一直在那，谁都看得到
  └── file-docker/…        ← 派生品，不增加任何新的可读信息
```

**看到封面的人，本来就能看到原文件。所以 file-docker 在你这个场景下不构成额外泄露。**

真正会构成新泄露的只有这三种，你要防的是这些：

| 情况 | 有风险吗 |
|---|---|
| 封面和原文件在同一块盘 | **没有**，信息量等价于原文件名 |
| 把封面**聚合**到某一处 / 上传云端 | **有**，会形成一份「你看过什么」的清单 |
| 硬盘只拷走 `file-docker` 给别人 | 理论上有，但没人这么干 |

**所以你允许明文存储的直觉是对的。我不该提议「改成不落盘」——那会丢掉「缓存跟盘走」这个核心收益**（换电脑、换盘符、重装系统，缓存都还在；这恰恰是 DB 放在 C 盘做不到的）。

**但这个设计有三个真实缺口**——不是泄露，是没做完整：

| # | 缺口 | 证据 |
|---|---|---|
| 1 | **图片封面没跟上**。视频走 file-docker（跟盘走），图片却 base64 存进 C 盘 nedb（**不跟盘走**）。两套策略并存，DB 因此膨胀到 103 MB | 实测缓存 107 条全部 `H:\`，101.6 MB 是 base64 |
| 2 | **视频封面尺寸失控**。`size: '320x240'` 被注释掉 → 抽的是原始分辨率帧，**1280×720 PNG，base64 1.1–1.2 MB/张**，是图片封面的 **7.4 倍** | 实测 2 条 video 条目 |
| 3 | **命名互相覆盖**（P1-8）。`fileInfo.name + '.png'` 用的是**剥掉扩展名**的名字 → `TST-027.mp4` 与 `TST-027.jpg` 都映射到 `TST-027.png` | `index.ts:85` |

**正确方向不是替换 file-docker，是把它补完。**

### 顾虑 1：为什么要换掉 HTTP？→ **不换了**

收回。保留 HTTP，修复 P2-1（安全面）、P0-5（端口崩溃）、P0-1（URL 编码），再收敛成一个统一 client + 统一响应体。**通信层不是瓶颈，不值得重写。**

### 顾虑 2：隐私 → **改成「把图片也纳入 file-docker」，而不是不落盘**

先给你一个仍然是事实、但结论要改的判断：

> **base64 不是加密。** 用记事本打开 `searchCache.db` 就能看到 `data:image/jpeg;base64,/9j/4AAQSkZJRgABAQ...`，任何人都能还原。
> 所以现在 DB 里那一份**既没提供隐私保护，又丢了跟盘走的收益**——两头不占。

修正后的方案：

| | 现在 | 建议 |
|---|---|---|
| 视频封面 | `file-docker/<剥扩展名的name>.png`，1280×720 PNG，**1.1 MB** | `file-docker/<完整文件名>.jpg`，480 px JPEG，**约 20 KB** ← 缩 **56 倍** |
| 图片封面 | base64 存 C 盘 nedb，161 KB/张 | **同一条路**：`file-docker/<完整文件名>.jpg` |
| 元数据 | 和 base64 混在同一条 nedb 记录 | nedb 只存文件名/大小/时间/`dev` → **1.5 MB** |
| 前端取图 | `<n-image :src="base64">` | `<img src=".../thumb?d=H&f=xxx.jpg">`，浏览器原生并发 + 渐进解码 |
| `openFolder` payload | 674 KB（含 base64） | **约 10 KB**（只含缩略图文件名） |

**收益**：缓存跟盘走（你原本的意图保住）+ DB 103 MB → 1.5 MB + payload 674 KB → 10 KB + 真懒加载成立。

**代价（如实说）**：

1. 移动硬盘**只读 / 写保护**时 `mkdocker` 会失败 → 必须降级成「不缓存、每次重算」，而不是报错或卡住。
2. 存量缓存要处理：DB 里的 base64 可以**一次性提取**写成 file-docker 文件（我可以写迁移脚本），也可以直接丢弃重扫。
3. 视频封面换成 jpg 后旧 png 成为孤儿文件（可顺手清理）。

**配套要修的**：`file-docker-list.txt` 写在 `process.cwd()`（打包后不可靠，现有文件里 `D:/file-docker` 还重复了两次）→ 建议移到 `~/.file-finder/`，或直接废弃（启动时枚举各盘扫 `file-docker` 就够）。另外 `file-docker` 目录本身会在盘根被当普通文件夹显示，建议加进 `excludedFiles`。

### 顾虑 3：缩略会影响画质吗？→ **不影响，而且现在才是真浪费**

先算你的格子实际多大：

```
--item-width: calc(100% / 6)        // 一行 6 个
窗口 1200px → 每格 200px，减去 gap/margin ≈ 180px
.n-image { height: calc(100% - 36px) }  → 图片显示区约 180 × 144 px
窗口 1920px → 每格约 320 × 256 px
```

对比实测的封面尺寸：

| | 宽度 | 相对显示区（180px 格子） |
|---|---|---|
| 现有封面（中位） | **800 px** | 4.4 倍 |
| 建议缩放 | **480 px** | **2.7 倍**（1200px 窗口）/ 1.5 倍（1920px 窗口） |
| 实际显示 | 180 px | 1 倍 |

**结论**：

1. **480px 缩略图相对显示区仍是 1.5–2.7 倍，绰绰有余**（2 倍是 HiDPI 屏的经验值）。800→480 在 180px 的格子里看不出差别。
2. **现在才是浪费**：拿 800px 的图去填 180px 的格子，每次渲染浏览器都要做一次降采样；而且 800×538 解码后位图 **1.7 MB/张**常驻内存。全库 432 张若同时解码 = **724 MB**。
3. 缩放用 Electron 内置的 `nativeImage`（`createFromPath().resize().toJPEG(82)`），**零新依赖**，不引入 sharp 那种原生模块。
4. 尺寸做成常量，你觉得不够清晰随时调大——**这是可逆的**。

### 顾虑 4：换硬盘识别 → **用 `dev` 卷序列号（问题 4）**

启动时枚举盘符读 `dev`，建 `序列号 → 盘符` 映射，自动重映射缓存路径。**存量缓存直接受益**，不需要重扫。手动「盘符变更」按钮保留作兜底。

## 七、磁盘身份与按盘聚合（对应你的点 1）

### 结论：**能做到，而且盘符可以彻底不要**

判据已经验证过（第一节）：`fs.Stats.dev` 在 Windows 上就是**卷序列号**，与盘符无关。所以：

- **同一块盘换盘符 → 序列号不变 → 自动识别，不需要提醒**（这正是你说的"根本就不需要盘符"）

### 数据模型：存"盘内相对路径"，盘符从数据里消失

```
记录 = {
  dev:     "FE91E472",              // 硬盘身份
  relPath: "新建文件夹/示例演员M",   // ← 盘内相对路径，不含盘符

}
```

打开目录时现算：`path.join(resolveDrive(drives, dev).root, relPath)`

| 收益 | 说明 |
|---|---|
| **换盘符 = 零数据改写** | 不用改 107 条记录、不用搬任何数据。对比现在：`JSON.parse(JSON.stringify())` 深拷贝含 base64 的整条记录，改一次盘符要搬 103 MB |
| **多盘同时插入天然支持** | 每条记录只认自己的 `dev`，互不干扰 |
| **拔盘后** | `resolveDrive()` 返回 `undefined` → 界面上标成"离线盘"，点它提示插盘 |
| **"先选对应的盘"** | 按 `dev` 分组就是你要的界面结构 |

1. **在"减少移动硬盘读写"这个硬指标上，只有 E 和现状并列最优**（首次生成后零盘访问），而 A 是反向的——它让每次冷启动都要去移动硬盘读 20 KB × N 张。**这一条我上一轮漏算了，直接说 A 更好是错的。**
2. **它保留了你原本的形态**——缩略图就是存在 DB 里的，只是把存的**内容**从"原图"换成"缩略图"。改动面最小。
3. DB 103 MB → 约 12 MB，启动从 361 ms / 314 MB 堆 → 约 45 ms / 数十 MB
4. payload 674 KB → 约 10 KB，图片走独立端点由浏览器原生并发 + 懒加载
5. 位图内存 -2.8 倍（800px → 480px，这是渲染卡顿的真实来源）
6. 隐私上更好：封面**不留**在移动硬盘上（A 会把封面写到移动硬盘）
7. **零新增文件、零新增目录、零新增抽象**——最符合奥卡姆

```
缩略图 480px JPEG（nativeImage，内存里生成）
        ↓ base64
   存进 nedb（约 12 MB，启动时整个进内存）
        ↓
/openFolder 只返回元数据 + thumbKey（约 10 KB）
        ↓
<img src="http://127.0.0.1:3060/thumb?k=<记录id>&i=<序号>">
```

**代价（如实说）**：换电脑 / 重装系统后，缩略图要重新生成一遍（要重读原图）。A 能省这一步，但要拿"每次冷启动读移动硬盘"来换。我认为不值得。

## 九、读写规范评估（对应你的点 3）

先立判据。对硬盘来说，"伤不伤"实际是四件事：

| 维度 | 说明 |
|---|---|
| **字节量** | 读/写了多少。SSD 的寿命直接按写入字节算 |
| **随机 or 顺序** | HDD 一次随机 seek ≈ 5–15 ms；顺序读同量数据 ≈ 0.1 ms。**差两个数量级** |
| **次数（系统调用）** | 每次 `open`/`stat` 都有固定开销；**注定失败的调用同样要付** |
| **重写** | 同一文件反复全量重写，是 SSD 的主要杀手 |

对照你的实现：

| # | 写法 | 问题 | 类别 | 严重度 |
|---|---|---|---|---|
| 1 | `getBase64` 读**完整原图**只为得到封面 | 读 176 KB 只为了最终显示在 180 px 的格子里。而且**缓存里存的也是原图的 base64**，不是缩略图 | 字节量 | **高** |
| 2 | 缩略图**非原子写**（ffmpeg 直接写目标文件） | 抽帧中途崩溃 / 取消 → 半写的文件永久留在盘上，而 `hasFile` 判定它有效 → **封面永远坏，且永远不会重新生成** | 正确性 | **高**（隐蔽） |
| 3 | 每个子目录**无条件 open `avatar.jpg`** | `readdir` 早就把文件名列表拿到了，却还要 open 一个多半不存在的文件。大目录 = N 次注定失败的 syscall + N 条错误日志 | 次数 | 中 |
| 4 | `hasFile` 用 `existsSync` **逐文件查**缩略图 | N 次目录查找。一次 `readdir` 建个 Set 就够 | 次数 | 中 |
| 5 | `readFolder` 串行 `for + await` | N 个文件 = N 次串行 IO，总延迟 = Σ 单次延迟，而不是接近并发上限 | 次数 | 中 |
| 6 | F5 强制 `noCache` → 整个目录原图**全部重读** | 重读整目录 | 字节量 | 中 |
| 7 | ffmpeg 抽帧**无并发限制** | 一次浏览几十个视频 → HDD 疯狂 seek | 随机 | 中 |
| 8 | 视频封面抽的是**原始分辨率帧**并输出 **PNG** | 实测 1280×720 PNG，base64 **1.1–1.2 MB/张**，是图片封面的 **7.4 倍**。实测只把扩展名换成 jpg 就小 3.1 倍（64.8 KB → 20.6 KB） | 字节量 | 中 |
| 9 | `file-docker` **单目录平铺** | 攒到上万文件后 `readdir` 和查找都会变慢 | 次数 | 低（未来） |
| 10 | `FileFinderDockerManager.detect()` 同步探测盘符，且在**模块顶层** | 实测 26 个盘符只要 2 ms，**不是启动慢的原因**；但 `statSync` 遇到**已断开的网络映射盘**可能阻塞数秒 | 阻塞 | 低（有风险） |
| 11 | DB 放 `~/.file-finder/`（C 盘） | ✅ **这条是对的**：所有写操作都在系统盘，移动硬盘纯读 | — | 好设计 |

### 总体评价

## 十、端到端验证结果（91 项全绿）与收尾

上一轮所有结论都是**读代码推出来的**。这一轮把它跑成了可复现的实测。

### 10.1 怎么跑起来的（以及为什么必须这样跑）

要在终端里把整条管线（HTTP → 盘识别 → 扫目录 → 生成缩略图 → 写 nedb → 下发）跑透，得解决两件事：

| 障碍 | 现象 | 处理 |
|---|---|---|
| 沙箱里没有可用 GPU/显示 | 纯 Electron 脚本 5 秒自行退出（exit 3），日志 `GPU process exited unexpectedly: exit_code=-2147483645`，`app.ready` 永不触发、Node timer 不被 pump。`--disable-gpu` 能救回生命周期，但一碰 `nativeImage` 又卡 | 把 `electron` 换成可控替身（`_electron_stub.cjs`），纯 Node 跑服务端管线。**这是环境限制，与服务端逻辑无关** |
| 只有一块物理硬盘 | 没法真的插拔两块盘 | 在 `require` 服务端**之前**截住 `fs/promises.stat`，把"盘根"（`D:/`）的 `dev` 换成可控值 → 同一块盘上模拟出任意多个"盘身份" |

第二件是本轮最有价值的手法：**用户最关心的那条需求（A 盘 H: 拔出、B 盘插进同一个 H:，双方不冲突）因此可以被真正验证，而不是靠推演。**

### 10.2 换盘符实验：先复现 BUG，再证明修复

用旧代码（修复未生效时）跑，得到的正是**用户担心的那个数据冲突**：

```
FAKE=A  → 首次 openFolder: AAAA-...  size=1234      ✅ A 的缓存单独建
FAKE=B  → 首次 openFolder: BBBB-...  size=4321      ✅ B 没吃到 A 的缓存
FAKE=A  → 再 openFolder:  BBBB-...  size=4321      ❌ 拿到的还是 B 的数据
```

根因：`findDriveByLetter()` 直接信了内存里那份盘列表。盘符是会被复用的，缓存里的 `"D → 旧序列号"` 一旦过期，服务端就会**用旧的序列号去查缓存**，于是插上 B 却看到 A 的封面清单。

修复（`electron/utils/driveIdentity.ts`）：解析盘符时用**一次 `stat`** 复核这个盘符现在到底是谁，主人换了就让整表作废重扫。修完同一组实验：

```
FAKE=A  → AAAA-...  size=2234
FAKE=B  → BBBB-...  size=5321   （B 自己的内容）
FAKE=A  → AAAA-...  size=2234   （A 的缓存原封不动，key 与原值一致）
数据文件里该盘内路径：2 条并列记录，serial 分别 AAAA1111 / BBBB2222，
每条记录里的封面 key 都指向自己那块盘的图，无互相串。
```

**注意这组实验里刻意不调用 `/getDisks`** —— 内存里那份盘列表始终是上一轮的映射。服务端必须自己发现"盘符换主人了"，才算过关。

### 10.3 旧库回收：可行，且比预期干净

真实旧库（103 MB / 107 条旧格式记录）在隔离目录里跑一次启动流程：

| 指标 | 结果 |
|---|---|
| 回收后体积 | **72 B** |
| 耗时 | 7.5 s（读 103 MB + 备份写 103 MB + 压缩重写） |
| 自动备份 | ✅ `searchCache-YYYYMMDD.db` |
| 遗留旧记录 | 0 条 |

一点必须记下来的**nedb 内部行为**，不然后面会误判成脏数据：

- 数据文件里除了记录本身，还有两种**元数据行**，它们不是记录：
  - `{"$$indexCreated":{"fieldName":"serial",...}}` —— `ensureIndex` 写进去的索引声明。压缩后剩下的那个 72 字节文件，装的就是这一行 + 换行。
  - `{"$$deleted":true,"_id":"..."}` —— `remove` 往文件尾部追加的删除标记。
- 这两行合起来解释了"append-only 为什么只涨不缩"：**删一条不是抹掉，而是再追加一行**；`compact()` 才是真正重写。所以覆盖写同一个目录必须走 `removeCache → insertCache`，并且要有压缩兜底。

### 10.8 用真实缓存库核对：我上轮说错了一条
