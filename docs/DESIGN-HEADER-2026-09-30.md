## 0. 结论摘要（一句话）

**做「调整」，不做「重构」。** 病灶是一个**结构问题**——头部高度是用户数据的函数。它可以用**两个容器 + 一个纯函数 + 一处折叠规则**在结构层解决；重构（例如换成资源管理器式可编辑地址栏）只会引入新风险，不带来新收益。

| 决策 | 我的定夺 | 一句话理由 |
|---|---|---|
| 调整 vs 重构 | **调整** | 病灶是"无界内容没有有界容器"，不是"组件选错了" |
| 根路径 chip | **保留，但显示有界化**（不是删、不是合并进面包屑） | 它是唯一根目录回显 + 唯一"清空根"控件（`×`），删不掉；合并进面包屑要重做 `×` 语义（奥卡姆） |
| 面包屑形态 | **单行 + 中间折叠 `…` + 单条省略** | 与 Explorer / Finder / GitHub / 主流设计系统一致 `[引用]` |
| 交互行为 | **一个都不改** | 点标签跳转 / 返回恢复滚动 / 进目录清空搜索词 / 快捷键 = §四神圣 |
| 读盘 | **零** | 纯渲染层改动，无新端点、无新请求、无扫盘 |

### 用户截图里已经发生的事

截图那一帧头部是**两行**：第 1 行只有根路径 chip（右侧 90% 空白），第 2 行才是「面包屑 + 工具条」。

- 这**正是 F2+F3 的必然结果**：`.toolbar` 先占满自己需要的宽度（缩不下去），剩下的宽度留给 `.hstack`；`.hstack` 装不下就**在内部换行**，于是它自己变成 2 行高，而 `.toolbar` 被 `align-self:flex-end` 钉在第 2 行 —— "看起来并在同一行"是**巧合，不是设计**。
- 按面板宽度反推（`.toolbar` 内容约 600px、截图约为 2× DPI `[推理]`），换行点出现在窗口约 **700–900 CSS px** 时。**未实测**具体断点。
- 另一个佐证：截图里**面包屑与工具条是紧挨的、中间没有任何空隙** ⇒ 那一帧的内容**刚好把宽度吃满**（`justify-content:space-between` 没有余量可分）`[推理]`。这也解释了为什么"第 1 行只剩根路径 chip、其余全空"——第 1 行是被挤出来的，不是设计出来的。
- ⚠️ 但**不要以为"窗口够宽就没事"**：只要三个无界量（根路径长度、单层名字长度、层级数）中任一个够大，就会翻行 —— 而这三个都是**用户数据**，天生无界。这就是本方案的靶子。

## 2. 第一性原理：这块区域到底在回答什么？

一行 UI 元素，本质在回答 4 个问题，**按使用频率排序**：

| 优先级 | 问题 | 回答者 | 频率 |
|---|---|---|---|
| 1 | **我在哪？怎么回去？** | 面包屑（+ 返回） | 每次下钻/返回都读 |
| 2 | **这里有多少东西？** | `n-badge` | 每次进目录扫一眼 |
| 3 | **我能做什么？** | 工具条 4 个按钮 | 中频 |
| 4 | **我的根设在哪？** | 根路径 chip | **设一次，之后几个月不动** |

**病灶（根因，一句话）**：

> **头部的高度是「用户数据」的函数。** 一个低频的、无界的字符串（根路径）和一个高频的、无界的序列（面包屑层级）被塞进同一个 `flex-wrap` 容器，共享同一份宽度预算 ⇒ 用户数据一变长，布局就变形。

**正确的第一性原理**：

> **容器的高度必须是常量；任何无界内容必须被关进「有界盒子」，并在盒子里规定溢出行为。**

这不是审美问题，是**约束问题**。它决定了修法：给现在的元素加一个 `max-width` 是**补丁**（下个月新增一个元素照样复活）；把"无界 → 有界"变成**容器层面的规则**才是**修复**。

## 3. 三个膨胀源（各有各的解）

| 源 | 方向 | 现状 | 本质 | 解 |
|---|---|---|---|---|
| A. `.hstack` 内部换行 | **垂直无界** | `flex-wrap: wrap` | 换行容器的高度由内容决定 | 容器 `nowrap` + 分区，且分区内**不靠换行**消化溢出 |
| B. 面包屑 tag 个数 = 层级数 | **水平线性无界** | 一层一个 tag，全平铺 | 深路径在水平轴上线性增长 | **按层数折叠**（保首尾，中间折 `…`），当前层永不折 |
| C. 单条路径/名字长度 | **水平无界** | 无 `max-width`、不省略 | 文本没被关进有界盒子 | `max-width` + `text-overflow: ellipsis` + 全名进 tooltip／`title` |

**A 是总闸**：只要 A 还在，B 和 C 修了也会在别的窗口宽度下复发。所以**顺序是 A → C → B**。

## 4. 产品经理视角

### 4.1 信息架构：把「设置回显」从「导航」里拆出去

现在的错误是**两类语义共享一行宽度**：

- 根路径 chip = **设置回显**（低频、长、可变）
- 面包屑 = **导航**（高频、必须有界）

PM 结论：头部划成 **2 个固定槽位**，各自有**固定的宽度策略**，互不挤占。

```
┌ header-bar : display:flex; flex-wrap:nowrap ─────────────────────────────────────┐
│ ┌─ 导航区  flex: 1 1 auto; min-width: 0 ─────────────┐ ┌─ 动作区  flex:0 0 auto ─┐ │
│ │ 📁F:…/videos │ home › … › 父 › 当前 │ [返回]        │ │ 补全 重读 补封面 🕶 35 🔍 ↻ │ │
│ └──── 唯一的弹性槽位：随窗口伸缩，内部自己解决溢出 ────┘ └─ 内容固定，永不伸缩换行 ─┘ │
└──────────────────────────────────────────────────────────────────────────────────┘
       ↑ 行数恒为 1        ↑ 行数恒为 1
```

**这一条就是"修复"而不是"补丁"的判据**：以后往这两个区里加任何东西，只要它遵守"分区 + 各自有界"，**头部不会变高**。而现在只要加一个元素就可能翻行。

### 4.2 动作区：一个"内容统计"住错了地方

`n-badge` 35 是**内容统计**（这一层有多少条目），却住在**动作区**、还夹在两个动作控件之间 ⇒ 被读成图标按钮的角标（`index.vue:55-56` 的注释自己也承认这个风险）。

- 资源管理器的做法：**不显示**；Finder 的做法：显示在**底部状态栏**。
- 本项目**已经有**一条网格下方的状态条（`.scan-bar`），语义位置现成。
- **建议（待裁决，我不擅自改）**：把「N 项」搬到网格下方状态条，与扫描进度共用一行（扫描时显示"已扫 n/待扫 m"，平时显示"共 N 项"）。收益：语义归位 + 动作区少一个元素；成本：状态条由"扫描时出现"变成"常驻"，网格矮约 28px。

### 4.3 明确**不改**的（保护既有认知）

| 不改 | 理由 |
|---|---|
| 四个动作按钮的文案 | `index.vue:76-77` 已明确记录「名字沿用用户已经在用的，改名有认知成本」；且"补全/重读"的语义区分已在上一轮用 tooltip + 分组解决 |
| 根路径 chip 的整体形态（选文件夹 → 显示路径 → `×` 清空） | 已声明特性（快捷键 `D`、唯一选根入口、唯一清根入口）；本轮只让它**显示有界**，不动结构 |
| `n-badge` 的存在 | 只是位置有争议（见 §4.2），不是"该不该有" |

## 5. UI/UX 视角

### 5.1 外部权威共识（`[引用]`）

搜了一圈主流设计系统与 UX 指南，**四家结论高度一致**，正好逐条对上我们的三个膨胀源：

| 共识 | 出处 | 对应本项目的哪一条 |
|---|---|---|
| **绝不让面包屑换行**，"truncate instead" | Cognite Aura 设计系统 · SSW Rules · TYPENORM | 解 A |
| 轨迹**超过 4–5 条**就把**中间**折成省略号 | SSW（"exceeds 4 items"）· Cognite（"first and last two shown, middle condensed"） | 解 B |
| **首段 + 末段永远可见；当前页永远可见** | Cognite：*"the active (current) page name should always be visible"* | 解 B 的硬约束 |
| 单条标签过长 → **截断 + tooltip 显全名**（约 80 字符上限） | Cognite · SSW · TYPENORM | 解 C |
| 当前项**不应是可点的**（"Don't make the current breadcrumb navigable"） | Cognite · 与 F8 的死交互对上了 | 附带修 F8 |
| **不要横向滚动面包屑**（用户发现不了滚动） | TYPENORM | 明确不做项 |

> `[引用]` 来源：`docs.cognite.com/aura-design-system/primitives/breadcrumbs`、`ssw.com.au/rules/effective-breadcrumbs`、`typenorm.com/articles/breadcrumb-navigation-patterns-best-practices`（后者转引 Nielsen Norman Group）。

### 5.2 落地设计

#### (1) 分区（解 A · P0）

- `.header-bar`：加 `flex-wrap: nowrap`（现在没写，靠子项自己表现），明确"头部永远一行"
- 新增「导航区」包裹层：`flex: 1 1 auto; min-width: 0; flex-wrap: nowrap; overflow: hidden`
- 动作区 `.toolbar`：`flex: 0 0 auto; flex-wrap: nowrap`（保持 nowrap，补上 `flex:0 0 auto` 让它**不参与压缩**）
- ⚠️ `min-width: 0` **是这整套的地基**：flex 子项默认 `min-width:auto`，不加它，容器再怎么设 `overflow` 都不会真的收窄。

> 注意：`FolderSelector` 的**组件根是 `<div>`**，它内部还有一个 `n-space`。分区时它应留在导航区**最左**，作为"导航的起点"。

#### (2) 单条有界（解 C · P0）

- 面包屑 tag：`max-width: 160px` + `overflow:hidden` + `text-overflow: ellipsis`（`nowrap` 已有，见 F5）+ `title`/`n-tooltip` 显全名
- 根路径 chip：**不要**用 CSS 反向截断（`direction: rtl` 那种）—— 它会把 `F:/` 里的 `/` 排到错位置。用**一个纯函数**把路径段收成有界字符串：

```
foldPath('F:/videos')                          → 'F:/videos'          （够短，不动）
foldPath('E:/sample/videos/示例演员E/示例作品标题') → 'E: …/示例演员E/示例作品标题'
```

  规则：`盘符` + 末 `n` 段（`n=2`），中间折成 `…`。**零 DOM 测量、零 resize 监听、可单独验**，和项目既有的 `levelName()` 是同一个套路。完整路径进 `title` + `n-tooltip`。
- 好处：它同时也是 `…` 折叠规则的**同一个函数的两种用法** —— 一处实现，两处受益，以后新增"显示路径"的地方直接复用。

#### (3) 按层数折叠（解 B · P1）

- 层数 ≤ **4** ⇒ 全显
- 层数 > 4 ⇒ **首 1 段 + `…` + 末 2 段**（＝**父 + 当前**）⇒ 显示**最多 4 段**，当前层永远在末段、**永远可见**
- ⚠️ **阈值已于 2026-09-30 晚更新**：原定"≤4 层全显"是按**相对用户选的根**的浅链估的；而面包屑的定义后来改成了**绝对路径链**（`E: › 祖 › 父 › 当前`，天然更深）⇒ **以 `docs/DESIGN-NAV-2026-09-30.md` §5.2 的表为准**。阈值是可调常量，真机目视定。
- `…` 用 `n-popover` 触发，列出被折叠的层级，**每层可点跳转** ⇒ **折叠只牺牲"常显"，不牺牲任何能力**（这是 §四「面包屑跳转」神圣的兑现方式）
- **纯声明式、不测量**：按**层数**折叠，不按像素折叠 ⇒ 无 DOM 测量、无 resize 监听、无抖动。后期若想更精细再考虑测量，但本轮不做。

#### (4) 附带修两处可读性缺陷（P1，低成本）

| 项 | 现状 | 改法 | 成本 |
|---|---|---|---|
| **当前层是死交互**（F8） | 所有 tag 都 `cursor:pointer`，但当前层点了没反应 | 当前层：`cursor: default` + 无 hover 态 + 视觉区分（`n-tag :type`）；也正对上"当前项不应可点"的共识 | 一个条件绑定 |
| **层级之间没有分隔符**（F7） | tag 之间只有 12px 空隙，层次靠"排在一起"暗示 | 用 **CSS `::before`** 加 `›`（**不加 DOM 子元素** —— 这一组的子元素个数是敏感量，见铁律 4） | 一条 CSS |
| loading 时 **N 个转圈**（F7） | `n-spin` 在每个 tag 里 | 只在**当前层**那个 tag 上转 | 一个条件绑定 |

> 分隔符用 `::before` 而不是插一个 `<span>`：`.hstack` 的子元素个数在本项目是**被记录过的敏感量**（`n-space` 重复 key 事故的同族）。CSS 零 DOM 成本，是这里的正解。

## 6. 成本阶梯（用户要求：先给阶梯，别替他选最完整那版）

| 档 | 做什么 | 拿到什么 | 拿不到什么 | 规模 |
|---|---|---|---|---|
| **① 一行版** | 导航区 `nowrap` + `min-width:0` + `overflow:hidden` | **头部恒 1 行**（不再把网格挤下去） | 溢出时**从右往左裁** ⇒ **当前层（最重要那个）可能被裁掉** | ~4 行 CSS |
| **② 标准版（推荐）** | ① + 单条 `max-width`+ellipsis+tooltip + `foldPath()` 纯函数 | ① + **每条都看得见轮廓**，全名可 hover | 层级 >4 时仍然会挤满/被裁 | ① + 1 个纯函数 + 3 条 CSS |
| **③ 完整版** | ② + 按层数折叠 + `…` 可点开 + 当前层不可点 + 分隔符 + 单个转圈 | ② + **当前层永远可见**、层次一眼可读、死交互修掉、`…` 保留全部跳转能力 | — | ③ ≈ ② + 1 个 computed + 1 个 `n-popover` + 3 处条件绑定 |

**我选 ③（完整版）。** 理由：

1. **②不能保证"当前层可见"**，而当前层是"我在哪"的唯一答案 —— 把最重要的信息裁掉，等于修了个更糟的 bug。这不是加功能，是**②的必要补全**。
2. ③ 增出来的量**只有 1 个 computed + 1 个 popover + 3 处条件绑定**，没有新机制、没有新组件类型、没有新请求。
3. ①②③ 是同一个结构的三段，**不是三条路** —— 先落 ①，②③接着做，每段都能独立验收、独立回退。

## 13. 回溯三家官方规范（Google / Microsoft / Apple）

> 上一轮只引了 Cognite / SSW / TYPENORM（二手转引）。这一轮直接查了三家**官方**规范。
> 结果：**两家官方规范逐条命中了本方案的核心规则**，第三家给出了另一条完全不同的路线。

### 13.1 官方原文（`[引用]`，可点回原文核）

**Apple · HIG「Path controls」**（developer.apple.com/design/human-interface-guidelines/path-controls）

> · Standard 形态：一个线性列表，"**If the list is too long to fit within the control, it hides names between the first and last items.**"
> · Pop up 形态：只显示当前项的图标+名字，"**people can click the item to open a menu containing the root disk, parent folders, and selected item**"。
> · **"Use a path control in the window body, not the window frame. Path controls aren't intended for use in toolbars or status bars."**
> · "Note that the path control in the Finder appears at the bottom of the window body, not in the status bar."

⇒ 三条全是硬信息：**① 太长就"隐藏首尾之间的名字"（＝我们的折叠规则，Apple 的官方写法）② 折叠后可点开一个"祖先层级"菜单（＝我们的 `…` popover）③ 路径控件不属于工具栏**。

**Microsoft · Fluent 2 Web / Breadcrumb**（learn.microsoft.com 与 Fluent 2 Web 指南）

> · "**Don't wrap breadcrumbs to multiple lines**"
> · "**It's safe to keep breadcrumbs between 30% to 50% of the overall surface width.**"
> · 超宽时"collapse the breadcrumbs and use ellipses…**The first and last item (i.e current page) are shown by default.** Users can expand the breadcrumb by selecting the ellipsis button."
> · "An interactive breadcrumb item label **truncates when the name is longer than 30 characters**…Add a **tooltip** to display the full breadcrumb item name."
> · "**Keep the current page item as text only**"

**Microsoft · Windows 11 文件资源管理器**（行为事实）

> · 地址栏是**双模式**：默认是面包屑；点地址栏空白处或按 **Ctrl+L / Alt+D** ⇒ 变成可编辑路径（可粘贴 UNC、环境变量、甚至 URL）。
> · 悬停某个面包屑段会下拉出**同级/子级目录树**（横向跳转）。
> · 命令栏（动作）是**独立的一行**，与地址栏分离。

**Google · Material 3**（m3.material.io 组件清单）

> · M3 组件库**没有 breadcrumb 这一项** `[引用，基于官方组件清单]`；层级导航交给 **Navigation Drawer / Navigation Rail**（侧边栏树）。M3 Expressive 的 Toolbar 定位是"display frequently used actions"（只放动作）。

### 13.2 三家对照

| 维度 | Microsoft | Apple | Google |
|---|---|---|---|
| 头部（工具栏）放什么 | 命令栏：只放动作 | 工具栏：前进/后退 + 标题 + 视图 + 动作 + 搜索 | Top app bar + Toolbar：动作 |
| **层级导航靠什么** | **导航窗格（树）** + 地址栏面包屑 | **侧边栏（树）** + 可选路径栏 | **Navigation Drawer / Rail（树）** |
| **路径住在哪** | 头部地址栏（占满整行，与命令栏**分层**） | **窗口 body 底部**，规范明文"不属于工具栏" | 顶栏（Drive），**无 breadcrumb 组件** |
| 长路径怎么办 | 折叠成省略号，首尾保留 | **隐藏首尾之间的名字**，或收成 Pop-up | — |
| 当前项 | 保持为文本（不可点） | — | — |
| 单条过长 | >30 字符截断 + tooltip 显全名 | — | — |

### 13.3 三条共同结论

1. **「路径」和「动作」从来不在同一个不可换行的行里。** 三家都分层：MS 用两行（地址栏 / 命令栏）、Apple 把路径**移出头部**、Google 干脆不给顶栏派这活。我们的病灶（F2/F3）**恰好是这条共识的反面** —— 所以修法不是"把路径做小"，是**给它自己的层**。
2. **长路径的标准手法 = 保首尾 + 折中间**。Apple 与 Microsoft **两家独立收敛到同一条规则**（一个叫"hides names between the first and last items"，一个叫"first and last shown by default"）。⇒ 本方案 §5.2(3) 不是我发明的，是两家的默认行为。
3. **层级导航的主流答案是「树」，面包屑只是树的降级形态。** 三家都有侧边栏树（导航窗格 / 侧边栏 / Drawer），而面包屑只在"没有侧边栏位置"时才用。

### 13.4 为什么**不能照抄**（否则就是抄规范而不是用规范）

| 规范 | 直接照抄会怎样 | 正确做法 |
|---|---|---|
| Fluent：「单条 >**30 字符**截断」 | 中文 1 字 ≈ 拉丁 2 字宽 ⇒ **30 个中文字 ≈ 360px**，比现在的 tag 还宽，等于没截断 | 用**像素** `max-width`（跨语言稳定），把 Fluent 的 30 字符当"量级参考"而不是规则；初值 160px，真机目视调 |
| Explorer：可编辑地址栏 + Ctrl+L | 我们的头部一行要装面包屑 + 7 个动作控件，**没有整行空间** | 它的前提是"地址栏独占一行"。⇒ 想抄它得先做路线 B（见 §14） |
| Apple：路径控件放窗口底部 | 我们底部已有 `.scan-bar`（扫描进度），再叠一条会挤 | Apple 的前提是窗口**又高又宽**。我们要先算清楚底部还剩多少空间，才谈要不要 —— 见路线 B 的成本 |
| Google：用侧边栏树 | 要新造一整块导航面板 | 我们的**核心收益已被「缓存记录」面板覆盖**（见 §14 路线 C 的否决） |

## 14. 三条路线：A 调整 / B 路径下沉 / C 左侧树

> 注意区分：**§6 的 ①②③ 是「路线 A 内部」的成本阶梯**；这里 A/B/C 是**信息架构层面**的路线，不同维度。

### 路线 A · 调整（＝本方案 §5，头部内分区 + 有界化）—— **做**

| 项 | 内容 |
|---|---|
| 做法 | 头部内分「导航区 / 动作区」；路径与层级都关进有界盒子；层级折叠 |
| 成本 | 渲染层 3 个文件；无新端点、无读盘、主进程不动 |
| 收益 | 头部行数恒定；**且这条规则现在有两家官方规范的默认行为背书** |
| 风险 | 层级折叠是对"面包屑全平铺"的形态改动 ⇒ 需你点头 |
| 定夺 | **做**（也就是我上一轮的推荐，规格不变，只是证据等级从"三家二手指南"升级成"两家官方规范"） |

### 路线 B · 路径下沉到窗口底部独立一条（Apple 模型）—— **不做（2026-09-30 晚降级）**

> ⚠️ **降级理由**：用户随后明确「**不允许手动输入编辑路径**」。B 的两大收益之一是"路径拿到独占整行后**解锁** Explorer 式可编辑路径 + `Ctrl+L` 键盘直达" —— **这个收益被禁令直接归零**；而它的另一收益（头部与长路径解耦）**已被路线 A 的"分区 + 折叠"覆盖**。⇒ B 只剩下"把路径搬个位置"的搬迁成本，**不做**。下面的成本/收益表保留作历史记录。

| 项 | 内容 |
|---|---|
| 做法 | 头部只留「返回 + 当前文件夹名 + 7 个动作 + 搜索」；**完整可点路径栏移到网格下方**，与 `.scan-bar` 共用区域（或各自一条）。当前文件夹名 = Apple 那种"只显示选中项"的 Pop up 形态，点开列出祖先 |
| 成本 | 中：新增/改造一条底部区域（要处理与 `.scan-bar`、`.empty-tip` 的关系）+ 移动面包屑 + 保住"点标签跳转/返回恢复滚动" |
| 收益 | **头部与长路径彻底解耦**；且因为路径拿到了**独占一整行**，才**解锁** Explorer 式的「可编辑路径 + 键盘直达」 |
| 风险 | 把"我在哪"从**视线上方**挪到**下方**，与既有肌肉记忆冲突；底部已有 `.scan-bar`，空间要算 |
| 定夺 | **备选，先不做。** 触发条件：如果你觉得"路径本来就不该占头部"，那就做 B，A 变成 B 的前置步骤 |

### 路线 C · 左侧目录树（三家共同答案）—— **否**

| 项 | 内容 |
|---|---|
| 做法 | 导航交给一棵可折叠的树；头部只留动作与搜索；面包屑退化成"当前文件夹名" |
| 成本 | **高**：新面板 + 展开态持久化 + 宽度拖拽 + 与 `openStack` / 缓存面板的关系 + 暗色主题下多一块表面 |
| 收益 | 从**根上**消除"路径字符串"这个问题（不再需要展示长路径）+ 补上"横向跨层级跳转" |
| **否决理由** | **它的核心收益已经被「缓存记录」面板覆盖了。** 那一块面板就是**目录黄页**：213 个目录、可搜索、可点开、**纯内存零读盘**、并且**已经在线上**。树能给的"跳到任意层级"，它已经给了 ⇒ **边际收益小、成本最大**（奥卡姆）。而且你已明确「走功能完善路线、看板类大件暂缓」 |
| 定夺 | **否。** 如果哪天你觉得"缓存面板太绕、想要常驻可见的树"，再说 —— 那时它是**从缓存面板演化**出来的，不是从零造 |

> 一条复用建议（零成本）：Explorer 的 `Ctrl+Shift+E`（在树里展开到当前文件夹）在我们的对应物就是**「缓存记录」面板里高亮/定位当前目录**。这比造一棵树便宜得多。

### 三条路线的关系

```
路线 C（左侧树）        ✗ 否  ← 收益已被「缓存记录」面板覆盖
      ↑ 若真要做，从缓存面板演化
路线 B（路径下沉）      △ 备选 ← 解锁 Explorer 式「可编辑路径 + 键盘直达」
      ↑ 依赖
路线 A（头部内调整）    ✓ 做   ← 本轮方案；A 是 B 的前置步骤，不是竞争关系
```

## 15. 路线 A 因官方规范而**微调**的两处

1. **导航区加 `max-width: 50%`**（依据：Fluent 2「breadcrumbs 占整体宽度 30–50% 是安全的」）
   - 现在方案里导航区是 `flex: 1 1 auto` ⇒ 窗口很宽时会**无限扩张**，把动作区挤到 50% 以下（虽然永远不会换行，但动作区会被压）。
   - 加 `max-width: 50%` 之后：**动作区永远拿到 ≥50%**，且超出 50% 的部分交给折叠规则去消化 —— 与 §5.2(3) 天然衔接。
   - `[推理]` 50% 是直接采用 Fluent 的上限；我们动作区内容（约 600px）在 1200px 窗口下刚好过半 ⇒ 这个值对我们也是合适的。真机可调。
2. **单条截断用像素，不用 Fluent 的 30 字符**（理由见 §13.4 表）
   - `max-width: 160px` 作为初值 + `title` / `n-tooltip` 显全名（Fluent 明文要求 tooltip）。

已被官方规范**背书、无需再论证**的三条（原 §5.2 的结论，规格不变）：

| 本方案的做法 | 背书 |
|---|---|
| 面包屑绝不换行 | Fluent 2 明文；Apple 用"隐藏名字"达成同一效果 |
| 太长 → 保首尾、折中间 | **Apple HIG 原文** + **Fluent 2 默认行为**（两家独立一致） |
| 折起来的 `…` 可点开列出祖先 | **Apple 的 Pop up path control** 原文 + Fluent 的 ellipsis expand |
| 当前层作为纯文本（不可点） | Fluent 2 明文"Keep the current page item as text only" |
| 截断 + tooltip 显全名 | Fluent 2 明文 |

### 18.4 逐项判断

**① 「请选择文件夹(D)」缩短 —— 省不到你要的地方（这一条要纠正）**
那个按钮的渲染条件是 `v-if="!modelValue"`，**只在"还没选根"时出现**。
而那种状态下 `history` 是空的 ⇒ **根本没有面包屑** ⇒ 不存在"左边不够"。
所以缩短它（`请选择文件夹(D)` → `选择文件夹(D)`，约 12px）**是好事，但不是解法** —— 它不在关键路径上。

**② 三个不常用动作 = 242px，确实是元凶（你的判断成立）**
它们是常驻文字按钮里最宽的三个，占工具条 40%。

**③ 但"缩短"会丢掉一层语义（必须说清）**
「这一片」表达的是**递归整片**；与「刷新＝只重读当前层」区分开的正是它。
去掉之后 `补全`/`重读` 与「刷新」的差别更难看出来 ⇒ 上一轮 UIUX 方案专门解决的
"用户要问这两个按钮有什么区别"，会退回去一部分。
**折中**：`补全整片` / `重读整片`（4 字，各 76px）⇒ 只省 28px，但保住范围语义。
⇒ **这是取舍，不是纯优化。**

**④ 「更多」下拉收益最大，但撞到已声明的特性**
`index.vue` 里明确写着「两个入口仍然**平铺**，不拿下拉藏（这条特性没动）」。
而当年被否决的那个下拉，问题是"**不悬停就不知道它存在**"—— 那是**可发现性**，不只是"形式"。
一个常驻可见的「更多」按钮比悬停好，但入口仍要在下拉里找 ⇒ **它仍然损失可发现性**。
⇒ 按铁律 1，**这条要你点头才动**。

**⑤ 角标 35 挪走 = 纯收益（38px）**
它是**内容统计**（当前目录条目数），却住在**动作区**、夹在图标按钮与搜索框之间
（代码注释自己承认"像它的角标"）。挪到网格下方状态条：语义归位 + 省 38px + 不动任何动作。

### 18.7 落地实测（2026-10-01 已实现，真 Chromium + 真 scoped CSS）
