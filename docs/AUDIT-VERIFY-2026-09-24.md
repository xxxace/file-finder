## 三、被推翻的（教训比结论值钱）

### ① A2「缓存库 64% 是永久垃圾」—— 撤销，核心结论是错的

`nedb` 的 `loadDatabase()` **第 3 步就是压缩**。`node_modules/nedb/lib/persistence.js:250-262`：

```
 * Load the database
 * 1) Create all indexes
 * 2) Insert all data
 * 3) Compact the database
 * ...
 * Also, all data is persisted right away, which has the effect of compacting the database file
```

`:299` 就是 `self.db.persistence.persistCachedDatabase(cb)` —— 它只把活跃文档重写成整份文件。

**我自己复核过**（复制库副本跑，未动原库）：

```
load 前: 4261641 bytes / 18 行 / 其中墓碑 3 条
load 后: 2887915 bytes / 12 行 / 其中墓碑 0 条
文件缩小: 32.23%
```

所以「被删记录的字节**永远**留在文件里」是**错的** —— 每次启动都会整库重写、回收一遍。
「64.1%」也是会漂移的瞬时快照（实测当前 32.23%），不是固定属性。

`nedb.ts` 里那个自定义 `compact()` 是死代码这一点**仍然成立**，但它**不产生**我声称的后果。

> **教训**：我用「读了项目自己的 `nedb.ts`」替代了「读第三方库的真实行为」。
> 那个死掉的 `compact()` 是吸引我注意力的东西，真正干活的是**依赖内部**的 `loadDatabase`。
> 以后遇到"这条结论依赖谁的行为"，必须去读那一层（或实测），不能读包装它的那层。

### ② A3「抽帧慢 3 倍」—— 撤销

实测（同盘真实文件、**轮换顺序**消除冷缓存偏置）：

| 文件 | 现行方式 | 对照方案 | 比值 |
|---|---|---|---|
| TST-332.mp4 | 284 / 308 / 305 / 310 ms | 301 / 304 / 304 / 299 ms | **1.01x** |
| TST-155.mp4 (10GB) | 460 | 439 | 1.05x |
| TST-159.avi | 393 | 404 | 0.97x |
| TST-369.wmv | 216 | 244 | 0.89x |

**没有一条接近 3 倍。** 更关键：`fluent-ffmpeg` **本来就用 input seek**
（`node_modules/fluent-ffmpeg/lib/recipes.js:388` `self.seekInput(first)`，实测抓到的命令行 `-ss` 在 `-i` **之前**）。

也就是说，"提议方案的优势"里有一项（input seek）**现行实现早就有了** —— 我的对照组设计本身有偏。

> **教训**：**对照组里不能混入"被测对象已经具备的东西"**，否则差异全是我自己造出来的。
> 逐项核对差异来源，别把共有项算成优势。

### ③ C1「`/raw` 可读任意文件」—— 撤销（重开了一个已被裁决的决定）

### ④ B5「正则混进竖线」—— 撤销（零可观察影响）

语法事实成立：`/^[a-z|A-Z]/.test('|')` → `true`，`/^[a-zA-Z]/.test('|')` → `false`。

**但 `|` 是 Windows 文件名的保留字符**（`< > : " / \ | ? *`）。而 `filterByName` 的被测对象是
`item.name`（磁盘文件名）和搜索词：`item.name` **永不含 `|`** → 两种正则对它**逐字等价**；
最终的命中判据是 `name.indexOf(value)`，要求名字里出现 `|`，在本应用里不可能。

实测 12 个搜索词 × 8 个文件名，**产生差异的数量 = 0**。

> **教训**：**只观察代码的形状、不观察它能否产生可观察差异** —— 影子判据最典型的形态。

## 五、子代理新发现的（我的初审报告完全没提到）

1. **`Origin: null` 在白名单里**（`index.ts:704`）—— `file://` / `data:` / sandbox iframe 的 Origin 都是 `null`，
   服务端会回 `Access-Control-Allow-Origin: null`，而浏览器**承认这个匹配** → 这类页面**能真正读走**任意目录树。
   ⚠️ **这比 C2 严重**：C2 那条（`evil.com`）读不到字节，这条能。
2. **完全不校验 `Host` 头**（全仓库只有 `index.ts:701` 用到 `req.headers`，且是 `origin`）
   → DNS rebinding 的前提成立；只绑 `127.0.0.1` **不阻断** rebinding。
3. **`/getFileTree` 零校验且递归整盘**（`index.ts:419-423` → `collectCodeList`）——
   任意网页放一个 `<img src="http://127.0.0.1:3060/getFileTree?path=C:/">`（简单请求、无预检）
   就能让主进程**递归 stat 整块 C 盘**。**可被任意网页触发的 DoS / 磁盘抖动**，比"读一个文件"严重得多。
4. **`openFolderController` 无 `try/catch`，`event.emit` 也无兜底**（`index.ts:729`）
   → 服务端异步 handler 抛错时**响应永不返回**，客户端 `fetch` 挂起、`loading` 永真。
5. **`readFolder` 的逐项 `try/catch` 救不了一个永不 settle 的 `await`** —— catch 只捕获"抛错"和
   "已 reject 的 promise"，一条永不 resolve 的 `await` 会永远停在那一行。这是 A1 的机制补充。
6. **抽帧的 `settled` 守卫是必需的**：`kill()` 之后 fluent-ffmpeg 会补发一个 `'error'`，不挡住就会重复 resolve。

### ① C3 缩略图占内存 → **决定：不动**（实测数字推翻了"该修"的直觉）

**实测（不是估算）** —— 直接解析真实 `searchCache.db`：

| 指标 | 实测值 |
|---|---|
| 缓存条目总数 | **197** |
| 带缩略图的字段数 | **160** |
| 单张 base64 平均长度 | **45,386 字符**（最长 87,811） |
| 全部缩略图 base64 合计 | **6.93 MB** |
| DB 文件大小 | 6.96 MB |

**所以真实量级是 ~7 MB，不是我原先估的"5 MB/100 张"那种口径 —— 但要紧的是它怎么涨**：
每刷一个新 key 就多一份，而**整库全刷一遍 ≈ 7 MB**（单个常用目录约 1.8 MB）。
重启应用即归零（Map 在主进程内存里，不落盘）。

**为什么仍决定不动**：三条修法**没有一条是纯收益**，而且唯一"结构上正确"的那条
（稳定 key）要动的面比收益大：

| 方案 | 能解决什么 | 真代价 |
|---|---|---|
| ① key 改成稳定身份（路径+mtime+size 派生） | Map 不再涨（同键覆盖） | 要动 **3 个调用点**；`makeDirCover` 得先 stat（或改用无 mtime 的 key）；**改的是浏览器缓存语义**（同名换图后 `/thumb` URL 不变 → 界面不刷新） |
| ② 换成 LRU 上限 | 涨到上限就停 | `<n-image :lazy>` 还没取过图的格子**滚动到时变白图**（我原报告说"淘汰是安全的"**是错的**） |
| ③ 不存内存、按 key 回查 nedb | 泄漏从结构上消失 | 要给**嵌在数组里**的 key 建索引 → nedb 从"一目录一文档"变成"一缩略图一文档"，**写盘次数显著上升**，还和"少碰移动硬盘/少写盘"的项目目标相冲 |

**触发条件（写下来，将来不用重新论证）**：单次会话缩略图累计 > 200 MB
（约等于整库全刷 30 次）时再回来动它。现在离得很远。

**顺手做了的**：把 `thumbStore.ts` 顶部那句**错注释**改掉了 —— 原文写「内存开销为零：Map 里存的是引用不是副本」。
"引用不是副本"对，但结论错：**正因为它强引用住了，那个字符串才不能被回收**。
另外把估算口径也修正为实测：V8 对纯 ASCII 串用**单字节**表示，所以不是 ×2 的 13.85 MB，而是 ~6.93 MB。

## 七、本报告完全没提到的一条真实故障（2026-09-24 傍晚）

**现象**：`D:/sample/videos/TST-PPV-1000001` 在网格里是一张**空白卡片**。

**根因（实测到文件头，不是推理）**：
`TST-PPV-1000001.jpg` 的头 12 字节是 `52 49 46 46 ... 57 45 42 50` = `RIFF....WEBP` ——
**一个改了 `.jpg` 后缀的 WebP**。Electron 的 `nativeImage` 只认 PNG/JPEG，
`createFromPath` 对它返回 `isEmpty=true`，于是 `imageThumb` 返回 `null`、
条目没有 `thumb`，而渲染层按 `type` 分支 → `<n-image src="">` → 空白。

**为什么这个报告漏了它**：这份报告的所有条目都来自"读代码找问题"。
而这条**只有对着真实数据才看得见** —— 代码里 `imageThumb` 那句
「格式不支持或文件损坏 → 返回 null，调用方降级为无封面」读起来是**完全合理**的。
它不合理的地方是**另一半**：`server/index.ts` 选封面的正则放行 `webp|psd|svg`，
而解码器一个都解不了 —— 承诺比能力大，而这个矛盾**跨了两个文件**，单看哪一个都不算错。

**教训**：接到第三节那四条（影子判据／读包装层代替读真实行为／对照组掺假／重开已裁决的不做）后面，
这是**第 ⑤ 条** —— **"读代码"只能发现"代码内部的矛盾"，发现不了"代码与真实数据的矛盾"。**
这条不是交叉验证逼出来的，是**用户给了一个具体的失败样本**才逼出来的。
对照组的坑也在这一条里复现了一次：我第一版探针的"真 JPEG 对照组"是用空图的 `toJPEG()`
生成的，出来还是空图 —— **对照组本身是坏的，结论就成了噪声**。重做后才拿到干净证据。

**改法与实测**：见 `CHANGES-VS-ORIGINAL.md` 第九节（含 7 步定位证据链与 E2E 数字）。
核心是修在咽喉点：`imageThumb` 加 ffmpeg 兜底复用同一套超时/强杀保护和同一条缩放链路，
