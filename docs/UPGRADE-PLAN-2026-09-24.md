## 一、你问的第一件事：会不会损伤移动硬盘

### 1.1 硬答案：应用对 `E:/` `F:/` 零写入

**证据等级：实测 + 静态证据（可复算）**

全仓库穷举写盘 API（`writeFile` / `appendFile` / `createWriteStream` / `unlink` / `copyFile` / `rename` /
`mkdir` / `rmSync` / `truncate` / `.output(`），排除 `node_modules`，命中 **11 处，无一处目标路径含 `E:` 或 `F:`**：

| # | 代码位置 | 写什么 | 落在哪 |
|---|---|---|---|
| 1 | `electron/server/nedb.ts:62` | 缓存库 `searchCache.db` | `C:\Users\<user>\.file-finder\` |
| 2-3 | `@seald-io/nedb` 内部 `persistence.js:163` / `storage.js:238-250` | append + 临时文件 rename | 同上 |
| 4 | `electron/server/nedb.ts:84` | 缓存库备份 | 同上 |
| 5-6 | `electron/utils/driveIdentity.ts:175-176` | 盘注册表 `disks.json` | 同上 |
| 7-9 | `electron/utils/thumbnail.ts:94,121,225` | ffmpeg 中转图 / 抽帧临时文件 + `unlink` | `C:\Users\<user>\AppData\Local\Temp\` |
| 10 | `vite.config.ts:9` | `rmSync('dist')` | `D:`（仅构建期，非运行期） |
| 11 | `fluent-ffmpeg` 内部 `recipes.js:328` | 临时目录 mkdir（已存在则不执行） | `%TEMP%` |

**抽帧和图片转码的中转文件全部写在系统盘 `%TEMP%`，并在 `finally` 里立刻 `unlink`** ——
这不是巧合，`thumbnail.ts:93,99` 的注释就是这么写的动机（"中转文件写在**系统盘**临时目录（不是移动硬盘）"）。

### 1.2 但有三个前置条件（第 1 版漏了）

| # | 条件 | 一旦不成立会怎样 |
|---|---|---|
| 条件一 | **系统 `TEMP` 必须指向系统盘**（本机实测 `os.tmpdir()` = `C:\Users\<user>\AppData\Local\Temp` ✓） | 用户若把 TEMP 环境变量改到移动硬盘上 → **"零写入"立刻失效**，每次抽帧都会写移动盘 |
| 条件二 | **`USERPROFILE` 必须正常** | `config/index.ts:3-6` 是 `USERPROFILE \|\| USER \|\| '/'` 兜底。环境变量异常时 `userBasePath` 会退化成 `/`，**缓存库可能落到"当前盘根"** —— 而当前盘可能正好是移动盘 |
| 条件三 | **OS 层无法保证零写** | 本机实测 `fsutil behavior query disablelastaccess` → `DisableLastAccess = 2`（**已启用 atime 更新**）。NTFS 会以 60 分钟粒度回写 LastAccessTime —— **物理层存在 OS 发起的元数据写入**。准确表述是「**应用不写，OS 可能写元数据**」 |

> ⚠️ 另外实测：`fsutil fsinfo drivetype E:` → **"固定驱动器"**。
> Windows 把这两块盘当**固定盘**对待 → Search 索引器 / SysMain 预读 / VSS 快照会按固定盘策略自行碰盘。
> **这部分任何应用都无法通过"少写代码"消除**，只能由用户在系统层关闭。

### 1.3 唯一真实的风险：USB 供电（和"读多少字节"无关）

**证据等级：静态证据 + 厂商资料**

- 过热不是问题：HDD 连续读 3 分钟的温升是个位数 ℃。
- **真正伤盘的是频繁 spin-up / spin-down**（SMART 193 Load/Unload、马达轴承电流冲击），不是连续读。
- 但 2.5″ 移动硬盘铭牌常见 **5V/1A**，而 USB 3.0 口额定只有 **0.9A**。
  持续读盘会耗尽内部电容缓冲 → 低压保护掉盘（实测案例：电压从 5.08 V 掉到 4.61 V，低于 USB 规范的 4.75 V）。
  **3 分钟连续读恰好是最容易触发这个工况的负载形态。**

**所以方案里"串行、一次一块盘"这条不是随便写的 —— 它挡住了双盘同时供电峰值，是真实有效的保护。**
但要补一条：**扫描期间禁止系统休眠 & 关闭 USB 选择性暂停**（否则 Windows 会在扫描间隙掐掉端口供电）。

### 1.4 被所有旧文档漏掉的一个读盘者：**ffprobe**

**证据等级：静态证据（代码路径可追）**

`thumbnail.ts:191` 用的是 `timestamps: ['1%']` —— **百分比形式**，会命中
`fluent-ffmpeg/lib/recipes.js:159` 的百分比分支 → `getMetadata()` → `recipes.js:160` `self.ffprobe` →
`ffprobe.js:155` `spawn(ffprobe, ['-show_streams','-show_format',…, src])`，**`src` 就是移动硬盘上的视频文件**。

**即：每个视频在抽帧之前，还会多起一个 ffprobe 子进程去读它。**
方案、`thumbnail.ts` 注释、`AUDIT-VERIFY`、`CHANGES-VS-ORIGINAL` **全都只提 ffmpeg，没一个提到 ffprobe**。

⚠️ **附带风险（待核实，未量化）**：`runFfmpeg` 的 20 秒超时只 `cmd.kill()`（ffmpeg 命令对象），
而 `ffprobe` 是 fluent-ffmpeg 内部 **另外 spawn 的进程**。超时或异常时它是否被回收、
会不会继续持有移动硬盘句柄（进而阻止安全弹出），**需要实测确认**。

### 1.5 读出多少字节（第 1 版从未量化）

**证据等级：推理（未实测，受"禁止跑 ffmpeg"约束，无法用受控实验测准）**

- 目标树实测总容量 **822 GB / 398 文件**（`node docs/probes/scan-cost.mjs <dir> --stat`：E 379.5 GB + F 442.85 GB）。
- 但重建**不会读整个文件**：抽帧是 input seek（`-ss` 在 `-i` 之前，只读目标位置附近）、
  图片只解码一次、ffprobe 只读容器头部。
- 量级估计：**GB 级**。对照 Seagate 官方的消费级设计限值 **180 TB/年**（WRL 公式含读），
  这次全量重建约占 **0.001%**。
- 阅读材料：Micron 白皮书明确 "HDDs … incur wear when **read or written**"；
  **SSD 只在写入时磨损，读不影响寿命**。

### 1.6 本节总判

> **不会损伤移动硬盘 —— 有条件。**
> 应用层零写入（有穷举证据）→ 唯一真实风险是 **USB 供电**（靠"串行 + 禁休眠"挡住），
> 唯一未量化的是 ffprobe 的读取量与句柄回收。**磁盘健康方面的结论是：不需要为它改任何设计，只需要加两条保护说明。**

- 连跑两遍无法区分（7 ms → 6 ms，提速仅 1.2×），所以**冷态数据本次没测到**。

## 三、根因：你为什么会丢缓存

### 3.1 直接原因（**成立**，实测）

`nedb.ts:176` 启动时执行：

```ts
nedb.count({ v: { $ne: CACHE_VERSION } }, ...)   // CACHE_VERSION = 2
nedb.remove({ v: { $ne: CACHE_VERSION } }, { multi: true }, ...)
```

**已用真实 `@seald-io/nedb` 4.1.2 在临时库实测**：插入 4 条文档（无 `v` / `v:1` / `v:2` / `v:null`），
`count({v:{$ne:2}})` 返回 **3**，匹配 `{无v, v:1, v:null}`，`remove` 后只剩 `v:2`。
→ **判据确实是「没有 `v: 2` 就删」**，`$ne` 会匹配"字段不存在"。

**所以被删的那批里，包含了"格式完全正确、只是没打 `v` 标签"的记录。**

### 3.2 那条被误删的记录（**成立**，实测）

备份 `searchCache-20260924.db` 里有一条（`serial: BBBB2222`, `relPath: videos/示例演员I`），
实测其顶层字段集与活库 22 条 v2 记录**完全一致，唯一差异就是缺 `v`**；
`data[]` 的字段并集 `dir,ext,files,isDirectory,name,size,thumb,thumbData,type` 与活库 v2 记录**逐字相同**，
`files` 形状 `{name,size}` 与 `index.ts:52-55` 一致。

> ⚠️ **删掉一个第 1 版的错误佐证**：第 1 版还写了"`00CB-` 前缀 = `newThumbKey` 的新格式，可作 v2 佐证"——
> 这是**影子判据**。同文件里那条公认的旧格式记录，它的 `thumb` **同样是 `00CB-` 开头**
> （`newThumbKey` 取的是 `serial.slice(0,4)`，旧记录本来就有 serial）→ **这个判据对 v1/v2 零区分力**。

### 3.3 ⚠️ 修正：v1 能不能迁移 —— **现在无法验证**（第 1 版说错了）

第 1 版声称"v1 记录里 `dev` = 卷序列号、完整 stat、原图 base64 全在 → 107 MB 本可纯内存迁移"，
并据此断言 `ARCH-PLAN` 的"旧格式留着没用"**是错的**。

**这个论断站不住，两处问题：**

1. **证据张冠李戴**。第 1 版引用的那一条（带 `dev:13354734` 的），**它自己就带 `serial`、
   `dir` 是盘内相对路径、用的是 480px 的 `thumb`/`thumbData`** —— 这**不是** v1。
   真 v1（`git show 65516c5:electron/server/nedb.ts`）的结构是 `{_id?, path, data, create_at, mode}`：
   **键是完整路径 `path`、没有 `serial`/`relPath`/`count`/`v`**，`FileInfo` 是 `fs.Stats & {...}` +
   `base64`（**原图**，不是 480px 缩略图）、`avatar` 是 data URI。第 1 版拿"下一代格式"去反驳"上一代格式"。
2. **样本已灭失**。真正的旧格式数据：123 MB 那份已被用户确认删除、107 MB 那份被同名备份覆盖（`searchCache-YYYYMMDD.db` 同天互相覆盖）——
   **现在没有任何一条真 v1 样本可供验证**。

**修正后的表述**：
> 「v1 是否可无盘迁移」= **不可验证的推理**。理论上 `data[].dev` 能反推 serial，
> 但至少还有三处硬陷阱没被验证：`serial` 只能从 `data[].dev` 反推（`data[]` 为空即不可迁移）、
> `avatar` 在 v1 是 data URI 而 v2 是 key（直接搬必然 404）、`dir` 必须从完整路径改写为盘内相对路径。
>
> **对 `ARCH-PLAN` 那句话的公正评价**：「新代码读进来也会当脏数据清掉」在**当时的判据下是事实**；
> 「留着没用」是一个**判断**，在当时信息下不算错，只是**代价被低估了**（没意识到重扫要碰盘 ~90 秒/百目录）。

## 四、方案（修正后）

### P0 · 停自动删 + 版本不符即当成没缓存 ★唯一必做

**第 1 版设计的「迁移链 + `stale` 标记」被推翻 —— 理由：今天零输入，而且它有致命漏洞。**

| 被推翻的第 1 版设计 | 为什么不成立 |
|---|---|
| `MIGRATIONS[n]` 逐级迁移链 | 实测当前库 **22/22 全是 `v=2`**；v1 样本已灭失 → 给不存在的数据写框架。而且**迁移写错 = 静默产生错误数据，比删库更难发现** |
| 新增 `stale` 字段 | 不需要。`v` 已经在每条记录里，`stale` ≡ `v !== CACHE_VERSION`，纯推导 |
| "补漏了也只会降级重扫" | **这句是错的**。忘了 bump `CACHE_VERSION` 时 `migrate()` 看到 `v === CACHE_VERSION` 什么都不做 → **静默用错数据**。必须删掉这句 |

**修正后的 P0（真实核心 3 处改动）**

| # | 改动 | 说明 |
|---|---|---|
| 1 | **删掉 `dropLegacyRecords()` 及其在 `server/index.ts:810` 的调用** | 把"删除"从启动路径上**移除**。全库被清的唯一原因就是它 |
| 2 | **`findCache` 加版本判断：`v !== CACHE_VERSION` → 当作未命中（返回 null）** | 下次浏览那个目录时 `scanAndCache` 会 `removeCache + insertCache` **自然覆盖**。**符合版本的记录一律不碰** |
| 3 | **条目按白名单重建**（`pickFileInfo(raw)` 只放行 `FileInfo` 声明的 10 个字段） | ⚠️ **这条是漏洞修复，不是锦上添花**，见下 |

**第 3 条为什么必须做（第 1 版完全没有）**

实测证明"旧记录留在库里不会有害"是**错的**：
- `openFolderController`（`index.ts:523`）只用 `(serial, relPath, mode)` 精确匹配，**全程不看 `v`**
  → 键相同的旧记录会被**直接命中并下发**，"版本判断"如果只写在 `findCache` 里就够，但如果忘了写就漏。
- `stripThumbData`（`thumbStore.ts:58-63`）是**黑名单**（只解构掉 `thumbData`/`avatarThumbData`）
  → 实测下发内容里**保留了 17 个 `fs.Stats` 字段**：`atime,atimeMs,birthtime,blksize,blocks,ctime,dev,gid,ino,mode,mtime,nlink,rdev,uid,…`
  —— **含 `dev`，也就是盘身份**，正是 `index.ts:64-68` 注释明令不许发生的事。
- `toWire`（`index.ts:460-462`）对完整路径形态的 `dir` 会拼出 **`F:/E:/sample/videos`**（实测复刻确认）。

> **黑名单 vs 白名单，就是补丁 vs 修复**：
> 黑名单是"我知道哪些要剥掉"→ 将来 `FileInfo` 少一个字段、旧记录多一个字段，就漏。
> 白名单是"我只放行我认识的"→ **将来任何字段变化都不会泄漏**。

**P0 的验证判据**（第 1 版的判据 #2 是按迁移链写的，作废）
1. 启动日志不再出现「发现 N 条旧格式缓存，先清理」
2. 手动造一条 `v: 1` 记录 → 重启 → **它还在库里**；浏览那个目录 → 被新记录覆盖（旧记录消失）
3. 手动造一条含 17 个 `fs.Stats` 字段的 `v: 2` 记录 → 让 `/openFolder` 命中它 →
   **下发的 JSON 里不得出现 `dev`/`atime`/`ino` 等任何非 `FileInfo` 字段**

### P1 · 批量扫描 → **降级为可选**（第二轮自查后，见 §11）

> ### 🔁 状态更新（2026-09-24 17:15）：用户提出实际场景，**重新进方案**
>
> 用户原话：**「如果一个文件夹里有 80 多子文件夹，子文件夹里还有子文件夹合计大概有 500–1000 部，
> 要用户自己点 80 多下吗？但是主动读我又怕会损害用户磁盘什么的」**
>
> | 他的顾虑 | 证据 |
> |---|---|
> | **主动读会伤盘吗** | **不会。** 11 条写盘路径穷举 → 应用对 `E:/F:` 运行期写入 **0**；读取不磨损磁介质。唯一真实风险是 **USB 供电**（§1.3），挡法是"串行 + 一次一块盘 + **分批**"，**不是"少读"** |
> | **要不要点 80 多下** | **不用。** 实测他这几块盘：目录总数 **171**，其中 **127 个被收敛成封面、根本点不进去**，可点开的只有 **44**，其已缓存 **23**（含 17:09 新点的 `videos/井上瞳`）→ **还剩 ≈21** |
> | **那 500–1000 部呢** | 那是**文件数**，不是"要点几下"。它决定的是**抽帧总量**（全量 524 张缩略图 ≈ 70 s–2.5 min，**推算**），不是点击次数 |
>
> **关键对称性**：用户手点 N 下 与 程序扫一遍，**读的字节数完全相同**；
> 差别只是"分摊在几小时里"还是"集中在几分钟里"。
> → 所以 P1 的形态**不是「一键全盘扫」**，而是
> 「把这一层没缓存的目录**排队**扫完 —— **串行、可中断、带进度、每批 ≤20 个**」，
> 这样 USB 也不会被长时间顶住。
>
> **用户已拍板（17:15）**：ffprobe（§13）**跟着这批一起做**。

**第 1 版说它"唯一必做"，理由被第二轮自查推翻了。**

| 第 1 版的说法 | 实测 |
|---|---|
| "不做 = 手工导航 ~149 个目录（进 + 回 ≈300 次动作）" | ❌ **149 是点不进去的收敛目录也算进去的结果**。真实还需点 **22 次**（§2.5 实测） |

**降级理由**：这是一个**一次性**的操作 —— P0 修好之后缓存不会再丢，所以"点 22 次"这件事**这辈子大概只做一次**，
总耗时估计几分钟（22 个目录，多数是演员目录，每个等几秒到十几秒）。
而它的实现要碰**三处真实风险**（并发写竞态、UI 状态隔离、盘符→序列号换算）。

> **判断**：省 22 次点击，换三处需要仔细处理的风险 —— **不划算**。
> 如果你觉得这 22 次点起来烦，那就做；但**不做也不影响"以后不再丢"这件事**（那是 P0 的功劳）。

**如果决定做，实现要点（照抄即可）**

**第 1 版设计的「新增服务端端点 + 主进程任务队列」被推翻 —— 理由：可以在前端做，且不加任何接口。**

第 1 版给的理由是"渲染层发 N 个请求 = N 个并发扫描任务，会互相抢盘"。
**只要串行 await，这个理由就不成立。**

**修正后的实现（零服务端改动）**

```
1. 取已缓存集合：/getHistory（分页取全）→ 得到 (serial, relPath) 集合
2. 从用户选的根出发，深度优先遍历：
     对每个目录 → 若在已缓存集合里 → 跳过
                → 否则调已有的 /openFolder（它本来就是"扫这层并写缓存"）
                → 把返回里的 type==='folder' 条目入队
3. 进度 = 已处理/总数（总数可先用一次 /getFileTree 拿目录清单，或显示"已扫 N 个"）
4. 取消按钮 = 置一个 flag，每个目录边界检查一次
```

**必须注意的三条**
| # | 事项 | 原因 |
|---|---|---|
| 1 | **扫描用独立的请求函数，绝不能复用 `fetchFolder`** | `fetchFolder` 会写 `dataSource` / `loading` —— 后台扫描会把用户当前正在看的网格冲掉 |
| 2 | **串行，一次一块盘** | 挡住双盘同时供电峰值（见 §1.3，这是真实的 USB 掉盘保护） |
| 3 | **跳过已缓存** | 幂等 → 天然可续传（断电、取消后重跑接着来，不需要任何额外机制）；也避免把已扫过的 22 个目录再抽一遍帧 |

⚠️ **并发写竞态（子代理发现，第 1 版没提）**：`scanAndCache` 是 `removeCache` + `insertCache` **两步非原子**（`index.ts:483-484`）。
后台扫描期间，用户随时可能点进同一个目录 → 同键并发删/插。
现在偶发，加了 P1 会变成**必然**。修法：服务端把这两步收进一个队列，或前端扫描期间对已扫目录加一道内存锁。

⚠️ **收益要说实话**：真正还需要点的只有 **22 次**（§2.5 实测），不是 149 次。
省下的是"22 次点击 + 每次几秒到十几秒的等待"，即**一次性几分钟**。

### P2 · 导出 / 导入 / 加密 → **整体降级为"零代码"**

**第 1 版设计的「JSON 导出格式 + AES-GCM 加密容器」被推翻 —— 理由：已有零代码等效物。**

**关键事实**：缓存的键是 **`(serial, relPath, mode)`** —— 卷序列号 + 盘内相对路径。
**盘符根本不落在数据里**（下发时才补，`index.ts:460`）。所以：

> **`~/.file-finder/searchCache.db` 这个文件本身就是一份完整的、跨机器有效的导出。**
> 复制它 = 导出；覆盖它 = 导入。**不需要写任何解析、合并、冲突处理代码。**

**对你三个问题的正面回答**

| 你的问题 | 答案 |
|---|---|
| 记录支撑导出和导入吗？ | **支撑**，而且**不用开发** —— 直接拷 `searchCache.db`（7.82 MiB）。跨机器有效（前提是同一块盘） |
| 导出的内容能加密吗？ | **能，但建议不这么做**。若要加密，**用现成工具**（7-Zip / VeraCrypt）加密那个文件即可 —— 比在应用里造一套新二进制格式 + "改口令 = 旧文件全废"的契约省得多 |
| 为什么不做加密？ | ① 第 1 版自己承认它"只防人类随手打开"，不防有心人；② 它和"选 JSON 是为了**人可读、可 diff、能手改**"**自相矛盾**；③ 加密是**正交维度**，跟"要不要做导出功能"没关系 —— 用系统工具就能加 |

**降级后的可选小动作**（1 小时以内，你想做再做）：缓存面板上加一个「打开数据目录」按钮
（`shell.openPath(userBasePath)`），让你能直接找到那个文件去复制。

> ⚠️ **第 1 版留了一个硬错误必须记下来**：方案写的 `scryptSync(pwd, salt, 32, {N:2**15, r:8, p:1})`
> 在 Node 22.22.2 上**直接抛错** `ERR_CRYPTO_INVALID_SCRYPT_PARAMS: memory limit exceeded`
> —— 因为 `128·N·r = 32 MiB` 正好顶满默认 `maxmem`。要跑起来必须显式传 `maxmem ≥ 33 MiB`（建议 64 MiB）
> 或把 N 降到 2^14。**幸好这条在被推翻的 P2 里，没有进入实现。**

**观察项 1 展开 —— 库损坏的真实行为（第 1 版写反了）**

|---|---|

## 十三、第三轮实测：ffprobe 超时会不会留下孤儿进程

> **为什么值得测**：`runFfmpeg` 的超时保护是全项目唯一的"卡死兜底"。它的注释写着
> 「kill 之后那个 ffmpeg 进程会一直拿着移动硬盘的句柄不放，所以必须杀」。
> 但如果**超时那一刻跑的根本不是 ffmpeg，而是 ffprobe**，这句话就不成立 ——
> 而 ffprobe 同样在读移动硬盘上的源视频。这是唯一一条"读"能真的伤到盘
> （拔盘失败 / 盘一直被顶住不转停 / 句柄不释放）的路径。

### 13.1 静态链（逐行可复算，三条独立证据）

| # | 证据 | 位置 |
|---|---|---|
| 1 | `screenshots({timestamps:['1%']})` 内部是 `async.waterfall`，第一段 `computeTimemarks` 必须**先 `self.ffprobe(...)`** 拿到 duration，才能把 `1%` 换成秒 → **最先跑起来的子进程是 ffprobe** | `fluent-ffmpeg/lib/recipes.js:156-215` |
| 2 | `screenshots()` **同步返回**（waterfall 还没跑），而 `extractFrame` 的 `runFfmpeg(cmd, ...)` 是紧接着同步调用的 → **20 秒计时器在 ffprobe 阶段就已经开始计时** | `electron/utils/thumbnail.ts:187-197` |
| 3 | `proto.kill` 只做一件事：`if (!this.ffmpegProc) { logger.warn(...) } else { this.ffmpegProc.kill(signal) }`；而 `ffmpegProc` 是在 `processCB` 里才赋值的 → **ffprobe 阶段它是 `undefined`**。且 ffprobe 在库里是**局部变量** `var ffprobe = spawn(...)`，从没挂到命令对象上 → **命令对象够不着它** | `processor.js:653-662` / `processor.js:445` / `ffprobe.js:155` |

**推断**：超时若落在 ffprobe 阶段（盘拔了 / 坏道 / USB 掉线），`cmd.kill()` 走 `logger.warn`，
**一个进程都没杀**，孤儿 ffprobe 继续攥着源文件不放。

### 13.2 实测（探针 `docs/probes/ffprobe-kill-leak.mjs`，Node 22.22.2）

素材用 lavfi 现生成到 `%TEMP%`（10866 B，**不碰任何外盘**）；
卡死用「永不写入也不关闭的 stdin 管道」模拟 —— 机制与「ffprobe 卡在读盘上」相同：进程阻塞在 read，命令对象够不着它。

**A. 子进程启动顺序 + 命令对象在 ffprobe 阶段的状态**（正常本地文件）

| 观测 | 结果 |
|---|---|
| 实际 spawn 顺序 | `ffprobe.exe` → `ffmpeg.exe -formats` → `ffmpeg.exe -encoders` → `ffmpeg.exe -ss 0.02 -i <src>` |
| **ffprobe 存活期间 `cmd.ffmpegProc` 曾为 undefined** | **是** |
| ffprobe 阶段耗时 | **698 ms**（本地 SSD + 2 秒小视频；换移动盘上 5–7 GB 的片子只会更长） |

**B. 卡住时调 `cmd.kill('SIGKILL')`（与 `runFfmpeg` 超时分支逐字相同）**

| 观测 | 结果 |
|---|---|
| kill 前 ffprobe 存活 | 是 |
| kill 前 `cmd.ffmpegProc` 是否已存在 | **否** |
| kill 后 ffprobe 存活 | **是** |
| 判定 | **❌ 未杀掉 —— 泄漏成立** |

**C. 连续触发 5 次**

| 轮次 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| kill 后仍存活的子进程数 | 1 | 2 | 3 | 4 | 5 |

→ **线性累积**，每卡一次多留一个。

### 13.3 边界（不夸大）

| 项 | 说明 |
|---|---|
| 触发条件（第四轮补精度） | **不是概率，是确定性条件**：计时器从 `screenshots()` 那一刻起跑，ffprobe 跑在 `[0, t_probe]`、ffmpeg 跑在 `[t_probe, t_total]`。所以——<br>**超时落在 ffprobe 窗口 ⟺ `t_probe > 20 s`**（ffprobe 自己 20 秒没读完元数据）。<br>反过来，只要 ffprobe 在 20 秒内返回，超时就必然落在 ffmpeg 窗口、kill 正常生效。所以**"低概率"这个说法成立，且可以精确表述为"只有当盘已经病到 ffprobe 自己超 20 秒"** |
| 影响面 | 孤儿 ffprobe 持有源文件句柄 → 拔盘可能失败 / 盘持续被顶住；不会写盘、不会改文件 |
| `ffmpeg -formats` / `-encoders` 两个能力探测进程 | 也在超时窗口内、也够不着，但它们**不碰源文件**（首次使用时每进程各跑一次） |

### 16.1 任务 A —— P1 批量扫描 + 重扫模式

**入口（1 个按钮，不放两个）**：网格上方加一个按钮，文案 **「补全缓存」**。
悬停/下拉给第二个选项 **「重扫这一片」**（同一套队列，区别只在带不带 `noCache`）。

**语义**

| 模式 | 做什么 |
|---|---|
| 补全缓存 | 从**当前目录**出发向下递归，只扫**没有缓存**的目录 |
| 重扫这一片 | 同一套递归，但每一层都带 `noCache=true` 重扫一遍 |

> 「重扫这一片」就是"目录增删改之后"的答案 —— **不需要去精准识别变更**：
> ① 精准识别只能做到"这一层直接子项的增删"（存目录 `mtimeMs` 比对），深一层、同名替换都看不出来，
> 会给出**假安全感**；② 而每次打开缓存目录都要多一次 `stat` 碰盘，与项目最高优先级冲突；
> ③ `fs.watch` 递归订阅确实几乎不读盘，但那是**新增一个子系统**（拔盘/重插/UNC/漏事件都要处理）。
> **同一套队列多一个 flag 就够了，零新概念。**

**必须遵守（4 条）**

| # | 约束 | 原因 |
|---|---|---|
| 1 | **用独立的请求函数，绝不复用 `fetchFolder`** | `fetchFolder` 会写 `dataSource` / `loading` —— 后台扫描会把用户正在看的网格冲掉 |
| 2 | **串行，一次一个目录** | 挡住双盘同时供电峰值（§1.3，这是真实的 USB 掉盘保护） |
| 3 | **跳过已缓存**（补全模式） | 幂等 → 天然可续传；也避免把已缓存的目录再抽一遍帧 |
| 4 | **每批 ≤20 个目录后主动让一下** | 别让 USB 被长时间顶住；也给取消留出响应窗口 |

**进度与取消**：显示「已扫 n / 待扫 m」（`m` 动态增长）；取消 = 置 flag，每个目录边界检查一次。

**入口位置**：网格上方。**这是用户的交互地盘** —— 按钮位置和文案可按他的意见改，逻辑不变。

**顺带必须修（子代理发现，第 1 版没提）**：`scanAndCache` 的 `removeCache` + `insertCache` 是**两步非原子**。
现在偶发，加了 P1 会变成**必然**（后台扫同一个目录 vs 用户点进去）。
修法判据 = 「以后新增同类场景会不会复发」：**把这两步收进服务端的唯一写入点**，而不是给每个调用方加锁。

### 16.2 任务 B —— ffprobe 超时修复（§13）

**目标**：让 20 秒超时**全程有效**（现在 ffprobe 阶段够不着，见 §13）。

**必须保住的行为（不许顺手改）**
- 抽帧位置仍是**时长的 1%**（不是固定秒数 —— 这是有意选的，躲开片头黑场）
- `THUMB_WIDTH` / `THUMB_SCALE` 链路不变；`FFMPEG_TIMEOUT_MS = 20000` 不变
- 取不到时长 → 返回 `false`（与今天的行为一致），**不要**退化成固定时间点

**修法（照做）**
1. 自己 `spawn` ffprobe（用 `@ffprobe-installer/ffprobe` 的 path）拿时长，**自己带超时 + 自己 `kill` 手里的 pid** ——
   这样"够不着的子进程"在结构上就不存在了。
2. 拿到时长后调 `screenshots({ timemarks: [dur * 0.01] })` —— **传数字而不是 `'1%'`**，
   因为 `'1%'` 会让 `fluent-ffmpeg` 内部再去起一次 ffprobe（`recipes.js:156-215`）。
   传数字后 `computeTimemarks` 直接跳过，命令里**只剩 ffmpeg** → 超时全覆盖。
3. 结论要写进注释：**为什么不能用 `'1%'`**（否则下一个人会改回去）。
