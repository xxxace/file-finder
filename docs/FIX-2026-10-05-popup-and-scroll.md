## 一、弹层重做

### 丑在哪（实测，不是观感）

探针 `docs/probes/popup-visual/`（真 scoped CSS + 真 naive-ui + 真 fiv 图标，改前改后同一套量）。

| 量 | 改前 | 改后 |
|---|---|---|
| `.file-item` | 84 × 84 | 150 × 116 |
| `.file-cover` 盒 | **0 × 0** | 18.7 × 26（背景 `mp4.svg`） |
| `span` 的 `white-space` | `nowrap` | `normal` |
| `span` 盒 | 78 × 38（**单行**） | 132 × 30～45（2～3 行） |
| 大小行 | 无 | `1.29 GB` … |

⇒ 改前的真身：**一个 84×84 的空盒子 + 一行截断到约 9 个字符的名字**。
而这一层的文件名常常**同前缀**（`[TST-593] … CD1 / CD2`）⇒ 4 个格子显示成**一模一样**的
`[TST-59…` —— 不是"不好看"，是**根本没法选**。

### 根因：网格的规则漏进了弹层（两处，同一个病）

`.image-box-item, .file-item { … }` 把两者写在**同一个选择器**里，于是网格那半的属性原样漏了下来：

| 症状 | 漏下来的属性 |
|---|---|
| 图标从来没画出来 | 网格那套尺寸与 `!important` 高度把没有显式尺寸的 `.file-cover` 压成 **0 高**；再加上它漏写了 `fiv-cla fiv-icon-*`（网格第 172 行是写全的），只剩 `blank.svg` ⇒ 等于没画 |
| 名字只剩前缀、选不了 | `white-space: nowrap` + `height: 38px !important` ⇒ 弹层里那句 `word-break` / 多行**全是死代码** |

### 修法（不是打补丁：让"漏"在结构上不可能）

按「**谁的属性谁持有**」把那个共用块**拆开**：

```
.image-box-item, .file-item { … }   ← 只留真的共用：flex 底座 / 边框 / 过渡 / hover·active
.image-box-item { … }               ← 网格独有：--item-* 6 列算法 + 三个 !important 高度 + .n-image/img/span(nowrap) + 5 个断点
.file-item { … }                    ← 弹层独有：150×116 + 图标 + 可换行名字 + 大小
```

**判据（同类场景会不会复发）**：拆开之后，往网格那条 `span` 规则里再加任何属性，都**不可能**再漏到弹层。

**"拆对了"的旁证**：弹层那边原来有 3 个 `!important`（全是在跟网格那条抢），拆完**一个都不需要**了。

⚠️ 网格那三条 `!important` 高度是**生命线**（`--item-height` 由 `utils/flexible.ts` 的 `1rem = clientWidth/10` 推；
去掉 192px 的格子会塌成 24px）⇒ 它们必须留在**只有网格会命中**的选择器上。

**"拆分没动网格"怎么证的**（三份独立证据）：
① 把原共用块与拆分后的两块做**声明名集合双向比对**（`comm`），**逐一相同**（无缺无增），相对顺序也没变；
② 真布局探针：`grid-6col` 15/15、`grid-typography` 5/5、`row4-boundary` 13/13 —— 一行仍是 6 个、首末格仍贴边；
③ `grep` 全文件确认**没有第二处**把 `.image-box-item` / `.file-item` 写在一起的选择器。

⚠️ **措辞纠正（code review 抓到）**：这里**不能**说"网格一个字没变"。
上面三条证明的是"**这次拆分**没改网格"。而工作区相对 `HEAD` 的 diff 里，网格的
`:hover` 底色 / `.cursor` 底色 / `span` 字号字色**确实变了**（`1em`→`14px`、`#000`→`#374151`、
`bold`→`400`、去掉单侧 `box-shadow`）—— 那是 2026-10-04/05 的焦点与排版工作带来的，
**不属于本次范围**，别把两者混成一句话。

### 弹层现在长什么样

类型图标（`fiv-cla` + `fiv-icon-${ext}`，按扩展名）+ **可换行**的文件名（最多 3 行，尾部才是区分点）
+ 灰色大小（钉在卡片底部）。容器 `max-width: min(660px, 88vw)` ⇒ 4 个一行，多了换行，不会横向撑到屏幕外。

**没有改"横向排布"**（←→ 是业主 2026-10-05 明确要的，见 `DESIGN-GRID-CURSOR-2026-10-04.md` §三）。

⚠️ 已知的顺序敏感点：`.file-cover` 的兜底 `blank.svg` 与 `.fiv-cla.fiv-icon-*` 特异性打平（`0,2,0`），
谁在后谁赢。实测真实产物里 fiv 在后（`dist/assets/index-*.css` 偏移 12124 vs 595983）⇒ 图标正常。
这是**既有机制**（网格同一个），本次没动。

## 二、「返回后滚动串屏」根因

### 现象

- A（0）→ B（0）→ 回 A：A = 0 ✅（**看起来对，其实那段代码根本没执行**）
- A（0）→ B → B 滚 300 → 回 A：A = **300** ❌

### 根因（一行）

`onBack` 里恢复滚动的那一段原来是 `if (to.scrollY) { … }`。

**这条路径上没人归零**：容器只在**前进**时被归零 —— `enterScreen` 里那两处 `scrollTo(0, 0)`
（取数前 + 取数落地后）。而 `onBack` **绕过 `enterScreen`**、直接调 `fetchFolder`
⇒ `fetchFolder` 换的是**数据**、容器元素没换 ⇒ 返回时 `scrollTop` 原样留在身上。

⇒ 目标屏记的位置是 **0** 时整段被**跳过**，容器就把**上一屏的偏移**一直带着。
B 没滚过时容器本来就是 0 ⇒ 跳过后看起来正常（**"没触发滚动就正常，滚动了就不对"**逐条吻合）。

⚠️ **措辞纠正（code review 抓到，很重要）**：我第一版写的是
「网格容器**不会**自己归零 —— `grep scrollTop` 全项目只有'被记录'和'被恢复'两处，**没有任何一处写 0**」。
**这是错的**：`enterScreen` 就是写 0 的地方（`index.vue` 的 `scrollTo(0, 0)` 两处）。
错在**取证方式** —— `grep scrollTop` 枚举**结构上就漏掉** `scrollTo(0, 0)` 这种写法，
于是"全枚举"这个说法本身站不住。
⇒ 正确的判据是「**返回这条路上有没有人归零**」，不是「全项目有没有 `= 0`」。
（修复结论不受影响，但根因描述与证据等级必须按这条改写。）

### 修法

**无条件恢复，包括恢复成 0。** 但两者的前置条件不同：

- `to.scrollY === 0`：**不需要等 DOM** —— `scrollTop = 0` 在任何内容上都成立，新内容铺上来之后仍是 0。
- `to.scrollY !== 0`：**必须**等 `waitForGridOf`（否则会在**旧屏**上"成功"滚到那个位置，回读也一致 ⇒ 判据抓不到）。

同时删掉了两处**临时诊断** `notify`（源码注释写着"拿到答案后删除"）：

- `notify('info', '诊断：返回恢复', …)` —— 纯诊断，且每次返回已滚动过的屏都会弹一次，是噪音。
- `notify('warning', '诊断：未就位', …)` → 改成 `'这一屏没能定位'`（它是真的兜底信号，留着；只是把"诊断"这个面向开发者的措辞换成面向用户的）。

### 证据等级

- 「**返回这条路径**上没人归零」= **静态**（枚举 `onBack` 的调用链：它不经过 `enterScreen`，
  而全文件的 `scrollTo(0, 0)` 只有 `enterScreen` 那两处 —— 这条可以复算）。
  ⛔ 不要写成"全项目没有一处写 0"（错，见上面的措辞纠正）。
- 「弹层那两处丑是 CSS 漏属性造成的」= **实测**（`docs/probes/popup-visual/out.txt`，真 Chromium 量 `getComputedStyle`）。
- 「返回后 A = 300」这条修复 = **未实测**（需要真机跑 dev：A→B→滚 B→返回，看 A 是否在顶）。
  ⚠️ 本项目唯一能验的地方是 `wire()` 之下的真机路径，探针够不到。

## 四、业主复验（00:59）：两处收尾缺陷

### ① 弹层橙色边框 = **浏览器默认焦点环**（不是项目里的颜色）

业主原话：「弹出层是橙色边框」。**全仓 grep 没有任何橙色字面量**
（`src` + `electron` + `index.html` 全扫；naive-ui 的 popover 样式里也没有 `outline`）。

⇒ 它是 UA 的 `:focus-visible { outline: auto }`，而 `outline: auto` 的**色值取自系统强调色**
（这台机器的强调色是橙的 ⇒ 换个系统主题它就换个颜色）。
几何也对得上：环正好**内缩 popover 的内边距**（探针量到 664−636 = 14px 横向、132−116 = 8px 纵向），
说明它画在**焦点所在的那一层内元素**上 —— 即 `.file-list`（`tabindex="-1"`）。

触发者就是 `openFileList` 里那句 `focus()`（`index.vue:658`）—— 它存在的唯一意义是**接住方向键**。
而那是个**为键盘操作设计的路径**（`:focus-visible` 正是在键盘交互下才匹配），
所以"用键盘打开弹层时冒出一个橙框"。

**修法**：在元素**自己**身上抑制 —— `.file-list:focus, .file-list:focus-visible { outline: none }`。
理由：它不是控件，"我在哪"由 `.file-cursor` 的蓝框表达 ⇒ 焦点环纯噪音。

⚠️ **探针复现不出这一条**（headless 里没有真实输入，Chromium 不给 `:focus-visible`；
连 `focus({ focusVisible: true })` 也不生效 —— 见 `run.cjs` 里那个最小复现，实测 `focusVisible: false`）。
⇒ 这一条的**证据等级 = 推理 + 排除法**（项目里没有任何橙色 + 几何吻合），**未实测**。

### ② 标题过长没有省略号

上一版只写了 `overflow: hidden` ⇒ 长名字被**硬切**，看不出"后面还有"。

**修法**：`display: -webkit-box` + `-webkit-box-orient: vertical` + `-webkit-line-clamp: 3`
（多行省略号**只有这一种 display 能让 `-webkit-line-clamp` 生效**，写成 `block` 会静默无效）。
`max-height: 45px` 留着当兜底（万一某个版本不认 line-clamp，也不许把卡片撑破）。

**实测**（探针第 4 个样本刻意用超长名）：
- `-webkit-line-clamp` 计算值 = **3**（属性被认得）；
- `clientHeight 45 < scrollHeight 60` ⇒ 内容**确实被钳住**（内容 4 行、盒子 3 行高）；
- 对照图里第 4 格末行是 `…`。

⚠️ **不要把 `nameDisplay` 这个量当证据**（code review 抓到）：探针里它报的是 `flow-root`，
而生成的 CSS 写的是 `display: -webkit-box` —— 两者不能同时字面成立（疑为 Chromium 的序列化差异，
**未复测**）。功能信号（上面那条 `clientHeight < scrollHeight`）是硬的；"display 计算值"这个量
在本探针里**不可引用**。
