## 一、P0 —— 唯一必须的一条（证据齐、改动小）

### 问题（`docs/UX-DESIGN-INPUT-2026-09-24.md` §2.3，静态可复算）

`electron/server/index.ts:219-225` 的 `readFolder` 把两件事混成一个返回值：

| 真实情况 | 现在返回 | 应该 |
|---|---|---|
| 目录**真的是空的** | `[]` | `[]` ✅ |
| 目录**读不到**（I/O 错 / 权限 / 未就绪 / UNC 断） | `[]` ❌ | **报失败** |

而 `scanAndCache`（同文件 `:552-573`）**无条件**拿它写缓存 → `removeCache()` + `insertCache(count: 0)`
→ 一条真实记录被**合法地覆盖成空**，且 nedb 是"删旧+插新"，**旧记录拿不回来**。

### 修法（判据：让竞争在**结构上**不可能发生）

**核心动作只有一个：让 `readFolder` 不再把"读不到"伪装成"空目录"。**

1. `readFolder` 的 `readdir` 失败 → **抛错**（而不是 `return []`）
   —— 只有「`readdir` 成功且返回 0 项」才是"真的空目录"。
   ⚠️ 注意保留它**逐项 `try/catch`** 的容错（那一项失败跳过它）—— 那是另一个语义，**不许一起改**。
2. 上层按调用方各自处理（**这是"每个调用方错了才要改"，不是"要加守卫"**：
   语义变正确之后，两处本来就应该表现不同）：
   - `scanAndCache`（写缓存那条路）：抛错 → **走不到 `queueCacheWrite`** → 旧缓存完好 ✅
   - `openFolderController:604`（非盘符路径，不缓存）：抛错 → 前端 `catch` ✅
3. **"盘不在"也走失败通道**，不要返回 `[]`：
   现在盘不在时 `findDriveByLetter` 返回 `null` → 走 `:604` 分支 → `readFolder` 读不到 → `[]`
   → 前端 `dataSource = []` → **网格空、且没有任何提示**（`UX-DESIGN-INPUT` §2.2）。
   改成失败后，前端**不用改一行**：
   - `loadFailed.value = true` → `emptyTip` 自动变空串（`src/views/FileFinder/index.vue:207`）
   - 已有 `notify('error', '打开失败')`（`:387`）
   - 已有「不清空 `dataSource`」的兜底（`:385`）

### 为什么这样修是对的（三条硬理由）

1. **前端零改动**，而且正好命中用户已声明的特性 ——
   他要求「失败时**不显示**那行空状态小字」（`MEMORY.md` §一.16），
   这条特性本来就是为这个场景写的（`index.vue:195-198` 的注释解释了动机）。
   **修复方向与既有设计一致，不是新发明。**
2. **是根因修复，不是打补丁**：不写"如果 readFolder 返回空就跳过写入"（那是给调用方加守卫，
   以后新增写入入口立刻复发），而是让**返回值本身不再说谎**。
3. **不碰任何用户特性**，不动 `CACHE_VERSION`，不增加读盘。

### 验收判据（✅ 均已实测通过，见 §六）

| # | 判据 |
|---|---|
| 1 | 指向一个**不存在的目录**（同一块真盘上的合法盘符）→ 请求 `/openFolder` → **该目录旧缓存仍在** |
| 2 | 同上场景 → 前端弹「打开失败」+ **网格保留旧内容** + **不出现**「这个目录是空的」 |
| 3 | 一个**真的空目录** → 正常写入 `count: 0` 缓存（**不许**因为这次修复把真空目录也变成失败） |
| 4 | 回归：正常目录首次扫描、缓存命中、批量「补全这一片」全部照旧 |

> 证据等级：问题本身 = **静态证据（可复算）+ 推理**；修复效果 = **实测**（A/B 对照 + 回归，落盘记录逐条比对，见 §6.2）。
> 判据 3 是最容易"修过头"的一条，已单独回归。

## 二、P1 —— 入口重构（回答用户"你确定设计合理吗"）

**最强证据是用户自己提的问题**：「补全缓存和刷新按钮的作用有什么区别？」
—— **用户需要问区别，就说明入口设计失败。**

### 2.1 命名（待用户裁决，默认取保守版）

| 现名 | 建议 | 说明 |
|---|---|---|
| ↻（无文字） | **保留"刷新"**，加 tooltip「重新读取当前文件夹」 | ⚠️ 用户已用"刷新"称呼它（原话），改名有认知成本。**默认不改名，只补说明** |
| 补全缓存 | **补全这一片** | 这是**本轮新加**的功能，名字是我取的，可改。"缓存"是实现词 |
| 重扫这一片 | **重读这一片** | 「补全」vs「重读」语义对立、一眼可辨；旧名两者都像"重扫" |
| 缓存记录 | **保留** | 用户已熟悉，非本轮重点 |

### 2.2 入口结构

> ⚠️ 下表的「`trigger="click"` + 可见箭头」是**当时的建议**。最终没采它 ——
> 箭头方案只是把"隐藏"从 hover 挪到 click，**还是得展开一次**，可发现性只解决一半。
> 实际做的是**两个平铺按钮**（`补全这一片` / `重读这一片`），零展开成本。见 §6.3。

| 改动 | 现状 | 建议 | 为什么 |
|---|---|---|---|
| **可发现性** | 「重扫这一片」藏在 `trigger="hover"` 下拉里，不悬停看不见 | 改 **`trigger="click"` + 可见的下拉箭头** | 它恰是"目录增删改"的正解，却最不可见 |
| **防护反差** | 悬停展开、点一下立刻开跑，零确认 | 只给**「重读这一片」**加 `n-popconfirm` | 门槛 ∝ 不可逆 × 范围（见下） |
| **扫描中** | 只禁用了那个按钮 | **扫描期间禁用 刷新 / 重读 / 换目录** | 防止用户在整片扫描期间再叠一次强制读盘 |

**门槛原则（子代理提出、我采纳）**：
- 前置校验 > 二次确认（能提前拦住就别事后问）
- 覆盖类动作**必须盘在线**（`findDriveByLetter` 已实时 `stat`，现成能力）
- **不做撤销**，改做"不写坏数据"（即 P0）
- 只给 `重读这一片` 弹窗；`刷新` 与 `补全` **不弹** —— 刷新是高频操作，弹窗会烦死 ADHD 用户，
  而它的损失上限只是**一个目录**（重新点一下就回来）

### 2.3 三态可区分（真痛点）

现在「盘不在」「读不到」「空目录」在界面上**长得一模一样**（一片空白）。
用户看到空 → 合理怀疑数据丢了 → 不敢再用。

| 状态 | 呈现 | 组件 |
|---|---|---|
| 空目录 | 保持不变 —— 一行浅灰小字（**用户特性，不许动**） | 无（现有 `emptyTip`） |
| 盘不在 | 顶部横幅「盘没插上」 | `n-alert`（warning） |
| 读不到 | 顶部横幅「读不到，稍后再试」 | `n-alert`（error） |

> ⚠️ 这一条**依赖 P0 先落地** —— P0 之前，前端根本收不到"读不到"的信号（都被伪装成空）。

## 三、P2 —— 可选（做不做由用户定）

| 项 | 内容 | 代价 / 风险 |
|---|---|---|
| **快照可撤销** | 重读整片前自动调一次 `/backup`（已有 API、纯本地拷贝、零读盘）→ 把"不可逆"变"可撤销" | ⚠️ **`cacheBackup` 是同名覆盖**（`searchCache-YYYYMMDD.db`），同一天备份会互相盖。要用它兜底，**必须先给快照单独开一个槽位**，否则"以为有备份、其实早被盖了"。且全库涨到 ~96 MB 后每次拷一份不便宜 |
| **导入导出入口** | 只在「记录」面板加一个**文字链接**「打开存放文件夹」（`shell.openPath`） | 最小、只读、零新概念 |
| ~~完整导入/导出按钮~~ | **不做** | 理由：缓存就是 `%USERPROFILE%\.file-finder\searchCache.db` **一个文件**，拷它=导出。而"导入"= 用外部文件**覆盖全库**，**危险度高于所有扫描动作** —— 为极罕见场景引入最高危险动作，不划算。系统文件管理器复制自带回收站/撤销，比应用内做更安全 |

## 六、落地与实测（2026-09-24 晚 · 本节是**执行记录**，不是计划）

> 证据等级逐条标注：**静态**（可复算）／**实测**（真机复现，探针可重跑）／**推理**／**未验**。

### 6.1 P0 实际改了 **4 处**（比 §一 多 3 处，都是审查时新发现的）

| # | 位置 | 改动 | 为什么多出来 |
|---|---|---|---|
| 1 | `readFolder` 的 `readdir` 失败 | 抛错（原 `return []`） | §一 的核心动作 |
| 2 | `handleCover` 读取失败 | 返回 `null`（原 `[]`） | **新发现**：空数组是 **truthy**，调用方 `if (converged) { …; continue; }` 会把这个子目录**静默跳过 —— 连名字都不出现**，用户以为文件夹不存在 |
| 3 | `openFolderController` | 拆开 `!parts`（合法，只是不缓存）与 `!disk`（**报错**） | §一 §3 的落实 |
| 4 | 路由咽喉点 `route()` 替掉全部 `event.on` | 统一接住 async 抛错 | **新发现**：`event.emit` 是**同步调用**，async handler 抛错无人接 → unhandledRejection + **请求永久挂起**。不加这条，改动 1 会从"写坏数据"变成"页面永远转圈"，**越修越糟** |

### 6.2 P0 实测（A/B 对照 + 回归，探针可重跑）

**A/B 对照**（`out/before.cjs` vs `out/after-p1.cjs`，同一套判据）：

| 判据 | before（缺陷版） | after（修复版） |
|---|---|---|
| 请求 1 状态码（`noCache` 强制读盘） | `200` ← **对"读不到"报了成功** | `500` + `{"error":"读不到这个文件夹（EPERM）","kind":"unreadable"}` |
| 假记录 `count:5` 现状 | **被覆盖成 `count:0`** | **完好 `count:5`** |
| 请求 2 返回条目数 | `0` | `5` |
| 请求 2 是否碰盘 | 没碰（命中了那条空记录） | 没碰（命中了原记录） |

**回归（防"修过头"）**：

| 场景 | 期望 | 实测 |
|---|---|---|
| 真的空目录（能读、0 项） | `200` + 落盘 `count:0` | ✅ PASS |
| 普通目录（2 项） | `200` + 落盘 `count:2` | ✅ PASS |

**"读不到"的真实形态怎么造的**（静态可复算）：对夹具目录 `icacls /deny <user>:(RD)`
→ `fs.statSync` **成功**（存在、是目录）、`fs.readdirSync` 抛 `EPERM`。
这是"目录在、但这一层读不到"的真实形态，比造假数据可信。

### 6.3 P1 实际落地

| 项 | 改动 |
|---|---|
| 入口可发现性 | 「重扫这一片」从 `trigger="hover"` 下拉里**拿出来**，改成**两个平铺按钮** |
| 门槛 ∝ 风险 | **只**给「重读这一片」加 `n-popconfirm`；「补全这一片」「刷新」不弹 |
| 扫描期间 | 禁掉「刷新」（`scanning`）—— 它带 `noCache`，会和整片扫描叠成两路读盘 |
| 三态可区分 | 新增 `n-alert` 横幅（`offline` = warning / `unreadable` = error）；**不做 closable**（寿命由取数结果管，手动关掉会让"读不到"重新变回一片空白） |
| 命名 | 「补全缓存」→**补全这一片**；「重扫这一片」→**重读这一片**；**「刷新」不改名**（用户在用的词），只加 tooltip |
| 失败分类链路 | 服务端 `kind` 字段 → `route()` 透传 → `request.ts` 的 `ApiError.kind` |
| 状态单一真相 | `failKind` 为真源，`loadFailed` 改为 `computed` 派生（两个各自赋值的变量迟早不一致） |

**为什么失败分类不复用文案匹配**：`error.includes('现在不在')` 这类判别，服务端改一个字就**静默失效**、横幅说错话。分类进结构化字段，文案随便改。
（先例：`apiUrl()` 是唯一 URL 出口、`wire()` 是唯一下发出口、口令校验挂在唯一请求入口 —— 同一个"收成一个咽喉点"的思路。）

**我裁掉的一条**（UI/UX 方案提的）："扫描期间禁用**换目录**"——
换目录走 `fetchFolder`、**不带** `noCache`，不会"再叠一次强制读盘"，危害论证不成立，属过度防御。
**证据等级：推理。**（UI/UX 自己给的理由是"防止扫描期间再叠一次强制读盘"，而换目录不具备这个性质。）

### 6.5 P2 落地（用户要的"导入导出的交互"，按 §三 收成最小形态）

| 项 | 做法 |
|---|---|
| 入口 | 「缓存记录」面板里一个**文字链接**「打开存放文件夹」（挨着已有的「备份」） |
| 通道 | 新增 IPC `openDataDir` → `shell.openPath(config.userBasePath)` |
| 为什么不新建机制 | `shell.openPath` 对目录开资源管理器、对文件才用默认程序 —— 和已有的 `openFile` 是同一条路、同一个"成功空串 / 失败描述"约定 |

⚠️ **这一条的端到端未实测**（需真机点一次看资源管理器是否弹出）—— `shell.openPath` 的路径正确性由 `config.userBasePath` 保证（静态可复算），但"点下去真的有反应"要跑起来看。
