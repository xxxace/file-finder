## 一、先回答「加在哪」—— 只加**一个**地方：`readFolder`

**架构事实（逐行核过）**：

| 事实 | 位置 |
|---|---|
| 全项目**读一层目录**只有**一个**实现 | `readFolder()` `index.ts:217` |
| 全项目**写缓存**只有**一个**实现 | `scanAndCache()` `index.ts:666` |
| 四个入口**全部汇聚**到同一个咽喉 | `openFolderController()` `index.ts:701` |
| 全项目会产生**抽帧**（贵操作）的地方只有 **3 处** | 见 §二 |

**所以：不在入口加。**

```
 打开目录   F5 刷新   「补全这一片」  「重读这一片」
      \        |          |            /
       \       |          |           /
        ▼      ▼          ▼          ▼
        openFolderController      ← 唯一咽喉点（route → 它是唯一入口）
                │
                ▼
          scanAndCache            ← 唯一写入点（queueCacheWrite 的调用方）
                │
                ▼
           readFolder             ← 唯一读取点  ★ 闸门加在这里
                │
                ▼
        抽帧 ×3（唯一昂贵的地方）
```

- ❌ **在 4 个入口各加一道守卫 = 补丁** —— 责任在调用方，**将来新增第 5 个入口一忘就复活**
- ✅ **加在 `readFolder` = 修复** —— 责任在唯一的读取点，**新入口自动获得，结构上漏不掉**

**这跟项目里既有的三个先例是同一个设计思路**（不是我新发明的规矩）：
`wire()` 是唯一下发出口（`index.ts:544`）· `route()` 是唯一错误咽喉点（`:1231`）· `apiUrl()` 是唯一 URL 出口（渲染层）。

⇒ 所以答案是：**「触发刷新缓存的都要加」这个问法是错的** —— 加了就散；只加一处，全都自动有。

## 二、对账的实质：**不是复用整条记录，是复用那 3 张图**

逐行核过，全项目只有 3 处会抽帧（起 ffmpeg 子进程 / 解码整图）：

| # | 位置 | 抽什么 |
|---|---|---|
| 1 | `readFolder:287` `makeThumb(filepath, ext)` | 图片 / 视频的缩略图 |
| 2 | `makeDirCover:203` `makeThumb(filepath, 'jpg')` | 目录自己的脸（`avatar.jpg` / `cover.jpg`） |
| 3 | `handleCover:410` `makeThumb(filepath, ext)` | 收敛条目的封面 |

⇒ **对账 = 这 3 处在「源文件没变」时，直接复用上次那张 base64。**

**为什么不做「整条记录复用」**：那个抽象太大、太脆 —— 父层的条目会被子目录的收敛形态改变
（`dir` 指向子目录、`name` 是封面名），按名字对账会对不上。而**按"源文件的盘内路径"对账，键空间天然一致**：

| 条目 | `dir` | `name` | 反推出的源路径 |
|---|---|---|---|
| 普通文件 | 当前层 | 文件名（无扩展） | `当前层/文件名.jpg` ✓ |
| 收敛封面 | **子目录路径** | 封面文件名 | `子目录/封面.jpg` ✓ |
| 目录的脸 | 当前层 | 目录名 | `当前层/目录名` ✓ |

⇒ **一个 Map 就能覆盖三种情形**，键 = `joinRel(item.dir, diskNameOf(item))`
（`diskNameOf` 已存在，`index.ts:525` —— **直接复用，不新造**）。

## 三、复用判据（一份实现，3 处共用）

```ts
/**
 * 缩略图复用闸门 —— 抽帧前的**唯一**判据。
 * 上一次那条记录还在、且源文件没变 ⇒ 那张图仍然有效，不必重抽。
 */
function reusable(prev: Map<string, FileInfo> | undefined, srcRel: string): FileInfo | undefined {
    return prev?.get(srcRel);
}
```

三处各自的附加条件（语义不同，所以条件不同）：

| # | 键 | 附加条件 | 为什么 |
|---|---|---|---|
| 1 文件 | `当前层/全名` | `hit.size === stat.size` | 同名**同大小**才算没变；换了内容大小通常变 |
| 2 目录的脸 | `当前层/目录名` | `hit.avatarSrc === 命中的文件名` | 上次的脸可能来自 `avatar.jpg`、这次是 `cover.jpg` ⇒ 必须确认是同一个源 |
| 3 收敛封面 | `子目录/封面名` | 无（键本身就是那个源文件路径） | 记录里的 `size` 是整组之和，**不是封面图大小**，不能拿来比 |

⚠️ 第 2 条需要给 `FileInfo` **加一个字段 `avatarSrc?: string`**（记录"这张脸来自哪个文件名"）。
- 它**只存不发** —— `pickFileInfo()`（`index.ts:491`）是白名单，不含它 ⇒ 不会污染下发 JSON ✓
- 旧记录没有这个字段 ⇒ 视为不复用 ⇒ 重抽一次并写入 ⇒ **不需要升 `CACHE_VERSION`** ✓

## 四、改动清单（**5 个函数，约 25 行，零入口改动、零前端改动**）

## 五、每个入口改完之后的行为（**不改特性**）

| 入口 | 现在 | 改后 | 是否动特性 |
|---|---|---|---|
| 打开**已缓存**目录 | 0 读盘（`findCache` 短路） | **一样**（`cached ??` 那一支没变） | ❌ 没动 |
| 打开**未缓存**目录 | 全量 | **一样**（prev 为空 ⇒ 全量） | ❌ 没动 |
| **F5 / 刷新当前层** | 整层全量：100 stat + **100 抽帧** | 对账：`readdir` + stat + **0~2 抽帧** | ❌ 没动（**结果一样，只是快**） |
| **「重读这一片」** | 整片每层全量 | 整片每层对账 | ❌ 没动（同上） |
| **「补全这一片」** | 命中缓存就**只回缓存、完全不碰盘** | **完全一样**（它压根不调 `scanAndCache`） | ❌ 没动 |

**⚠️ 关于「补全这一片」—— 我不建议动它，理由**：
它的已批准语义就是"**有缓存就跳过、不读盘**"。改成对账 = 每次都要 `readdir` 已缓存目录
⇒ 直接违背它当初被批准的那条性质。**新增文件的收录交给 F5（单层）和「重读这一片」（整片）就够了。**

**另外**：`noCache=true` 仍然是"**不信缓存、去看盘上现在是什么**"—— 对账**确实重新读了盘**
（`readdir` 是真实读盘），只是复用了没变的缩略图。⇒ 语义**没有变**，只是不浪费了。

## 六、为什么这不是"打补丁 / 面条代码"

| 判据 | 本方案 |
|---|---|
| **同类场景会不会复发？** | 不会 —— 闸门在**唯一读取点**，任何新入口（包括将来的）自动获得 |
| **有没有给每个调用方各加守卫？** | 没有 —— 只有 `readFolder` 一处建索引，3 个抽帧点共用**同一个判据函数** |
| **有没有新造机制？** | 没有 —— 复用 `findCache` / `diskNameOf` / `pickFileInfo` 白名单 / `wire()` 的重新登记 |
| **有没有引入新依赖 / 新存储** | 没有。加 1 个"只存不发"的字段，**不升 `CACHE_VERSION`** |
| **有没有破坏既有特性** | 没有。§五 逐条列了"结果不变" |

**唯一净新增的读盘**：对已缓存目录多做 **1 次 `readdir`**（目录元数据；本机实测 489 项 < 1 ms）。这是本方案的全部代价。
