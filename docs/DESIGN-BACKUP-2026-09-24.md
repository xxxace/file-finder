## 一、先把术语改对（用户 18:34 指出：「你这是替换不是导入吧？」）

| 词 | 实际语义 | 现状 |
|---|---|---|
| **替换** | 外部文件**整份顶掉**当前库，原来的全没了 | 当前唯一能力 |
| **合并**（= 真"导入"） | 两份都保留，按主键并起来 | **做不到** |
| **备份 / 还原** | 这套动作的**准名** —— 「导出」通常指"生成一个专门的导出文件"，而现在只是让你拷内部数据文件 | 建议全面改口 |

**这不是抠字眼**：叫"导入"会让人以为能"补充/挑选"，而实际是**整体顶掉**。
§6.5 那个「打开存放文件夹」链接旁边若写"导入"，就是这个坑。

## 二、技术验证：nedb 能不能加密（**实测**）

`@seald-io/nedb` 4.1.2 **官方支持**加密钩子，源码注释（`datastore.js:128-130`）原话：

> The `beforeDeserialization` and `afterSerialization` callbacks are hooks … **They can be used for example to encrypt the Datastore.**

探针：`%TEMP%/ff-enc-probe/probe.cjs`（隔离目录，不碰真库，可重跑）。

| 判据 | 结果 |
|---|---|
| **A** 写入后文件是否人不可读 | ✅ 全 base64 密文，**看不到任何明文关键词** |
| **B** 重新加载能否原样读回 | ✅ 3 条读回、`relPath` 复原、按 `serial` 查得到 |
| **C** 元数据行 / 墓碑行 | ✅ 都走钩子 —— **删除操作不会把明文写回去** |
| **D** **密钥不对**时 | ⚠️ `loadDatabase` 回调报 "100% of the data file is corrupt"，**但之后所有查询永久挂起**（3s 无响应） |

### ⚠️ 判据 D 是本次最要紧的发现

错密钥的后果**不是"打不开"，是"打不开 + 之后每个请求永久卡死"**。
而现有代码 `nedb.ts:81-83` 对 `loadDatabase` 的 err **只打了日志、没有处理**：

```ts
nedb.loadDatabase((err) => {
    if (err) console.error('[nedb] 缓存库载入失败:', err);   // ← 就这一句
});
```

→ **加密的前置条件是先把这个补上**（否则密钥/文件一不对，界面直接卡死）。
这同时也是**既有缺陷**（memory 已记："库损坏 >10% → executor.ready 永假 → 所有请求永久挂起"），
只是加密会让它更容易被触发。

## 三、旧明文库怎么迁移 —— **零代码**（静态确认，两处源码交叉）

1. `persistence.js:308-341` 的 `loadDatabaseAsync()` **末尾无条件**调用
   `this.db.persistence.persistCachedDatabaseAsync()`。
   JSDoc 原话：「all data is persisted right away, which has the effect of
   **compacting the database file**」（顺带说明"启动时本来就会整库重写压缩"）
2. 写盘路径**每个 doc** 都过钩子：`persistence.js:98`（全量）与 `:158`（增量 append）

→ 只要 `beforeDeserialization` **兼容明文行**，**启动一次就自动整库重写为密文**。
**不需要迁移代码、不需要手工转换。**

**怎么区分"明文行"和"密文行"**：
- 明文行以 `{` 开头；
- 而 base64 字符集是 `A-Za-z0-9+/=`，**不含 `{`** → 判据清晰、不会误判。
- 顺带：nedb 自带 `testSerializationHooks` 逆运算自检测的是 `dec(enc(x)) === x`，
  而 `enc` 输出一定是 base64（不含 `{`）→ 走解密分支 → 自检照样通过。**静态推理，未实测。**

## 四、三个功能

### 4.1 本机库加密（直接命中"防一眼看到"）

| 项 | 决定 |
|---|---|
| 算法 | `node:crypto` **AES-256-CBC + base64**，**零新依赖** |
| IV | **固定** —— 必须是**确定性加密**，否则同一个 `relPath` 每次密文不同、索引和查询都会失效 |
| 密钥 | **应用内固定常量**（从字符串 sha256 派生） |
| 改动量 | `nedb.ts` 约 20 行（两个钩子 + 常量） |
| 体积 | **+33%**（8.2 MB → ~11 MB），且密文**不可压缩** |
| 启动开销 | ~500 条要逐行解密 + 整库重写一次；nedb 自己标称 10k docs 60ms → **推理**：百毫秒量级，**未实测** |

⚠️ **诚实边界（必须写进代码注释，也不能对外宣称"安全"）**：
**固定密钥 = 混淆级别**。它防的是"随手打开"，**不防有心人** —— 解包挖源码能拿到密钥。
用户的诉求正是"防一眼看到"，**恰好匹配**；但不能把它当成真安全。

⚠️ **密钥永不可改**：改了 = 旧库全废。这正是旧裁决担心的"改口令 = 旧文件全废"的契约，
只不过我们把它简化成"密钥写死、永不更改"（在代码里注明，防止以后有人"顺手换个 key"）。

### 4.2 备份到文件 / 从文件还原（应用内按钮）

| 动作 | 实现 |
|---|---|
| 备份到文件… | `dialog.showSaveDialog` → 复制主库 → 用户选的位置 |
| 从文件还原… | `dialog.showOpenDialog` → **先自动备份当前库**（专用槽位）→ 覆盖主库 → **就地重新加载**（`loadDatabase` 再来一遍） |

**为什么还原之后必须"重新加载"**（实测支撑）：
nedb 启动时整库读进内存，**运行时内存才是真相源**；而且实测
**运行中主库文件没有独占锁**（`r+` 能打开）→ 覆盖面**不会报错**，
会被内存态**静默冲掉**。所以光复制文件是不够的。

> ⚠️ **本节第一版（原文）写的是「必须 `app.relaunch()` 重启」，已被实测推翻。**
> 探针 `%TEMP%/ff-enc-probe/reload.cjs`（6/6 PASS）证明：**二次 `loadDatabase` 完全可用** ——
> 重读后内存内容 = 新文件内容、executor 不会变僵尸、坏文件会报错且不改写、把好文件放回去能恢复。
> 所以改成**就地重载**，理由不只是"更省事"：
> `app.relaunch()` 在 dev 下本来就不可靠（进程是 vite-plugin-electron 起的），
> 重启方案会在开发时表现成"点一下就没了"。**能重载就不要重启。**

**为什么必须先自动备份当前库**：还原 = 不可逆的整体覆盖。
且 `cacheBackup()` 是**同名覆盖**（`searchCache-YYYYMMDD.db`，同一天互相盖），
所以快照要用**独立槽位**：`searchCache-before-restore.db`，不能借用日常备份名。

**还原失败要能回滚**：这是唯一会"让记录消失"的动作，所以覆盖前一定先留快照，
失败就把快照复制回去、再重载一次。回滚也失败时不继续挣扎 —— 那时 `loadError` 已挂着，
`assertUsable` 会让所有请求响亮报错，而不是拿一份半坏的内存态继续对外服务。

### 4.3 合并两份缓存（用户说"两者都要"）

| 项 | 决定 |
|---|---|
| 规则 | 按 `(serial, relPath, mode)` 比；本地没有就补；都有就取 `create_at` 新的 |
| 版本 | 只并 `v === CACHE_VERSION` —— 版本不同的记录形状就不对，并进来是污染 |
| 写入口 | 每一条都走 `queueCacheWrite`（和 `scanAndCache` **同一条链**），先删后插 |
| 只读性 | 读的是**临时副本**：`loadDatabase` 会整库重写，直接在用户的备份文件上 load 等于改了它，只读介质还会直接失败 |
| 成本 | 最高、频率最低（真实场景：两台机器各扫了一半的盘） |

**与「还原」的分界（这两个词必须分清）**：

| | 还原 | 合并 |
|---|---|---|
| 本机独有的记录 | **消失** | 保留 |
| 可撤销性 | 有（快照 + 自动回滚） | 无（只增不删） |
| 二次确认 | **要** | 不要 |

### 7.5 判据 D：启动开销（**实测**，机制未定位）

`%TEMP%/ff-enc-probe/{timing,matrix,synth,reload}.cjs`，同进程、交替顺序、3~6 轮取中位：

| 场景 | 耗时 |
|---|---|
| **升级前**：明文库加载（也是今天线上的路径） | **~1300 ms** |
| **升级后第一次**：明文进 → 密文出（迁移那一次） | ~612 ms |
| **之后每次**：密文进 → 密文出 | **~150 ms** |

纯 AES 成本可忽略：加密 8.6 MB 一轮 **21 ms**、加解密一轮 37 ms。

**结论（站得住的部分）**：加密**没有引入启动代价**。
**未站得住的部分**：为什么明文加载反而慢 8 倍，**机制没定位**，不当作"加密的性能优势"来宣称。
做过的排除（都能复现）：不是 fsync（`fs.writeFileSync`+fsync 两组都 2–5 ms）、不是体积、
不是内容字符集（换成合成库 + 中文名都只有 84–130 ms）、不是顺序（交替跑结论不变）、
不是 `copyFileSync`（`plain-nocopy` 也慢）。差异只出现在 **nedb 那条 stream 写盘路径**上。
