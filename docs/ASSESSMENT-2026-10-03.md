### ❌ 已撤回：上一版里的「修 `npm install`」

**我上轮把它排第 1，这个判断是错的，撤回。**
主人 2026-10-03 反馈「可以跑啊我都跑完了」⇒ 复查后确认：

- `node_modules/app-builder-bin` **确实不存在**（只剩 `.app-builder-bin-YaNL61c1` 暂存目录），
  但那个目录是 **2022-09-12 的 v4.0.0 旧版残留**（`stat` 实测 mtime = 2022-09-12）。
- `electron-builder@26.15.3` 的依赖表里**没有** `app-builder-bin`；
  全库 `grep "require('app-builder-bin')"` = **0 处真 require**（只有 `certInfo.js:321`、`yarn.js:146` 两处**注释**提到它）。
- ⇒ **它跟打包失败没有因果关系**。我上轮把"两件事同时发生"读成了"因果"，是典型的相关当因果。

**教训（血泪，值得进 MEMORY）**：
"某依赖缺失" + "打包失败" 同时出现 ⇒ 不等于"依赖缺失导致打包失败"。
`node_modules` 里大量**旧版本残留目录**（带 `.` 前缀的 npm 暂存目录）天然会缺，
**必须 grep 真实 `require` 再判因果**，不能看 `ls` 结果下结论。证据等级：静态+实测（`stat` + `grep` 双证）。

## 四、❌ 撤回：「升维成内容库」——我上轮的头号建议，错了

**这一节整条撤回。** 主人 2026-10-03 两个反问（"都是本地的"、"多个盘有同一部怎么办"）都成立，
且我随后用实测数据验证了我的建议**解决的是一个不存在的问题**。

### 撤回理由一：跨盘聚合的收益是 0（实测）

探针 `docs/probes/dup-scan/`（读缓存库，**不读盘**；输出已脱敏，见 `out.txt`）：

| 指标 | 实测值 |
|---|---|
| 缓存记录 | 208 条 / 1202 条目 / 4 块盘（序列号后4位 `9870` `DC72` `C6EE` `EBFC`） |
| 不同**视频条目名** | 166 个 |
| **跨盘出现的视频条目名** | **0 个 = 0.0%** |
| 不同目录名 | 180 个，跨盘 28 个 = 15.6% |
| 那 28 个是什么 | 1 个容器名（`videos`）+ 27 个**作品名形态的目录**（演员名/番号名，真名已脱敏） |

**结论**：主人的组织方式里，**同一部作品的文件从不跨盘分散** ——
视频条目跨盘重复率精确为 0。跨盘重复只发生在**目录名**层面（同名演员的多个作品各自在单盘里），
这不构成"一部作品散在多盘"。

> ⚠️ 我第一版把这 28 个目录说成"全是容器层、不是作品" —— **不准确**（实测只有 1 个是容器名）。
> 但**结论不变**：判据是**视频条目跨盘重复 = 0%**，那才是"一部作品是否分散"的直接证据。


### 撤回理由二：「多个盘有同一部」不需要新机制，它已经是这么处理的

主人原话：「这种本来就是可能发生的事情，程序没限制就是允许，有什么好浪费时间去确认的」。

**这句话是对的，而且现有设计已经对**：
`/resolveAnchor` —— 每次打开只读条目，都**在动作那一刻**问服务端要完整路径；
盘不在就不给开、给的是"离线"状态。**它从一开始就是"多盘同一部"的正解**：
不聚合、不合并、不建索引，只在**用的时候**按事实回答。

我要提的"作品 → 多位置的一对多映射 + 同番号不同版本处理"是一个**索引引擎**，
而 `resolveAnchor` 是**一次询问**。为了一个零发生的场景引入前者，是拿数据库的力气解不存在的问题。
⇒ **技术上成立 ≠ 该做。**

### 撤回理由三：番号当主键，我没说清它的真实代价

`parseTitle` 的结果目前只喂给抓封面，用完就扔。想把它升成主键，就得面对：
同番号不同版本（BD/无码/合集）、同番号在多盘的版本差异、部分源缺失时的展示语义。
这是**一对多 + 弱匹配**，不是一个字段。

**主人自己的库里有多少？跨盘视频重复 0 个。** 收益 0，成本是一个索引引擎。

### 那"超前"到底在哪？

**诚实回答：对这个应用，"超前"不是个有意义的词。**
它是**单机 · 本地 · 移动硬盘 · 5 块盘 1202 条目**的工具。
- 云同步 = 它不是云产品（主人已明确）
- 语义检索 = 1202 条目用不上向量库，且要引入模型运行时（最大新增依赖）
- 自动更新 = 单机自用，手动换 exe 够用
- 盘舰队看板 = 主人已定「短期不做」

**真要"领先"，只有一个方向是它独有的：**
> **在不读盘的前提下，把"盘的状态"讲清楚。**

现在这个应用**不知道**（而这些全部零读盘，数据都在 nedb 内存里，`loadSubtreeBytes` 已证明子树聚合中位 0.84 ms）：

| 能力 | 现在的状态 | 读盘代价 |
|---|---|---|
| 「这部作品只在 E 盘，拔了就永久没了」 | **不知道** | 零（`serial` + `relPath` 全在库里） |
| 「每块盘各存了什么类型/体积/年份」 | **不知道** | 零（同上） |
| 「E 盘上次扫描是 3 天前」 | 只有缓存记录表里的 `create_at`，无显式呈现 | 零 |
| 「哪些目录扫过很多次、扫得慢」 | **不知道** | 零（但要看扫描耗时，`ffprobe` 那条是唯一有代价的） |

**这一条是真差异化**：别的文件管理器要么读盘去算，要么压根不管盘。
`driveIdentity.ts` 已经认得每块盘的序列号 —— **身份已经在了，缺的是"拿身份做统计"这一步。**

**成本**：小到中（纯内存聚合，复用 `loadSubtreeBytes` 的出口）。
**为什么不排第 1**：它的价值随盘数增长而增长，现在 5 块盘还没到"必须"的临界。
