# 顶栏升级方案（2026-11-08）

> 一轮完整访谈后的定稿。**所有尺寸单位 = 逻辑 px**；证据等级标在每条后面：`[静态]` 读代码得出、`[推理]` 算术/推导、`[外部]` 参考 Windows / Chrome / macOS 实测值。

## 一、结论：一条 44px 的行，三段式

```
[▤] [←] [↻] │ [ 盘: › videos › 某作品名 › 当前段 ⑫ ]        │ [⌕] [▦] [⊞] | [⋯]
   导航箭头组    ↑ 地址槽（唯一弹性槽，吃掉全部剩余宽度）        搜索  视图组     更多
```

- 顶栏高度 **44px 不变**（主人裁决：能一行就不两行，高度占用越小越好）。
- **全部控件 28×28**，图标 16px（`ionicons5` outline，主人裁决不换族）。
- 地址槽高 **30px**（比按钮高 2px，视觉上"这是一个面"而不是"一颗按钮"）。

| 元素 | 尺寸 | 备注 |
|---|---|---|
| 文件夹按钮 | 28×28 | 内含 16px **彩色**文件夹 PNG（保留） |
| 返回 / 清空 | 28×28 | `←` / `⨯` |
| 刷新 | 28×28 | `↻` |
| 地址槽 | h30, flex:1, radius 7 | `1px --ff-line`，`padding: 0 8px` |
| 段 | padding 2/6, radius 5 | **无描边**，hover 出 `--ff-ctl-hover` |
| 当前段 | 同上 | `--ff-text-1`，**font-weight 400**（见 §五） |
| 角标 | 48px 常驻槽 | 槽的 `padding-right` |
| 搜索 | 28 收起 / 220×28 展开 | `⌕` ⇄ 输入框 |
| 视图组 | 28 + 28, gap 4 | 密度 / 平铺 |
| 更多 | 28 | 竖线 `1×16 --ff-line-strong` 与视图组隔开 |

## 二、七条改动

1. **文件夹选择器 → 纯图标**（保留彩色 PNG）。选根后图标加一个小底色点表示"已设起点"；完整路径进 `title`。
2. **返回 / 清空 → 图标**。`history.length > 1` 是 `←`；栈底是 `⨯`（清空视图）。同一个 28px 方格，**字形不同、盒子不变**，比原来"两个都是两字的词"更强的宽度保证。
3. **返回常驻、初始置灰**。原来是 `v-if="history.length"`，首次导航时按钮出现会把整条面包屑推 60px 左右 —— 改图标后顺手修掉这类跳动。
4. **刷新从右侧动作区移到左侧导航区**，紧跟返回。跟 Chrome / Explorer 同构：`[←][→][↻][地址栏]` `[外部]`。语义也对得上 —— 它重读的是**当前这个位置**。
5. **面包屑段去描边、收进一条槽**。视觉层改造：外层 `.nav-zone` 加一条 `1px --ff-line` 的连续槽，段自己不再画边框，hover 才出底色。**节点结构、key、TransitionGroup 全部不动** ⇒ 11-08 那套零位移动效不受影响。
6. **搜索 260 常驻 → 28 图标，点或按 `S` 展开成 220**，Esc / 失焦收起（主人裁决：挤压地址栏取空间，不做浮层）。
7. **「更多」从最左移到最右**。它是兜底入口，永远在末端（Chrome `⋮`、Explorer `⋯` 同理）。

## 三、宽度账（为什么"挤压地址栏"是安全的）[推理]

窗口 1024 时可用宽度 = 1024 − 64（左轨）− 2×18（inset）= **924**。

| | 今天 | 新版收起 | 新版展开 |
|---|---|---|---|
| 左固定 | 文件夹 chip ≤150 + 返回 60 | 3×28 + 3×6 = **102** | 102 |
| 右固定 | ⋯ + 搜索260 + 3×28 + gap = **~420** | 4×28 + gaps + 分隔 ≈ **137** | 137 |
| 地址可用 | ≤ 492 | **≈ 673** | **≈ 481** |

⇒ 收起态面包屑多了 **+181px**；**展开态仍比今天宽 ~0**（481 vs 492，略窄 11px，肉眼无差）。
⇒ 不存在"比现状更挤"的状态，所以不会复现 `foldCrumbList` 注释里记的那个"末段被压到 22px"。

**折叠不会因为挤压而触发** [静态]：`foldCrumbList(crumbs, max = 4)` 判据是**段数**，不看宽度。挤压只让段内文字缩短/省略，不会引起整排重新折叠。

## 四、不动的东西（神圣清单）

- `--ff-header-h: 44px`、通栏直角、纯色 `--ff-chrome-bg`、**不画底边线**。
- 面包屑折叠 `max = 4`（保首段 + `…` + 当前段）、`crumbRows.ts` 的三段渲染、`pinLeaving` 退场抄 rect。
- 当前段**不加 `font-weight: 500`**（第七轮实测：加���是唯一会让字形重画的东西）。
- 角标仍是红底白字胶囊、`::after` + `attr()` 挂盒子外侧、`left: 100%`。
- galaxy 顶部进度条、网格密度三档、`.toolbar{flex-wrap:nowrap}`。

## 五、实现要点与坑

1. **`.header-bar .n-input { width: 260px }` 不能整条删。** n-input 天生 `width:100%`，删了它会撑满整行、把工具条顶成多行（2026-09-24 事故）。新版改成"展开态 220px + 收起态不渲染"。
2. **`.nav-zone` 的 `max-width: calc(50% + 48px)` 必须重算。** 那个 50% 预算是按"右侧 420px"定的；右侧已经降到 137px，还写 50% 会把地址槽卡在一半。
3. **角标槽 48px 从 `.nav-zone` 的 `padding-right` 下移到内层槽的 `padding-right`。** 不变量保持：当前段左右边距不随角标有无/位数变化。
4. **段去描边后 `--crumb-gap` 可从 12 降到 8**，`::before` 的 `›` 盒子同步（它依赖 gap，改一处即可）。
5. **搜索展开/收起 200ms**，只过渡 `width`；兄弟节点靠 flex 自动跟随，不需要逐个写 transition。
6. **图标 16px 是起点值，需目视校准**：ionicons5 是 24 viewBox，缩到 16 会让描边变细一档；若偏细改 18。
7. **刷新移到左侧后禁用逻辑不变**（`scanning || readOnlyLevel || playlistLevel`）。

**本轮推翻的旧裁决**（主人已在此对话中同意）：返回/清空从"两个同宽的中文词"改为"同盒不同字形"；文件夹从彩色 chip 降为彩色图标；搜索从常驻 260 改为图标展开。

## 六、验收清单

- [ ] 1024 窄窗：地址槽仍 ≥ 400，末段不被压到 22px
- [ ] 搜索展开/收起：面包屑不折叠、不出现整排重排
- [ ] 换层（`F: › videos` → `F: › videos › a`）：面包屑零位移（复用 `docs/probes/crumb-motion/`）
- [ ] 栈底：`←` 变 `⨯`，按钮宽度一个像素不变
- [ ] 首次导航：返回按钮不出现位移（常驻置灰）
- [ ] 扫描期间：刷新置灰、更多置灰
- [ ] `typecheck` 0 error；`docs/probes/tokens/no-raw-color.mjs` 通过

## 七、实现记录（2026-11-08，写完代码后补）

改动文件：`src/views/FileFinder/index.vue`（模板头部 + `.header-bar` / `.nav-zone` / `.toolbar` 样式 + 脚本）、
`src/components/FolderSelector/index.vue`（重写为图标态）、`src/views/FileFinder/GridDensityMenu.vue`（去文字、加激活态）。
`typecheck` 0 error、`vite build` 通过、`no-raw-color` 探针 PASS。

**与原方案的六处偏差**（都是落地时才发现的事实，不是临时改主意）：

1. **面包屑本来就没有描边** —— 2026-11-08 上午已经改成"只留文字"（`--n-border: transparent`）。
   所以"去描边"不是本次新增的工作；本次真正加的是**外层那条槽**。下划线 hover 改成了圆角底色。
2. **槽用填充而不是描边**：`background: var(--ff-field)`、不画线。
   理由：顶栏里六颗图标按钮都是无框的，这里再出现一个描边矩形会被读成"贴歪的框"；
   而 `--ff-field` 是唯一明暗两个主题都调过的那一档（浅差 17 / 深差 18）。
3. **段 hover 色必须用 `--ff-ctl-on`、不能用 `--ff-ctl-hover`**：
   深色下 `--ff-ctl-hover`(#313131) **正好等于** `--ff-field`(#313131) ⇒ 悬停零变化。
   这是"同一块面上再叠一层"特有的坑，按钮之间不会遇到。
4. **`.suffix-key`（输入框里的 `S` 键帽）删掉了** —— 收起态没有框，键帽无处可放；
   改由搜索图标按钮的 tooltip 带「搜索（S）」。同时删掉那段 18 行 kbd 样式。
5. **密度按钮去文字后靠激活态表达档位**：偏离默认档（宽松）才亮底色（`.is-on`）。
   原注释"纯图标看不出当前档"这个顾虑仍然成立，只是改用按钮自身回答。
6. **`pinLeaving` 多减了一次边框宽**：绝对定位的坐标系是 padding box，而
   `getBoundingClientRect()` 给 border box —— 槽一旦有边框，幽灵会偏 1px。本次最终没画边框
   （值为 0），代码保留，因为它防的是"哪天补回 1px"。

**踩到的真坑（写进注释了）**：Less 里 `.is-open &` 展开的是**累计选择器**
（`.toolbar .search-btn`）⇒ 编译成 `.is-open .toolbar .search-btn`，祖先顺序反了、规则**静默失效**。
第一版就是这么错的，靠翻 `dist` 里的编译产物抓到 —— 这类错误 `typecheck` 和 `vite build` 都不会报。

## 八、地址槽内部的**光学居中**（同日第二轮，主人："我要视觉对齐"）

判据不是"盒子居中"，是**每块墨迹的重心落在槽中线上**。工具：`docs/probes/header-optical/measure.mjs`
（截图 → 逐行中位亮度找槽 → 逐列聚墨迹 → 亮度加权重心，直接打偏移量，超容差退 1）。

实测基线（314×63 截图，DPR 1.25，暗色；槽 y 14..50、中线 32.00）：

| 墨迹块 | 重心 | 与中线差（物理 / 逻辑） | 处理 |
|---|---|---|---|
| 汉字「新建文件夹」 | 31.64 | −0.36 / −0.29 | 不动（本来就在线上） |
| `›` 分隔符 | 33.51 | **+1.51 / +1.21** | 加 `--crumb-sep-dy: -1.2px` |
| 红角标胶囊 | 35.62 | **+3.62 / +2.89** | 删掉 `+ 2.8px` |

两处偏差**性质完全不同**，修法也不同：

1. **红角标**：代码里 `translateY(calc(-50% + 2.8px))` 的 2.8 是按**拉丁字母 x-height 带**
   调的补偿（字母小写主体偏下）。可这里地址永远是中文，汉字墨迹几乎填满字身框、
   重心就在行盒中心 ⇒ 那个补偿在中文上纯属"压低"。**删掉即正确**（结构性问题，改假设）。
2. **`›`**：字体把这个字形画在字身框偏下的位置 ⇒ "行盒居中"只让**盒**居中、墨迹仍低。
   这不是布局错，是字形度量差，CSS 没有原语可修 ⇒ **按实测做光学补偿**，
   值放在一个具名变量里、依据写在旁边（换字体栈要重量）。

**唯一没做的**：折叠占位 `…`（U+2026）。它画在基线上，同样会偏低，但当前路径不够深、
截图里没有它 ⇒ **没有实测就不猜数**。它出现时再量一次，或改成 CSS 画的三个点
（几何居中、与字体无关）—— 后者是根治，但要动模板，等他点头。

## 九、进度效果搬进地址槽（同日第三轮）

主人："先隐藏 `n-loading-bar`（不移除，仅关掉），我想将效果用到地址栏的盒子中，占满整个盒子"。

- **`n-loading-bar` 保留、只关**：`App.vue` 的 `container-style` 加 `visibility: hidden`。
  ⚠️ **不能用 `display:none` / `height: 0`** —— 地址槽那一层仍以它的实际宽度当进度真相源
  （`rect.width ÷ 容器宽 = 比例`），而 `display:none` 会让 `getBoundingClientRect()` 全归零。
  `visibility` 不改布局 ⇒ 尺寸照常读得到，字面意义上的"只是看不见"。
  退路：去掉 `visibility` 就回到顶部轨道（像素层仍在，只是不再挂在那里）。
- **像素层改成铺满自己的父盒子**：几何从"窗口宽 × `--ff-bar-h`"变成"父盒子实际尺寸 × 100%"
  （`position:absolute; inset:0; border-radius:inherit`），进度仍是 `比例 × 盒宽`。
  `draw.ts` 一个常数都没动 —— 逐格相位、左疏右密、三层辉光、放射粒子仍是唯一实现。
- **地址槽拆成两层**：`.nav-zone`（面：底 + 圆角 + padding + 角标槽）套 `.crumbs`
  （`TransitionGroup` 本体：flex + gap + `z-index:1`）。
  为什么必须拆：画布要铺满整条槽，而 `TransitionGroup` 的子节点必须带 key、还会被 FLIP 挪动
  ⇒ 画布不能当它的兄弟。**类名仍叫 `.nav-zone`**，非 scoped 块的 10 处 `.nav-zone .fx-*`
  靠后代关系继续命中，一处不用改。
- 画布自己的尺寸用 `ResizeObserver` 盯父盒子 —— 搜索展开/收起会把槽收窄，
  那时 backing store 必须重建，否则点阵会被 CSS 拉伸成一片糊。
- `pad: 0`：盒子外面是别人的地盘（会被槽的 `overflow: hidden` 裁掉），不留扩散余量。
- **底色紫渐变要自己画**（同日第四轮，主人："底色的紫色渐变色呢？怎么取消了？"）：
  那层是 naive 的 `colorLoading`（`--ff-bar-base`），bar 一藏就跟着不可见；像素层原先只画星点
  ⇒ 看着像"渐变被取消了"。现在 `draw.ts` 加 `drawBase()`，坐标系与 naive 一致
  （`0 → 当前进度宽度`，元素变宽渐变被拉伸）。`--ff-bar-base` 为此**拆成两个色标**
  `-from` / `-to`（canvas 的 `createLinearGradient` 只吃颜色、不吃 CSS 渐变串），
  CSS 那条由它们拼出来，六位十六进制不写第二遍。
- **没有最小开启阈值**（主人："不用等到 30%，0% 或 10% 就开启"）：判据就是 `ratio > 0`。
  之前那段"看不出在加载"的死区是**自然的**——底色没人画、星点又"左疏"，两个原因叠起来。
  底色从 0 就跟着画之后，这个死区就不存在了。
- ⚠️ **风险（未实测）**：底色是**不随主题变**的深靛（token 注释里就是这么定的）。
  深色主题下白字压上去没问题；**浅色主题下深灰字压在深靛上会看不清**。
  他没有在浅色下看过，先按他要求实现；如果确认难看，改法有两条：底色按主题给透明度，
  或让底色只铺盒子下半截（读作"文字脚下的一条进度"）。
