# cursor-ux3 · 三条体验反馈的判定（纯逻辑）

```bash
node docs/probes/cursor-ux3/run.mjs
```

**46 PASS / 0 FAIL。** 与 `grid-cursor/`（55/0）一起守住 `stepPos` 的行为。

## 验什么：业主 2026-10-04 四次报的三条

| # | 原话 | 定位 |
|---|---|---|
| 1 | 「进别的目录再回来，焦点默认回到了第一个 / 没记住」 | `useGridCursor` 的指纹 watch **无条件** `activateCursor` ⇒ 覆盖 `onBack` 恢复的 key；且 `onBack` **缺 `noteIntent()`** |
| 2 | 「到第一行和最后一行都不会到顶和到底」 | `block:'nearest'` 只管"这一格看得见吗" ⇒ 首/末行已可见 ⇒ 不滚 |
| 3 | 「`[[12345][1234]]` 在五按下没反应，应该切到第二行的 4」 | `stepPos` 上下**列号硬不变** ⇒ 落到不存在的列就停住 |

## 第 3 条是「设计错了」，不是「没考虑到」

原 `stepPos` 注释写着：
> 「残行上按 ↓ 落到不存在的列就**停住**……那会让『↓ 是往下』这个直觉在末行失效。」

⚠️ **这条理由只看了"最后一行"**，漏了残行可以出现在**任何位置**：
搜索过滤后、封面收敛后、任何数量非列数整数倍的数据。
一旦残行在中间，"按 ↓ 停住"就变成**在网格中间卡死** ——
用户按 ↓ 看到焦点不动，**会以为程序坏了**，而下面明明有格子。

**真正的失败不是"挪到了行尾"，而是"停在原地"** ——
「↓ 是往下」要求的恰恰是**焦点确实往下走了**。

### 正解：目标行存在就投影（clamp）

```
目标行存在 ⇒ 列号取 min(当前列, 目标行长度 − 1)
目标行不存在（已在最后一行）⇒ 停住   ← 这才是真正的边界
```

## 枚举判据（X2，40 个位置逐个比对）

| 残行位置 | 修复前 | 修复后 |
|---|---|---|
| 末行（总数非 6 倍数）| `c=4/c=5` 按 ↓ **停住** | 落到末行末格 |
| **残行在中间**（搜索过滤后）| `c=2..5` 按 ↓ **停住** | 落到短行末格 |
| ↑ 方向 | 同样卡住 | 同样投影 |
| 末行/首行 | 停住 | **停住不变**（真边界不能被投影吃掉）|
| ← → | 停住 | **停住不变**（横向越界是"这一行到头了"，语义与纵向不同）|

⚠️ **"残行在中间"是主人没提但更严重的一个** —— 搜索过滤一次就会出现，
症状是"在网格中间按 ↓ 卡住"，比末行卡住更容易被误判成程序坏了。

## 判据效力（X6）

把「列号硬不变 + 越界停住」复刻出来跑同样的用例 ⇒ `"k" 按 ↑` 得到 `"k"`（停住）
⇒ 确认那些 FAIL 锁的是**被修掉的行为**，不是别的东西。

## ⚠️ 探针自身踩的坑

第一版 X1 断言的是"**修复前**停住"⇒ 修好之后它自己 FAIL了
⇒ **判据要断言"正确行为"，不是"当前的坏行为"**。
（另一条同类教训记在 `grid-cursor/run.mjs` 的 R5：那条断言锁的正是被推翻的设计。）
