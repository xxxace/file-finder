# reconcile/ · 增量对账（1.1.0-Q1）

一行复跑：`node docs/probes/reconcile/run.mjs`
（输出已落 `out.txt`；`.log` 会被 `.gitignore` 挡掉，所以证据一律 `.txt`）

**验什么**：同一层目录**再扫一次**时，没变的缩略图有没有被真的复用 ——
也就是"抽帧"到底有没有被跳过。**抽帧是整个优化唯一省下来的东西**（视频要起 ffmpeg 子进程抽帧、图片要解码整图）。

## 手法

用 esbuild 打包**真的 `electron/server/index.ts`**，只把外部依赖换成桩：

| 桩 | 换掉了什么 | 为什么必须换 |
|---|---|---|
| `stub-thumbnail.mjs` | 真抽帧 → **计数版**（不解码，只记抽了几次） | ★ **判据就来自这个计数**；且真 `thumbnail.ts` 依赖 electron 的 `nativeImage`，纯 Node 加载会炸 |
| `stub-nedb.mjs` | 真缓存库 → 内存 Map | `@seald-io/nedb` 是 CJS，打成 ESM 后 `require('events')` 会 `Dynamic require` 炸；而且它是**唯一的落盘点**，换掉之后探针**彻底不写盘** |
| `stub-assistant.mjs` | 管理助手 → 空路由 | 入口**在模块顶层**就调 `createAssistantRoutes()`，而助手依赖 electron |
| `stub-config.mjs` | 数据目录 → `%TEMP%` 隔离目录 | 真值算的是 `$USERPROFILE/.file-finder`，那是**主人的真库** |

外加两处**只属于探针**的入口文本注入（产品代码里没有这些东西）：
- `listen(3060)` → `listen(0)` —— 避开主人正在跑的 dev，端口 0 = 随机空闲
- 追加 `export { scanAndCache, findDriveByLetter }` —— 这两个内部函数原先不对外，这是探针能直接调它们的唯一办法

夹具建在 `%TEMP%`，跑完连夹具带隔离库一起删。**全程没碰真库、没碰任何移动硬盘。**

## 结果（2026-10-03 · 13 PASS / 0 FAIL）

| 轮 | 场景 | 抽帧次数 | 说明 |
|---|---|---|---|
| R1 | 首次扫（folder） | **4** | 3 张图 + `sub2` 的目录脸 —— 无旧记录，只能全量 |
| R2 | 紧接着再扫 | **0** | ★ 核心判据：全部复用 |
| R3 | 盘上新增 1 个文件 | **1** | ★ 只抽新增那张，**不是重抽全部** |
| R4 | 盘上删除 1 个文件 | **0** | 条目数减一，零抽帧 |
| R5 | cover 模式再扫 | **0** | ★ 收敛封面（`handleCover` 那条路径）同样复用 |
| R6 | 同名同大小、**只改 mtime** | **1** | ★ 源文件变了就得重抽 —— **这条一开始是 FAIL 的**，见下 |

另外三条断言：
- ★ 已有条目的 `thumb` / `avatar` key **逐一未变**
- ★ 复用回来的条目**带着 base64**（`thumbData` / `avatarThumbData` 非空）
  —— 这一条不能省：`wire()` 靠它在内存里重新登记 key，少带了前端拿到的就是查不到的 key（**图片全 404**）
- ★ 目录的脸（`sub2/avatar.jpg`）走的是 `avatarSrc` 判据，同样命中复用

## ★ R6 是从一次 FAIL 里挖出来的（修的是真实缺陷）

第一版判据**只比 `size`**。R6 把它暴露了：夹具里的文件是空的（`size` 恒为 0），
**改了内容、size 没变** ⇒ 判成"没变" ⇒ 复用旧图 ⇒ **封面永久定格**。
第一次跑出来是 `16 PASS / 1 FAIL`，FAIL 就出在这条。

现实里对应的正是「**把封面文件同名替换**」——改动前 F5 会重抽、能看到新图；判据不完整之后就再也更新不了。

改成同时比 `stat.mtimeMs`（`FileInfo.srcMtime`）后 R6 转 PASS，全绿 **17 / 0**。
**代价为零**：`makeDirCover` 原先调的 `access` 换成 `stat`，两者在系统调用层是同一件事
（读同一个 inode / MFT 记录），**不多读一次盘**。

## 性能（"确保没有性能问题"）

本次在 `noCache` 路径上**多了一次 `findCache`**。它是内存查询，但 nedb 挂着 AES-256-CBC 钩子，
所以不能靠推理 —— 实测了一次，规模照抄真实基线（218 条 / 每条 7 项 / 每项 47 KB base64 / 库 **70.3 MB**，
真实库 78 MB）：

| 项 | 数字 |
|---|---|
| `findOne`（**最坏情况**：同 serial 下 218 条待扫，且有加密钩子） | **0.066 ms** |

⇒ 边际成本 **0.066 ms**；而它省下的是 N 次抽帧（每次 50–200 ms）—— **差 4~5 个数量级**。

另一处新增开销：`readFolder` 里建基线索引 = 对上一次的条目做一遍 O(n) 的 `Map.set`（n ≈ 一层条目数），**微秒级**。

## 局限（未覆盖）

1. **没跑 `wire()`** —— 它在"下发"路径上，探针只做到存储态。所以"渲染层能正常取到图"仍是
   **推理**（依据：`wire()` 无条件 `registerThumb(item.thumb, item.thumbData)`，`index.ts:565`）+ 上面的 base64 断言。
   ⇒ **真机目视**仍是最后一道（重启 dev 后看图正不正常）。
2. **没覆盖"同名替换"** —— 文件条目比的是 `size`（能发现"换了内容且大小不同"）；
   目录的脸和收敛封面只比名字。已在 `docs/IMPLEMENT-reconcile-2026-10-03.md` §八 声明。
3. 夹具里的"图片"是**空文件** —— 抽帧已被桩掉，所以内容无关紧要；但也意味着
   **真解码路径（nativeImage / ffmpeg）没被本次探针走过**（那部分代码没改，不在本次范围）。
