# hotplug/ · 移动硬盘热插拔（1.1.0-Q2）

> ⚠️ **需要人配合** —— 跑起来之后要**手动插 / 拔一次移动硬盘**。

```bash
bash docs/probes/hotplug/run.sh
```

会弹一个小窗口（别关），终端里看输出。收到设备消息后 20 秒自动收尾，最多等 120 秒。

## 验什么

Electron 能不能用**系统事件**感知移动盘插拔，而不是靠轮询。

## 为什么必须真机

1. **无头环境插不了盘** —— 这个条件造不出来；
2. Electron 官方 issue [#8190](https://github.com/electron/electron/issues/8190)（2016）说：
   **Chromium 的 UI 框架会过滤掉 `DBT_DEVICEARRIVAL`**，`hookWindowMessage(WM_DEVICECHANGE)`
   实际只能拿到 `DBT_DEVNODES_CHANGED`；官方标了 wontfix（"这是 Windows 的限制"）。
   ⚠️ 但那是 2016 年的结论，当前 Electron 4x 的行为**可能已经不同** ⇒ 只能实测。

## 已经定下的（冒烟，不插盘）

| 项 | 结果 |
|---|---|
| `hookWindowMessage(0x0219)` 能否挂上 | **能**（`isWindowMessageHooked` = `true`） |
| **hook 机制本身通不通** | **通** —— 自证：自己触发的 `WM_SIZE` / `WM_MOVE` 收到 4 / 2 次 |

> **自证这一行是这一版探针的关键设计**：没有它，一条设备消息都没收到时，无法区分
> 「设备消息被 Chromium 过滤了」和「hook 压根没生效」—— 两者导致**完全不同的后续方案**
> （前者退回按需轮询、后者说明这条路根本走不通）。

## 结果（2026-10-03 23:40 · 插盘实测）

| 项 | 结果 |
|---|---|
| `0x8000` DBT_DEVICEARRIVAL（**插入**） | ✅ **收到了**（7.1s） |
| `0x0007` DBT_DEVNODES_CHANGED | ✅ 收到，**一次插入来了 7 条** |
| `scanDrives()` 复核 | ✅ 盘数 **4 → 5**，准确 |
| `0x8004` DBT_DEVICEREMOVECOMPLETE（移除） | 第一次没轮到（见下"待补"） |

### ★ 结论一：`DBT_DEVICEARRIVAL` **没有被过滤** —— 事件驱动方案成立

这与 issue [#8190](https://github.com/electron/electron/issues/8190)（2016）的说法**相反**：
当前 Electron 4x **能**直接收到 `0x8000`。官方那个 wontfix 结论已经**不再适用**。

⇒ **不需要轮询**。而且不只是"变了没有"——**能区分插入（`0x8000`）与移除（`0x8004`）**。

### ★ 结论二：一次插拔会来**一簇**消息，实现里**必须去抖**

实测**一次插入 = 7 条 `0x0007` + 1 条 `0x8000`**，全部挤在 7.0–7.1s 这 100ms 内。
日志里能直接看到后果：那一刻连跑了 **5 次** `scanDrives()` 复核。

单次 `scanDrives()` 是 2 ms ⇒ 一次插拔白扫 8 次共 ~16ms，**可忽略**；
但如果不在实现里去抖，将来回调里加任何动作都会在这个窗口里被放大 8 倍。

⇒ **实现要点**：收到任意设备消息后起一个 **~300 ms 的定时器**，期间再来的消息只重置定时器；
定时器到点才跑 **一次** `scanDrives()` 复核 + 通知渲染层。

### ★ 结论三：`0x8004`（移除）**同样拿到了**（第二次运行）

主人在一次运行里插拔了 3 轮：插入（`0x8000`）与移除（`0x8004`）**各捕获多次**，
`scanDrives()` 复核全程准确（4 ↔ 5）。
⇒ **插入 / 移除两条路径都成立**，事件驱动方案完全确定。

### ★★ 结论四（最要紧的一条）：消息比"盘真正挂好"来得**早**

第二次日志的 38.3s 那段：

```
38.3s  ★ WM_DEVICECHANGE  wParam=0x0007  DBT_DEVNODES_CHANGED
38.4s     复核 scanDrives()：当前 4 个盘（基线 4）    ← 消息已经来了，盘还没出现
39.5s     复核 scanDrives()：当前 5 个盘（基线 4）    ← 1.2 秒后盘才真的挂上
39.6s  ★ WM_DEVICECHANGE  wParam=0x8000  DBT_DEVICEARRIVAL
```

⇒ **收到消息就立刻复核，会拿到"还没挂上"的旧值。**
所以那个去抖延迟不只是"少扫几次"—— 它同时是**等系统把卷挂好**的窗口。

### 消息簇规模（去抖参数的依据）

实测：**插入一次 5~8 条、移除一次 2~3 条**，全部挤在 ~100 ms 内。
不去抖的话，一次插拔会白跑 8 次 `scanDrives()`（每次 2 ms ⇒ 共 16 ms，本身可忽略，
但回调里任何后续动作都会被放大 8 倍）。

## 怎么读结果

- 收到 `0x8000` / `0x8004` ⇒ ✅ 事件驱动成立，**不需要轮询**（← **本次就是这个结论**）
- 只收到 `0x0007` ⇒ 方案**仍然成立**（我们只要"变了没有"），
  但实现里必须**收到它之后再跑一次 `scanDrives()` 复核**
- 一条都没有 + 自证通过 ⇒ 再试一次（或盘没插稳）；自证失败 ⇒ 换方案

## 环境坑（冒烟时实测踩到）

- `env -u ELECTRON_RUN_AS_NODE` —— 不删这个变量，electron 退化成纯 Node，**根本没有 `hookWindowMessage`**
- **必须 `app.setPath('userData', tmp)`** —— 否则和主人正在跑的 dev 实例抢同一个
  `GPUPersistentCache` 目录，症状是 GPU 进程反复崩、最后
  `FATAL: GPU process isn't usable. Goodbye.` **把整个进程带走**（第一次冒烟就是这么挂的）
- `BrowserWindow` **没有 `move()`**，改窗口位置用 `setPosition()`
- 上面两条照抄 `../win-size/run.cjs`（那里头几行就写全了）
