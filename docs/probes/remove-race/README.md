# 探针：删除与扫描的竞态（「删了又回来」）

**缺陷**：面板的「删除记录」原来走 `removeByIds`（`nedb.remove({ _id: { $in: ids } })`），
**完全绕过** `server/index.ts` 的 `queueCacheWrite` —— 那是缓存写入的**唯一串行链**。
于是"用户删掉的记录"和"正在跑的那次扫描"可以交错：扫描在删之后把同一条记录又插回来。

**修法（用正确的方式，不是加守卫）**：把这个"口"整个拿掉。
`nedb.ts` 不再导出 `removeByIds`；`removeHistoryBatch` 先把 `_id` 翻译成主键，
再让每条删除**进各自主键的串行链**。库里没有"按 `_id` 批量删"这个能力之后，
任何删除都只能走 `removeCache`（按主键），而服务端只有一个地方调它 —— 那一处已经在链里了。

判据（用户定的）：**以后同类场景还会不会复发？** —— 只要那个口还在就会。所以删口，不加守卫。

## 复算

```bash
bash docs/probes/remove-race/run.sh     # 结果写进 out.txt
```

⚠️ **这个探针验的是机制，不是真服务端的端到端时序**：
它把 `queueCacheWrite` 的语义逐字复刻成最小可运行版本，用断言对比"删除进链 / 不进链"两种写法。
（复刻对照是 superpowers `verify-async-claims` 的手法：对并发/时序下结论前，先把逻辑跑起来。）

## 实测结果（`out.txt`，复算产出）

| 版本 | 删完之后库里还有这条记录 |
|---|---|
| **A 修复前**：删除不进链 | **true** ← 复现了「删了又回来」 |
| **B 修复后**：删除也进同一条链 | **false** ← 修复成立 |

## 顺带发现（**未处理，记录在案**）

`electron/server/assistant/apply.ts:261-262` 也在链外直接调 `removeCache(...)`（写封面后失效缓存）。
性质比这里**轻**：它是"删掉缓存让它重建"，最坏情况是刚建的缓存被丢掉、下次打开重扫一遍；
**不会**留下一条陈旧记录（那才是 "删了又回来" 那种令人不信任的形态）。
真要收，也是同一招：让那两处进 `queueCacheWrite`。**本轮没动它**（另一个模块的职责）。
