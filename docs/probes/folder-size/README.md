# 探针 · 「文件夹显示大小」值不值得做

**一句话**：用**真库**量三个数 —— 聚合一次多少钱、命中率多少、真做的话值不值。

## 复跑

```bash
node docs/probes/folder-size/run.mjs       # 可行性：聚合多快、命中率多少 → out.txt
node docs/probes/folder-size/verify.mjs    # 正确性：实现算得对不对 → out-verify.txt
```

两支探针分工不同：

| | `run.mjs` | `verify.mjs` |
|---|---|---|
| 回答 | **值不值得做**（成本 / 命中率） | **实现对不对** |
| 手法 | 真库统计 | ① 构造数据测边界 ② 真库守恒律 + 独立朴素实现对照 |
| 何时跑 | 评估阶段 | **改了 `nedb.ts` 的归并与取数之后** |

⚠️ `verify.mjs` 有 1 条**不是判据**的信息行（⑤ 目录名带点）：它量的是"当前数据有没有
这种形态"，不是"实现对不对"。实测当前库里是 **0 个** ⇒ 那条分叉**没被真实数据覆盖**，
"必须用原始名 `file` 查表"是**按契约推出来的**（库里键 = `readdir` 原始名），不是实测。
**别把"当前数据恰好没有"读成"这个问题不存在"。**

## 手法

照 `real-module-probe` 那套：esbuild 把**真源文件** `electron/server/nedb.ts`
打成 bundle，在**纯 Node** 里跑。

它只 import `@seald-io/nedb` / node 内置 / `../config` / `dayjs`，
唯一的项目内依赖 `import type { FileInfo } from './index'` 是 **type-only**，
esbuild 会擦掉 ⇒ **不会把 electron 拖进来，不需要 electron 替身**。

## ⚠️ 两条硬约束（都踩过或差一点踩）

1. **不碰真库**。`config.userBasePath` 读 `process.env.USERPROFILE`，
   所以先把库**拷**到临时目录、把 `USERPROFILE` 指过去再 `import`。
   理由：`loadDatabase()` 末尾会**无条件整库重写**（`nedb.ts:280` 的注释），
   而 dev 实例可能正开着那个文件。真库全程只读一次（`copyFile`）。
2. **bundle 必须落在项目内**（`node_modules/.cache/`）。用 `packages: 'external'` 时
   运行时还要按 node_modules 解析 `@seald-io/nedb`，而临时目录向上找不到项目的
   node_modules —— 第一次就报 `Cannot find package '@seald-io/nedb'`。

## ⚠️ 输出必须脱敏（仓库铁律）

只写**数字**：绝不写 serial / relPath / 目录名 / 番号。本探针的 out.txt 可以直接入库。

## 判据

| # | 判据 | 为什么 |
|---|---|---|
| 1 | 单次聚合中位 < **16 ms** | 一帧的预算。`readFolder` 是每次进目录都走的热路径 |
| 2 | 最坏情况 O(n²) 合计 < **50 ms** | 上界：给**每一条**记录各算一次子树总量 |
| 3 | **子文件夹**能算出大小的比例 ≥ **50%** | 用户实际看到的命中率。低于这个数，功能只在少数地方生效，不值 |

## 实测（2026-10-02）

```
① 单次 loadMeta({withBytes})   中位 0.80~0.90 ms
② 最坏 O(n²)：213 条各算一次    合计 2.2~2.4 ms
③ 缓存记录维度：213 条，子树能算出的 210（99%）
④ ⭐ 子文件夹维度：208 个子文件夹里 **205 个能算出大小（99%）**
                                                           判据 3/3 ✅
```

## ⚠️ 已知局限

- **测的是"按现有数据能不能算"，不是"实现之后对不对"** —— 实现还没写。
- `③` 和 `④` 的差别很重要：`③` 是"缓存记录维度"，`④` 才是"用户实际看到的"。
  第一版只有 `③`，那个数字会让人误判功能价值。
- **分隔符是实测确认的**（`/`：211 条含 `/`、0 条含 `\`），不是猜的 ——
  猜错的话 `startsWith(root + sep)` 对深层目录全 false，子树总量会退化成
  "只有自己那一层"，命中率虚高、结论直接错。第一版就差点这么过去。
- 本探针**不读移动硬盘**，只读 `searchCache.db`（本地文件）；把库拷到临时目录是为了
  不干扰正在运行的实例，不是安全考虑。
