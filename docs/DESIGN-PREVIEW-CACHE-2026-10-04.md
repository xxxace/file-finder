## 二、四条决策

**D1 —— 库只存元数据，图片全落 `<数据目录>/.file-finder/bin/`，逐文件加密。**
```
<数据目录>/.file-finder/
├── searchCache.db         ← 元数据（92 MB → 几 MB）
├── searchCache-before-restore.db
└── bin/
    ├── t-<sig>.enc        ← 缩略图（480 → 实测定档），[16B 随机 IV][AES-256-CBC]
    └── p-<sig>.enc        ← 大图（长边 2048 / q82）
```
加密沿用库那把 `CACHE_KEY`，但**每个文件一个随机 IV**（比库里的固定 IV 规矩）。**不加密不行**：库里的缩略图本来是加密的，图片留成明文等于把"库加密"绕过去了。

**D2 —— 一个 `sig` 字段定生死，key = `t-`/`p-` + sig。**
- 图片（含封面图、目录的脸）：`sig = sha1(源文件字节)` —— 字节**本来就在手里**（F1），哈希免费；
- 视频：`sig = sha1(抽帧渲染后的字节)` —— **帧就是它的"内容"**，帧没变就不该刷新；
- 播放器缓存语义（正对主人那条要求）：**内容变了 ⇒ sig 变 ⇒ URL 变 ⇒ 浏览器必刷新**；内容没变 ⇒ URL 不变 ⇒ 继续吃 `immutable` 长缓存（这才是"多利用浏览器缓存"的正确姿势）；
- 附带：内容完全相同的两张图共用一个文件（免费去重）。

**D3 —— 尺寸档位。**
- 缩略图：**P0 探针用真库实测**（只读本地库）后定档；候选 `480/q82`（现状）· `384/q78` · `360/q75`；
- 大图：**长边 2048 / q82**（本机窗口预览最多约 2016×1248 ⇒ 已覆盖），**扫盘时随同那一次解码产出**（视频是同一帧编两张）⇒ **零额外读盘**。

**D4 —— 导出/导入 = 一个 `.zip`（store-only）。**
- 内含 `searchCache.db` + `bin/`；**不压缩**（内容已是加密字节 + JPEG，压不动；F10 已证）；
- 手写 store-only zip 是可行的：容器格式简单，CRC32 用现成的 `zlib.crc32`（F13）⇒ 不需要引依赖、也不需要打包工具；
- **Explorer 能直接双击打开**，用户零心理负担；UI 文案只是"选文件"（后缀 `.zip`）。

## 三、逐条回答主人的三个点

**1｜不用兼容旧的** —— 采纳：库结构直接改（`CACHE_VERSION` 3）。但**迁移那一步留着**：它是"把旧库里那 1471 张 base64 缩略图写成 `bin/` 文件"，**纯本地、零移动硬盘读**，几秒钟跑完；不做它就得把 5 块盘重扫一遍 —— 那是拿第一目标换省事，不划算。（主人要是想干脆删库重扫，也行，但我不建议。）

**2｜缩略图太大** —— 走"搬出 JSON"这条路，不走 gzip：
- gzip 只能把 base64 那 +33% 捞回来（F10 实测 47.8 → 36.0 KB），**对 JPEG 本身 0 收益**，还要额外 CPU；
- 搬出 JSON 直接把那 33% 永久消灭（48 → 36 KB），**再叠加档位** 480→384（面积 ×0.64）⇒ 约 **23 KB**，即主人要的"缩小一倍"；
- 顺带的收益（都是真的）：库 92 MB → 几 MB ⇒ 启动那次整库重写的量少一个数量级；内存里不再常驻约 60 MB 的 base64 字符串（`thumbStore.ts` 自己那段注释就在抱怨这件事）。

**3｜原图一定要有 + 少读盘 + 浏览器缓存 + 不能显示旧图** ——
- **原图一定存**：见 D3（大图 2048，扫盘时免费产出）；
- **少读盘**：见 §四（比现状只少不多）；另外 `/raw` 今天没有缓存头（F11），换到带 `immutable` 的 `/preview` 之后，**同一张图重复打开连一次请求都不会发**；
- **不能显示旧图**：见 D2（key 里含内容指纹）；唯一漏网的是"内容变了但指纹也算不出变化"——视频的指纹取自帧，而**帧就是屏幕上显示的东西**，语义上不会错；图片的指纹取自源字节，**内容一变必变**。

## 五、体积（数字，不糊弄）

- 单张缩略图：**≈48 KB → ≈23 KB**（去 base64 −25%，384 档再 −35%）；落地用真库 1471 张实测定档。
- 单张大图：图片 **约 100~250 KB**（原图本就 100 多 KB，重编码后同量级）；视频帧 **约 250~500 KB**（大头）。
- 全库：`bin/` 约 **300~400 MB**（大头是视频帧）；`searchCache.db` **92 MB → 几 MB**。
- 备份 zip：≈ `bin/` 的体积（store-only，不膨胀）。

## 八、边界（知情选择，逐条给代价）

1. 大图放大超过 1 倍时比"真原图"略糊（2048 上限）。`/raw` 通道**保留不删**，将来要做"看真原图"直接复用。
2. 缩略图档位下调后，2× HiDPI 屏上网格会略软 —— 本机 dpr 在 P0 量，按实测定档。
3. 极旧记录（迁移来的）`sig` 是弱判据（路径+mtime+size 的哈希）；**重扫一次即升级为内容指纹**。
4. 缓存**永不自动删** ⇒ 换图/改名会留孤儿文件；将来做一条**显式**「清理图片缓存」命令（本轮不做）。
5. zip 是自己写的 store-only 容器：格式简单 + 有系统解压做外部校验；但它是**我们自己的实现**，所以 P3 必须过"系统能解"这一关。

## 10.1 与 v2 设计的差异（三处，都有理由）

| # | 变化 | 理由 |
|---|---|---|
| 1 | 缩略图档位**实测定为 384 / q78**（不是 480 也不是 360） | `docs/probes/thumb-tier/`：取样真库 400 张真缩略图 —— 480/q82 均值 39 KB、**384/q78 均值 23 KB**、360/q75 20 KB。本机 dpr **1.25**（逻辑 2048×1280 / 物理 2560×1600）⇒ 网格一格约 422 设备像素 ⇒ 384 是 1.1 倍插值（照片上看不出）；要零插值得 440px，但那样只能省 38% 而不是 56% |

| 3 | 数量级的修正：大图总量 **≈150~250 MB**（原估 300~400） | 真库类型分布实测：**image 931 / video 201 / folder 216 / file 5** —— 视频只占 15%，而视频抽帧才是大图的大头 |

## 10.3 落地过程中的三个发现（都改了代码或文案）

1. **`srcMtime` 只有 52/1353 条**（增量对账是 10-03 才上的）⇒ 迁移来的旧记录**判不出"变没变"**。
   选择：**让它在下次重扫那一层时重出一次**（一次性、且只在他主动刷新时发生），
   **不**改成"字段为空就信它" —— 那会让"扫过又被换掉的封面"永久定格（R6 修过的那类 bug）。
   代价已写进迁移的注释。
2. **`/raw` 一个缓存头都没有**（实测）⇒ 同一张图每次打开都真读一遍盘。换到带 `immutable`
   的 `/preview` 之后，重复打开连请求都不发 —— 这是"多利用浏览器缓存"那条要求的正面回答。
3. **`FileInfo`（存储态）与 `WiredFileInfo`（下发态）在渲染层被混用了**：
   以前两者字段重合所以看不出来，图片改名字段之后类型立刻炸出来 ⇒ 渲染层改成正确的下发态类型。

## 10.4 ⚠️ 一个必须报备的动作

我有个临时统计脚本**忘了先把 `USERPROFILE` 指到副本**就导入了探针 bundle，

- 迁移本身**是对的**（216 条记录 / 1236 张图，字节级核对过）；数据没丢。
- 当时他跑的是**旧构建**（内存态没变）⇒ 界面照旧；重启后就统一到新格式。
- 已把这条写进 `entry.ts` 的警告与探针 README，防止下一个人再踩。

   代价已写进迁移的注释。
2. **`/raw` 一个缓存头都没有**（实测）⇒ 同一张图每次打开都真读一遍盘。换到带 `immutable`
   的 `/preview` 之后，重复打开连请求都不发 —— 这是"多利用浏览器缓存"那条要求的正面回答。
3. **`FileInfo`（存储态）与 `WiredFileInfo`（下发态）在渲染层被混用了**：
   以前两者字段重合所以看不出来，图片改名字段之后类型立刻炸出来 ⇒ 渲染层改成正确的下发态类型。

## 10.4 ⚠️ 一个必须报备的动作

我有个临时统计脚本**忘了先把 `USERPROFILE` 指到副本**就导入了探针 bundle，
而那个 bundle **一导入就会加载并迁移 `USERPROFILE` 指向的库** ⇒ **真库被就地迁移了一次**
（2026-10-04 12:19 之前）。事实与后果：

- 迁移本身**是对的**（216 条记录 / 1236 张图，字节级核对过）；数据没丢。
- 当时他跑的是**旧构建**（内存态没变）⇒ 界面照旧；重启后就统一到新格式。
- 已把这条写进 `entry.ts` 的警告与探针 README，防止下一个人再踩。

## 10.5 待主人真机目视（无头测不到的部分）

1. 网格观感：384 档在他屏上是否够（1.1 倍插值）。
2. 点开大图：停住 300ms 后从缩略图换成清晰版的**手感**（第一次会读一次盘、之后不再读）。

# 十一、交付后自查（同日第二轮，抓到 3 处真缺陷）

主人体验后问"有没有遗漏"。这一轮**不是复述已做的**，而是专门找"我没想到的地方"，
逐条用实测证据判定。抓到 3 处，其中 2 处是我自己引入的。

## 11.1 ⚠️ 命名不变式被破坏（我引入的，有实测证据）

**实测**（遍历真 bin 仓 1349 个文件、解密后比对"名字里的指纹 vs 内容 sha1"）：

| 类别 | 名字 == 内容指纹 | 名字 != 内容指纹 |
|---|---|---|
| `t-` 缩略图（1277 个） | **1205**（出库迁移搬的那批） | **72**（之后新扫的） |
| `p-` 大图（72 个） | 72 | 0 |

**根因**：`makeRenditions` 把 sig 锚在**大图**字节上，但一条记录只有**一个** sig 字段，
而它要同时命名**两个**尺寸的文件 ⇒ 缩略图被存成 `t-<大图指纹>`，**名字里不含它自己的内容**。
后果不是"取错图"（取图只认名字），而是：
① **同一条命名规律有两套** ⇒ 同一张图在两条路径下得到两个不同文件名的 `t`，天然去重失效；
② 任何"按名字校验内容"的逻辑（完整性检查、跨机比对）都会误判。

**修法（不是打补丁）**：sig 锚回**缩略图**，`t-<sig>` / `p-<sig>` 成为
「**同一源的两个尺寸**」—— 对称、可解释，且与出库迁移**完全一致** ⇒ 那 1205 个文件继续有效、零重出。
「换封面 ⇒ 两个 URL 都变」这条主人明确要求的因果链**依然成立**（换封面 ⇒ 缩略图变 ⇒ sig 变）。

## 11.2 ⚠️ 懒生成不幂等 ⇒ 每次点开都重读一遍源（我引入的）

上一轮修 404 时用的"另存成内容指纹的名字 + 302 重定向"**解决不了问题**：
发起请求的名字来自**库**，不会因为一次重定向而改变 ⇒ 下一屏还是请求它、还是 404、还是再读一遍源。

**修法**：`/preview` **按请求的那个名字存**（"缓存槽位"语义），302 分支整个删掉。
存完之后 `hasBin` 命中 ⇒ 这一张此后 **0 读盘**。附带好处：**少一次 302 往返**。
（已知边界：两张封面若缩略图字节恰好全等会共用一个 `p-` 文件 —— 概率极低，
用"两个字段分别锚两个尺寸"消除它要付一个持久化字段 + 一处迁移，不划算。）

## 11.3 ⚠️ 备份在图片仓异常时会静默丢图

`backupToFile` 直接用 `listBinNames()` 拼包。若 bin 目录读不出来（`initBinStore` 失败），
`names` 是空集 ⇒ **打出一个只有库、没有一张图的 zip，接口还回 "ok"** ——
用户以为备份完整，真到需要时才发现封面全没了（静默丢数据，最坏的一种）。

**修法**：打包前 `binStoreFailed()` 为真 ⇒ **响亮拒绝**并说明原因。
（另有一条"包里必须有图"的自检被我在同轮**删掉**了 —— `entries` 本来就是它拼出来的，
永远不会触发，属于自己骗自己的假防护。）

## 11.4 顺带修掉 / 补上的

1. **启动竞态**：`initBinStore()` 是异步的，而 server 是 **import 即 listen** ⇒ 端口可能先就绪、
   `names` 还是空集 ⇒ 那零点几秒内进来的请求会判"这层没有图" ⇒ **首屏一排白格子**（刷新才恢复）。
   修法：`whenBinReady().then(() => app.listen(...))`（error 监听挂 `app` 上，它本来就是 EventEmitter）。
2. **面板统计漏了图片**：2026-10-04 之后**图片才是缓存的大头**（库 85 MB → 428 KB，图片 55 MB），
   而面板只显示「库 428 KB」⇒ **严重低估**。已加「图片 N 张 · X」（`binStats` 只 stat 本地文件，
   千级条目十几毫秒，不碰移动硬盘）。顺带消化了原先零引用的 `binStats`。
3. **注释与实现不符**（会误导下一个读代码的人）：`binStore` 头部的命名规则还写着
   `<kind>-<contentSig>.<ext>.enc` / "ext = jpg/png 决定 Content-Type"（实际已恒为 JPEG、无扩展名）；
   `FileInfo.sig` 与 `makeRenditions` 的返回说明都还写着"预览大图字节的 sha1"；
   `index.vue` 的升级注释还写着"换成 `/raw`"。全部更正。

## 11.5 这一轮**没改**的（想清楚后决定不动）

- **72 个"名字不符"的 `t` 文件**：它们是**今天新扫的**那些目录，内容与那 1205 个零重复
  （实测：1349 个文件去重后仍是 1349）⇒ 不是"同一张图存两份"，没有浪费磁盘。
  而且它们的 `p-<sig>` 都在 ⇒ 闸门判"没变" ⇒ **不需要重扫**。
  按「缓存层永不自动删」这条铁律，不清。
- **bin 的孤儿文件清理**：同理，永不自动删；要清只能靠显式命令（本轮不做）。
- **`getBin` 不做内存缓存**：现在每次请求都是一次同步读 + 解密（系统盘）。
  旧实现是内存 Map（常驻几十 MB）。取舍：换成"读盘"换来内存几乎为 0，
  且浏览器 `immutable` 让同一 URL 只请求一次 ⇒ 一屏只付一次。实测口径下完全可接受，不改。

## 11.6 待主人真机复核（本轮改动后的行为）

1. **网络面板**：点开一张**迁移来的**封面 ⇒ 应只有**一次** `/preview`（200），
   **没有 302**；再点开同一张 ⇒ **零请求**（浏览器 immutable 缓存）。
2. 面板总览那行现在多出「图片 N 张 · X MB」，与「库 X」并列。
3. 拔盘后看**看过一次**的那张封面 ⇒ 清晰。

# 十二、性能：逐条实测，不推理（同日第三轮）

主人问"有没有性能问题 / 能否再精进"。**全部结论都有实测数字**，探针 `docs/probes/perf-tick/`。

## 12.1 取图（`/thumb`、`/preview` 命中时）：**没问题，不加内存缓存**

| 场景 | 中位 | p95 | max | 一屏 216 张合计 |
|---|---|---|---|---|
| 同一张图反复取（全命中 OS 页缓存） | 0.23 ms | 0.40 ms | 1.67 ms | — |
| **一屏 216 张各取一次**（各自 inode 位置） | 0.72 ms | 1.00 ms | 1.57 ms | **160 ms** |
| 每张第二次取（页缓存命中） | 0.24 ms | 0.49 ms | 0.77 ms | 58 ms |

**判据**：单次最坏 1.6 ms ≪ 一帧 16 ms ⇒ 同步读+解密**不会**让界面掉帧；
一屏服务端总共占 160 ms。⇒ **加内存缓存只能省掉这 160 ms，代价是常驻几十 MB** ⇒ 不加。

## 12.2 扫盘：**写盘占了一半，已优化**

单条目 CPU（72 张真素材，外推 216 条目）：

| 环节 | 中位 | 216 条目外推 |
|---|---|---|
| 仅解码 | 0.97 ms | 0.21 s |
| 解码 + 缩 384 + JPEG78（缩略图） | 2.44 ms | **0.63 s** |
| 解码 + 缩 2048 + JPEG82（大图） | 2.54 ms | **0.85 s** |
| 写 bin（432 次 write+rename） | 3.13 ms | **1.39 s** |

⇒ **写盘 1.39 s 与全部 CPU 1.49 s 量级相当**，不是"可以忽略的小开销"。
（真实封面中位 800×536 ⇒ 大图多数走"原样重编码"，不缩放，所以这一档很便宜。）

**改法**：`makeRenditions` 只**登记**写盘 promise、不自己等；调用方（`readFolder`，
收敛封面 `handleCover` **共用同一个袋子**）在**返回之前**统一 `await flushRenditions(pending)`。
⇒ 写盘（IO 等待）与解码（CPU）**天然重叠**。
⚠️ 不变式没放松：**"调用方拿到 sig 时文件一定已写完"**仍然成立（唯一出口就是那个 flush）。

**A/B 实测**（`run-pipeline.sh`，同一批 40 张真素材，7 轮交替）：

| | 中位 | 范围 |
|---|---|---|
| A 每条等写完（原写法） | **333 ms** | 330–360 |
| B 登记不等待（现写法） | **154 ms** | 152–165 |

⇒ **快 2.16×**；外推到一屏 216 条目 **省约 1 秒**。
⚠️ 两个诚实的限定：① 收益只出现在**真扫盘**的时刻（首扫 / 重读 / 补全缺大图的层），
日常开缓存不扫盘 ⇒ 感觉不到；② 单次测量是噪声（第一版同一次改动量到 683 ms 与 363 ms，
差 2 倍）⇒ 探针改成 7 轮取分布，**别用单次数字下结论**。
⚠️ 附带好处：B 的分布窄得多（152–165 vs 330–360）⇒ **扫盘时间更可预测**（写盘被藏起来了）。

## 12.3 面板统计（`binStats`，本轮新加的那一行）

1349 个文件逐个 `stat` = **15.5 ms**；对比 `readdir` 一次 1.2 ms。
只在**打开面板 / 点刷新**时算一次 ⇒ 完全可接受。（顺带：启动时 `readdir` 只 1.2 ms，
所以"等 bin 就绪再 listen"那一行 await 的代价可以忽略。）

## 12.4 缩略图 384px：**够用，不动**（附换档的代价）

本机 dpr **1.25**、网格一行 6 格 ⇒ 显示时的插值倍率：

| 窗口逻辑宽 | 一格（设备 px） | 384 的表现 |
|---|---|---|
| 1280 | 267 | 0.69×（源比显示大，最舒服） |
| 1600 | 333 | 0.87× |
| **1920–2048（他当前）** | 400–427 | **1.04–1.11×（照片上看不出）** |
| 2560（全屏拉满） | 533 | 1.39×（开始可见软） |

换档的**隐藏代价**（必须先说）：**改常量只对新扫的条目生效** —— 复用闸门判的是
"源变没变 + 大图在不在"，**不看尺寸** ⇒ 想让全库升级必须**重扫一遍盘**（读盘 5 块）。
体积（按像素数正比）：384=23 KB/张（全库 ~30 MB）· 448=28 KB（~37 MB）· 512=34 KB（~45 MB）。

⇒ 结论：**不动**。只有"常把窗口拉到 2560 全屏"才值得升 448，代价是一次全盘重扫。
（这张表的**前提是 dpr=1.25**；换显示器/改缩放要重算，实测命令见探针 README。）

## 12.5 方案的真实弱项（不粉饰）

1. **备份包 ≈ 55 MB**（store-only）。压不动：库是密文、图片加密后高熵 + JPEG 本身已压缩
   （实测 `gzip(JPEG)` ≈ 原大小）。这是这份数据的下限，除非降档位或放弃加密。
2. **bin 只增不减**（缓存层铁律）：换封面/改档位会留下孤儿文件。面板现在能看到占用在长大。
3. **迁移来的那批层**，大图要等"扫到那一层"才补齐（补全会自动补，但补全本身要读盘）。
4. **一个 sig 命名两个尺寸** ⇒ 两张封面若缩略图字节恰好全等，会共用同一张大图（概率极低）。
5. `/preview` 懒生成时 `nativeImage` 解码是**同步**的 ⇒ 点开大图那一下主进程会卡十几毫秒。
6. 写盘仍占扫盘成本的一半（已从"暴露"变成"与解码重叠"，但没消除）。
