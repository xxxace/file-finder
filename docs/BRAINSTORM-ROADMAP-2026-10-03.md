## 〇、一句话诊断

**「一次扫描、之后零读盘」这件事，这个产品已经做对了 —— 这是唯一的护城河，也是唯一不能丢的东西。**
它现在缺的不是功能数量，而是**一次完整使用链路的后半段**。

## 一、诊断框架：为什么用「用户任务链」而不是「功能清单」

功能清单会越列越长（最后变成「别人有的我也要有」）。
任务链只暴露**断掉的那一环**，而且每一环都能追到「为什么」。

一次完整使用：

```
想起  →  找到  →  挑选  →  打开  →  记住  →  回访
```

| 环节 | 现状 | 依据 | 判断 |
|---|---|---|---|
| 想起 | 用户脑内 | — | — |
| **找到** | 搜索只过滤**当前层**（`index.vue:466` `filterByName(dataSource, …)`，`dataSource` 唯一写入点 `:861`，切目录整体覆盖） | 静态 | ❌ **断链** |
| 挑选 | 固定 6 列；**无排序 / 无密度调节 / 无键盘导航**（只有 4 个单键 `S`/`D`/`F5`/`Backspace`） | 静态（grep） | ⚠️ 弱 |
| 打开 | 双击格子；封面条目双击=打开里面视频；右键菜单已有（复制文件名等） | 静态（grep） | ✅ 完整 |
| **记住** | **无收藏、无标记、无星标** | 静态 | ❌ **断链** |
| 回访 | 「缓存记录」= **文件夹**打开记录（`HistoryTable`，可排序） | 静态 | ⚠️ 半（记的是目录，不是片子） |
| 维护 | 封面助手（抓取/抽帧/手动 URL/回滚）· 备份·还原·合并 | 静态 | ✅ 强 |
| 安心 | 看不到「这层数据是什么时候扫的」 | 静态 | ⚠️ 弱 |

> **结论：两条硬断链 —— ① 全局搜索 ② 收藏/标记。** 其余都是「弱」，不是「断」。
> 修「断链」的收益远大于修「弱」的收益。这是排序的全部依据。

## 二、1.1.0 —— 把「找东西」这条路打通

**定位：不改变产品性质**（它仍是一个浏览器），只补齐浏览链路的缺口。
**读盘代价：本节四项全部为零。**

### ① 全局搜索 ⭐ 唯一真缺口

| 项 | 内容 |
|---|---|
| **现状** | 搜不到当前层以外的任何东西。库里有 **1471 条目 / 5 块盘**，等于「在一格里找」 |
| **为什么是第一位** | 它是**唯一的硬断链**，且**基础设施已经铺好**：`nedb.ts:229` `loadDatabase()` 启动时全库常驻内存；`index.vue` 已有现成的 `filterByName` + `usePinYin`（拼音首字母）可复用 |
| **怎么做（大方向）** | 服务端把每条记录**投影**成 `{name, dir, size, type, serial}` 一次下发；前端在**投影**上过滤（目录名 / 拼音首字母 / 类型 / 大小区间），命中项带**路径**，点击直接跳转/打开 |
| ⚠️ **必须避开的坑** | **绝不能下发原始 `data[]`** —— 实测 **69.0 MB**（含 base64 缩略图），会冻界面。投影后 **~163 KB**，这是唯一可行的形态 |
| **成本** | 中（服务端加一个查询入口 + 前端一个结果面板）。不是「小」—— 结果面板的交互（在哪展示、怎么跳转、要不要支持跨盘）本身就是一个小设计 |
| ⚠️ **未实测** | VERDICT 明确记着：**「下发投影后前端搜 1471 条会不会卡」没验证过**。动手前先拿现有 200 条做一个 10 分钟的小验证，别等做完才发现卡 |
| 附带 | 主界面搜索框 placeholder 是光秃秃的「搜索」，而 `HistoryTable` 写的是「搜索目录名」⇒ 两处搜的东西不同。**改一行文案**消歧义 |

**借鉴 Everything**：它的核心体验不是「有搜索框」，而是**输入即筛、结果即时、结果带完整路径**。
我们要对标的不是功能，是**这个手感**。区别：Everything 建索引要读盘，我们的索引**已经在内存里了**——这是我们比它更有利的地方。

### ② 视图能力：排序 + 密度调节

| 项 | 内容 |
|---|---|
| **现状** | 网格**固定 6 列**（`100%/6 − 10px` + `.image-box` 负 margin），没有排序控件、没有缩略图大小调节 |
| **为什么** | 挑选环节目前只有一个视角。想「按大小排」「按时间排」「一屏多看几格」都做不到 —— 而这些都是**纯内存**操作 |
| **怎么做** | 工具条加一个排序下拉（名称 / 大小 / 时间，升/降）+ 一个密度滑块（影响每行格数） |
| ⚠️ **最大的坑（静态）** | 6 列宽度是**算出来的**（`width:100%/6−10px` + 负 margin 补偿）。密度滑块 = 把 `/6` 变成变量 ⇒ **必须走同一个算式**，不能用 `gap` 或 `nth-child` 改（`docs/CHANGES-2026-10-02.md` §五 已警示）。另外焦点态/角标**不能参与布局**，否则算错列宽 |
| **成本** | 中（布局算式改造是这块的真正成本，不是 UI 本身） |
| **读盘** | 零 |

**借鉴 Eagle / Billfish**：素材库标配的「缩略图密度滑块」。这是**最低成本提升观感**的一项 —— 用户第一次能「调整自己的视野」。

### ③ 键盘导航

| 项 | 内容 |
|---|---|
| **现状** | 4 个单键（`S` 搜索 / `D` 选文件夹 / `F5` 重扫 / `Backspace` 返回）+ `Escape`。**方向键完全没接** |
| **为什么** | 用户的真实动线是「手一直在键盘上、用方向键扫过一片封面、回车进下一个」。现在必须抬手用鼠标 |
| **怎么做** | ↑↓←→ 移动焦点 + `Enter` 打开 + `Home`/`End` 跳首尾 + 可选 `PgUp/PgDn` |
| **成本** | 小（**前提**：焦点态不参与布局，见 ② 的坑） |
| **读盘** | 零 |

**借鉴 Windows 资源管理器 / Everything**：方向键 + Enter 是文件管理类工具的**肌肉记忆基线**。缺了它，用户的每一次移动都有「切换设备」的微摩擦。

### ④ 数据年龄（诚实义务）

| 项 | 内容 |
|---|---|
| **现状** | 缓存记录里有 `create_at`，但界面**不显示「你正在看的这层数据是什么时候扫的」** |
| **为什么（第一性）** | 这是**离线优先应用的诚实义务**。移动硬盘的数据随时可能变（增删改），用户看到的是**快照**而不是现状。不告诉他快照多旧，等于让他相信一个可能已经过期的世界 |
| **怎么做** | 面包屑/标题附近显示「本层数据：3 天前」。**数据已在库里**（`create_at`），不是新字段 |
| **成本** | 极小（改文案 + 取一个已有字段） |
| **读盘** | 零 |

> ⚠️ 注意：`BACKLOG-2026-10-03.md` 的 B2 曾被 VERDICT 判为「伪缺口」，理由是「`HistoryTable:317` 已是可排序列」。
> **那是另一个东西** —— 可排序 ≠ 在当前网格里**看见它**。VERDICT 那条针对的是「缓存面板排序」，本项是「主界面显示年龄」。
> 两者不冲突，但**我必须把区别讲清楚**，不能拿一个没被推翻的项冒充被推翻的项。

## 三、1.5.0 —— 从「看」到「用」

**定位：仍是本地单机，但开始积累「跨会话的价值」。**

### ⑤ 收藏 / 星标 ⭐ 第二条断链

| 项 | 内容 |
|---|---|
| **现状** | 完全没有「记住」这个动作 |
| **为什么** | 任务链的「记住 → 回访」整个断掉。用户看中一部，下次还得**重新找一遍** |
| **怎么做** | 缓存记录加一个标记字段（不动 `CACHE_VERSION` 的办法要先验证：标记**不写进缓存记录**、另存一张小的用户侧表，最干净） |
| ⚠️ **关键判断** | 打星标是**用户数据**，不是扫描结果。混进缓存记录 = 下次扫描**可能被覆盖**（`scanAndCache` 是「删旧+插新」）⇒ 后果是**用户标记丢失**。**必须独立存储**，这是正确性要求不是洁癖 |
| **成本** | 中（新一张小表 + 一个「我的收藏」视图） |
| **读盘** | **零写盘/零读盘**（只写本地库） |

### ⑥ 「手气不错」/ 随机抽一部

| 项 | 内容 |
|---|---|
| **现状** | — |
| **为什么** | 解决**选择困难**：库里东西多到「不知道今天看什么」。这是**纯内存随机**，产品里最便宜的高兴点 |
| **怎么做** | 从投影列表（② 里的那 163 KB）随机取一条，直接打开 |
| **读盘** | ⚠️ **选中的那一刻零读盘；但「打开」要读盘**（挂载/起播）。按铁律 3：**凡涉及读盘的必须主动说** |
| **成本** | 极小（投影列表已在，一行 `Math.random`） |

**借鉴 Plex/Emby 的「随机播放」**：这不是玩笑功能 —— 媒体库规模上去之后，「随机」是**用得最多**的入口之一。

### ⑦ 打开记录升级到「文件级」

| 项 | 内容 |
|---|---|
| **现状** | `HistoryTable` 记的是**文件夹**打开记录（README ToDo #1 里「文件使用记录」仍标 x） |
| **为什么** | 任务链的「回访」目前只覆盖目录。真正想回访的是**那一部**，不是那个目录 |
| **成本** | 小（复用现有记录设施，加一个「文件」维度） |
| **读盘** | **零**（只记本地动作） |

## 四、2.0.0 —— 让「库」有自我认知

**定位：从「我打开一个盘，看一层目录」变成「我有一个库（5 块盘构成），我知道它长什么样」。**
这是**唯一有能力撑起 2.0 的方向** —— 因为它不引入任何新依赖、不上云、不读盘，纯粹是**把已有数据换一种方式讲出来**。

### ⑧ 跨盘统一视图

| 项 | 内容 |
|---|---|
| **是什么** | 不先「选盘」，直接看到一个**合并的库**（可按盘/类型/时间维度切） |
| **为什么** | 现在的心智模型是「盘 → 目录 → 条目」。用户真正的心智是「**我的片库**」，盘只是它的物理载体 |
| **现成设施** | `loadMeta` / `loadSubtreeBytes` 已在内存里聚合（实测子树求和 0.84 ms / 双算误差 0）；`driveIdentity.ts` 已认得**每块盘的序列号** |
| **成本** | 中（一个新的「库视图」+ 聚合查询，不新增存储） |
| **读盘** | 零 |

### ⑨ 盘舰队看板

| 项 | 内容 |
|---|---|
| **要回答的问题** | 「这部作品只在 E 盘，拔了就永久没了」「每块盘各存了什么、多大」「哪块盘最久没扫」 |
| **为什么** | 全部**零读盘可得**（`serial` + `relPath` + `size` 全在库里）。别的文件管理器要么读盘去算，要么压根不管盘 —— **身份已经在手，缺的只是拿身份做统计** |
| ⚠️ **我为什么会反驳 BACKLOG 把它排 D 级** | BACKLOG 说「5 块盘还没到临界，等 8–10 块再做」。**我不同意排序，但同意原因**：它确实**不该进 1.1**。但 2.0 的定位就是「等它到临界」。**结论相同、理由不同** —— 它是「现在不做」，不是「不值得做」 |
| **成本** | 中 |
| **读盘** | 零 |

### ⑩ 全库统计 / 时间线

- 类型分布、体积分布、按 `create_at` 的时间线（「这三个月扫进来的东西」）
- 全部零读盘，纯内存聚合
- **借鉴 Plex/Emby 的「最近添加」**：它让人**重新想起自己有什么**

> ⚠️ **2.0 的边界（必须先说清）**：上面三条都是「**换一种方式讲已有数据**」。
> 一旦越过这条线（上云、引模型、写移动硬盘），就变成**另一个产品**了。见 §六。

## 六、明确不做（附理由，别重开）

| 项 | 为什么不做 |
|---|---|
| 云同步 / 账号 / 自动更新 | **移动硬盘 + 离线不是缺陷，是前提**。上云 = 变成另一个产品（`BACKLOG` C 级，已裁决） |
| 视觉去重 / 以图搜图 | 你已砍过。**不重开** |
| 本地语义检索（向量库） | 1471 条目规模不成立；引模型运行时是**最大新增依赖** |
| 番号归一化当主键 | 跨盘重复率**实测 0%** ⇒ 收益 0。已撤回 |
| **标签体系（TAG）** ⚠️ | **唯一一条我建议「2.0 再评估」而非「不做」的**。理由：它会让产品从**浏览器**变成**素材库**，心智负担上升；且要有明确使用场景支撑（现在没有）。**不是不能做，是现在没有理由做** |
| 批量重命名 / 移动 | 会**写移动硬盘**。要做得等全局搜索做完（那时用户才知道要动哪些），且按铁律 3 附读盘清单 |
| 引入 TDD 测试框架 | 「探针 + 真机目视」三件套已跑 40+ 探针。换范式 = 全量重写验证方式 |

## 七、1.1.0 的成本阶梯（请你选）

| 档 | 内容 | 新增代码量（估） | 读盘 | 拿到什么 |
|---|---|---|---|---|
| **A · 最小** | 只做 ① 全局搜索 | 中 | 零 | 补上**唯一的硬断链**。产品立刻「能用」了 |
| **B · 推荐** | ① + ② + ③ + ④ | 中偏大 | 零 | 浏览链路**整体打通**：找得到、挑得快、手不用离键盘、知道数据多旧 |
| **C · 完整** | B + ⑤ + ⑥ + ⑦ | 大 | 零（⑥「打开」会读盘，已在文中标注） | 加上「记住 → 回访」，形成**闭环** |

> **我的推荐是 B**，理由：①③④ 都是**小成本高收益**，② 是**唯一有布局风险的**（能撑起 1.1 的「观感升级」）。
> ⑤⑥⑦ 属于「新能力」，更适合作为 **1.5.0** 单独一期 —— 混进来会让 1.1 的验收边界模糊。
