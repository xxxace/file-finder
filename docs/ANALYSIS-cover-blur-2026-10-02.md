# 分析 · 「封面很模糊，但扫不出来」

> 2026-10-02 · 起因：用户反馈「有些封面很模糊，由于都有封面，无法被识别出来，人工手动删除很麻烦」。
> 本文只写**结论 + 证据 + 成本阶梯**；不动任何代码，等确认。

---

## 一、结论（先说结果）

**说的"糊"，主因不是助手抓回来的封面糊 —— 而是 113 个影片目录里躺着一张
`125×125` 的旧头像（`avatar.jpg`），被现有扫描当成了"这个目录已经有脸"。**

它长这样：

| | 网格里的显示 | 真实来源 |
|---|---|---|
| **现在** | 一张糊的小方图（在 ~320px 的格子里被放大 2.5 倍） | 目录里的 `avatar.jpg`，原图仅 125×125 |
| **助手从来没碰过它** | —— | 因为 `scan` 的判据是「`avatar` 有值 = 已有脸 = 跳过」 |

所以它不是"缺封面"（扫不出来），也不是"封面卡"（不是助手写的）。**它是第三种东西：
一张伪装成封面的头像。** 用户的处理办法是手动去资源管理器删掉它再跑补封面 —— 所以"麻烦"。

## 二、证据（三级标注）

### ① 真库实测（`docs/probes/cover-blur/scan.mjs` · 可复跑）

读的是本机缓存库（**不碰移动硬盘**），输出只含数字：

```
cover 文档 216 条
封面卡(type:image) 926 个 · 带 thumbData 的 921 个（99.5%）
子目录(type:folder) 216 个 · 有脸(avatar) 114 个 · 全部带 avatarThumbData（114/114）
⇒ 可判定的缩略图样本 1035 张

宽度分布：<100 → 105 张 · 200–299 → 5 · 300–399 → 7 · 400–479 → 9 · == 480 → 909 · > 480 → 0

分来源：
  card（封面卡）   样本 921 · 宽度 < 480 的  12（1.3%）    ← 助手抓的，基本都够大
  avatar（目录脸） 样本 114 · 宽度 < 480 的 114（100.0%）  ← 全部偏小
  其中 125×125 占 96 张（来源：card 0 · avatar 96）

目录脸偏小的 114 个里：
  · 分类目录（里面有子目录，本来就不补）1
  · 单片目录（一部片一个目录）        113   ← 真正的目标
  · 子目录从没被扫过                   0
```

### ② 静态事实（读代码可复算）

- `electron/server/index.ts:39` `DIR_COVER_FILES = ['avatar.jpg', 'cover.jpg']`
- `makeDirCover`（`:195`）逐个 `access` 试这两个名字 —— 所以**条目上 `avatar` 有值
  ⟺ 这个子目录里真的有 `cover.jpg` 或 `avatar.jpg`**（不是"有任意图片"）。
- `handleCover`（`:315`）第一件事就是**把这两个名字摘掉**（`isDirCover`）。所以：
  **一个子目录只要还有别的图片，就会被收敛成"封面卡"（`type:'image'`），
  绝不会以 `type:'folder'` + `avatar` 的形态出现。**

  ⇒ 反推：**`type:'folder'` 且 `avatar` 有值 = 这个目录里除了那张小头像，一张图片都没有。**
  也就是说 —— **它实质上就是"没有封面"**。

- `scan.ts:238` 的判据是 `if (e.type !== 'folder' || e.avatar) continue;`
  ⇒ **只看"有没有"，不看"够不够大"**。这是漏判的那一行。

### ③ 修复后会怎样（推理，未实测）

目录里补上 `<目录名>.jpg` 之后，`handleCover` 摘掉 `avatar.jpg` 仍能找到图片 →
该目录在父层**收敛成封面卡** → 网格里显示的是一张真正的大图，而不是被放大 2.5 倍的小方图。

⚠️ **这一段是推理**：走的是现有代码路径（`isDirCover` 摘除 → 收敛），逻辑上必然，
但**没有在真机上跑过一次**（需要盘在线 + 一次真实写入）。验收方式见 §五。

## 三、判据为什么可以做到「零读盘」

`thumbnail.ts` 的 `scaleToThumb`：

```ts
const { width } = img.getSize();
const scaled = width > THUMB_WIDTH ? img.resize({ width: THUMB_WIDTH, ... }) : img;
```

**只在原图更宽时才缩** ⇒ 缩略图宽 = `min(原图宽, 480)` —— 这是一条**恒等式**。

实测交叉验证：**`> 480` 的缩略图 0 张**（1035 张样本）⇒ 恒等式成立，无反例。

而缩略图（`thumbData` / `avatarThumbData`）**就存在缓存文档里**（99.5% 覆盖率，实测），
解析 JPEG 尺寸只需要 base64 解码**前 16KB** 后扫一遍标记段 ——
**纯内存、不解码整图、不碰盘**。这和 `scan` 现有的"零读盘"姿态完全一致。

阈值取 **480**（= `THUMB_WIDTH` 本身），一句话能解释：**缩略图没被缩过 = 原图够大。**

## 四、方案与成本阶梯

### A 档 · 一行判据（推荐先做）

**改动位置：`electron/server/assistant/scan.ts`，其他地方一个字不动。**

1. 新增一个纯函数 `imageWidth(dataUri)` —— 解析 JPEG 宽（约 30 行，可单独单测）。
2. `evaluateDocs` 里那条判据放宽：

```ts
// 现在
if (e.type !== 'folder' || e.avatar) continue;

// 改成：有脸、但脸太小 ⇒ 当成"没有封面"照常处理
if (e.type !== 'folder') continue;
const faceW = e.avatar ? faceWidth(e.avatarThumbData) : 0;
if (e.avatar && (faceW === 0 || faceW >= MIN_FACE_WIDTH)) continue;
```

3. 目标构造**完全复用**现有的 `addFolderFace(childRel, e.name, …)` → 写入路径照旧
   `<目录>/<目录名>.jpg`。

**为什么这是"正确的修法"而不是补丁：**
- 责任落在**唯一的判据点**（`evaluateDocs` 是全项目唯一判定"要不要补"的地方），
  新加的场景天然被覆盖，不需要给任何调用方加守卫。
- **不违反任何既有铁律**：助手写的仍然是 `<目录名>.jpg`，
  `cover.jpg` / `avatar.jpg` 两个保留名**助手照旧一个都不碰**（不覆盖、不删除）。
- 用户那条"125×125 的小头像"**原地不动** —— 想留就留，它不再挡路。

**收益**：113 个目录（占全部"有脸目录"的 99%）从"永远扫不出来"变成"出现在待补清单里"。
**成本**：1 个纯函数 + 1 行判据；**零 UI 改动、零抓取改动、零写入改动**。

### B 档 · 再修那 12 张真·封面卡（A + 约 30 行）

封面卡里原图偏小的只有 **12 张（1.3%）**。要修它得让 `apply` 支持**覆盖同名文件**：

- `apply.ts` 加一个 `kind:'cover'` 分组分支：只下载 → 转 JPEG → **原子覆盖原文件**
  （`rename` 覆盖已实测可行，见下），不建文件夹、不搬视频。
- 加**比尺寸保护**：新图宽 ≤ 旧图宽就不写，报"没有更清晰的"（避免越修越糊）。
- 旧图尺寸从缓存里就有（A 档那个解析函数直接复用），新图尺寸下载后 `nativeImage.getSize()` 拿。

**收益**：12 个。**成本**：`apply.ts` 一个新分支 + 一次覆盖前的尺寸比较。
⚠️ 这一档会**改动写盘路径**，风险显著高于 A 档，建议等 A 档验收完再说。

### C 档 · 清单里加标签（UI 微调，可选）

给目标行加一个小 tag（`125×125 小图` / `封面卡偏小`），并在顶部计数里多一项。
**纯展示，不改变任何行为。** 不想要就不做 —— 这些目标混在现有"待补"清单里也能用。

### 顺带说明：不会做的事

- ❌ **不删任何文件**（不删 `avatar.jpg`）。用户想留着小头像就留着。
- ❌ **不改 `cover.jpg` / `avatar.jpg` 的"保留名"约定**，助手照旧永不写这两个名字。
- ❌ **不新增页面**。全部落在现有「补封面」弹窗里，走现有 扫描 → 勾选 → 抓取 → 确认 → 写入。

## 五、读盘清单（铁律 3：涉及扫盘的方案必须附）

| 动作 | 读/写 | 范围 |
|---|---|---|
| **扫描**（本方案唯一的日常动作） | **0 次读盘** | 只读内存里的 nedb 缓存文档 |
| 抓取 | 0 次读盘 | 打站点，只拿 URL |
| 写入（用户点"确认写入"才发生） | 每目标 1 次 `mkdir`+`close`（若目录已存在则 `mkdir` 直接命中） | 只写 `<目录名>.jpg` 一个新文件，**不读视频、不动旧文件** |
| **验收**（一次性，需要盘在线） | 刷新（↻）那几个目录 | 走现有缓存重建路径 |

对比"用户现在的手动做法"（开资源管理器 → 找到目录 → 删图 → 跑补封面 → 再翻一遍确认），
**本方案的碰盘次数严格更少，且删/写的决定都发生在"确认写入"那一步之后。**

## 六、风险与边界（诚实版）

1. **误报**：宽度恰好 400–479 的（实测 9 张）会被一起列出，用户可能不觉得它们糊。
   代价 = 清单里多几行、可不勾选；**不会自动写坏任何东西**。
2. **盲区**：原图 ≥ 480 但**内容**本身糊（站点拿小图放大、或压缩过狠）—— **判不出来**。
   判据只能量"尺寸"，不能量"清晰度"。这一条如实标出。
3. **盲区**：`avatarThumbData` 缺失（旧缓存 / 缩略图生成失败）的条目 —— 判不出来。
   实测覆盖率 114/114，当前库里不存在这种情况。
4. **误报可能性**：如果用户**故意**在某个目录放一张小图当脸（自制合集之类），它会被列进来。
   它只是出现在清单里，不勾就完全没事。
5. **特性确认**：`e.avatar` 有值就跳过 —— 这是既有决策。本方案是**放宽它**
   （"有没有"之外再问一句"够不够大"），不是推翻它。**所以需要用户点头。**

## 七、验证计划（实施后）

1. `npm run typecheck` → 0 error。
2. 新探针 `docs/probes/cover-blur/verify.mjs`：
   - 纯函数段：**构造数据**（手工拼几个最小 JPEG 头 + 非 JPEG + 空串 + 截断）→ 逐条断言；
   - **真库段**：用同一个函数重跑一遍统计，断言"宽 > 480 的缩略图 = 0"（恒等式不破），
     并输出 A 档前后的目标数变化（**只输出数字**）。
3. 真机目视（**需要用户**）：选一块盘 → 「补封面」→ 扫描 → 清单里应出现原来扫不出来的目录 →
   勾选 → 抓取 → 写入 → 刷新网格 → **看那张格子是不是变成清晰大图**。
