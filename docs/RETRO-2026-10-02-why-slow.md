# 我为什么花了两小时（2026-10-02 · 自查）

**结论：慢不在这两个问题难，在我的排查方法选错了。** 不是"问题比看上去大"，是我用了一套决定不了任何事的做法。

| 我实际做的 | 代价 | 本该做的 |
|---|---|---|
| 读完 popover 判定「看着没问题」，接着往上下游加码读（服务端 → 解密缓存库 → 主进程 bundle → naive-ui 源码） | 反复读代码约两小时，每一轮都像在推进，其实什么判据都没定 | **同一处读 2 遍没结论 ⇒ 立刻写最小复现**，不许读第 3 遍、不许"顺手再读一处" |
| 把「症状指向的代码逻辑是对的」当成"再读一处就能对上" | 越读越远：源码里根本没有"点击落在谁身上"这个事实 | 先问「这题靠什么证据才能定」——答不上来说明没想清，缺口一定在**运行时**（事件归属 / 命中测试 / 真实布局） |
| 第一版修复直接上机制（`preview-disabled` + 自己调 `showPreview()`，15 行） | 靠探针兜回来，白写一版 | **修之前先报「最小可行版几行」**；要发明机制先停下说理由。实际只需 3 行 |

**真正终结问题的是那个探针**（真 Chromium + 从活源码切 markup + 真编译 scoped CSS）：它一次跑出
`dblclick` 的 target = `.n-image-preview`，也当场否掉了我第一版方案。**这件事 30 分钟就能做完，我排在最后做。**

另一处失焦：popover 已被证明无误之后，我还去审了整库 1409 条数据、`/raw`、缩略图 key ——
那些与当时的判据**无关**。范围只服务判据，不做"顺手审计"。

## 已固化的规则（写在 `~/.workbuddy/MEMORY.md`「排查纪律」，跨项目生效）

1. 同一处读 2 遍无结论 ⇒ 立刻转最小复现。
2. 「看着没问题」不是结论；缺的那一环在运行时，只能跑出来。
3. 修之前先摆最小可行版几行；要发明机制先说理由。
4. 范围只服务当前判据，不做无关审计。

判据以**墙钟时间**为准 —— 不是结论多完整、证据多齐。

## 下次怎么保证（不靠承诺，靠三层可检查的机制）

**先说结论：保证不了 100%。** "我下次注意"是零分量 —— 证据就是：`SOUL.md` 里本来就有一条
「任何 bug / 行为异常 → 先根因」，我今天照样跑偏了。**能被忽略的规则等于没有规则。**

所以加的三层，都是**能被主人看见 / 能被主人触发**的，不依赖我的自觉：

| 层 | 是什么 | 谁在起作用 |
|---|---|---|
| ① 触发条件改硬（`~/.workbuddy/SOUL.md`） | 「任何 bug → **先最小复现（≤10 分钟跑一下），再读代码**」，每会话注入，绕不过 | 我，但写在会被强制读到的位置 |
| ② **可见标记** | 第 2 遍仍无结论时，我**必须先说**「读了 X 处、没结论，转最小复现」再动手，不许静默继续读 | **主人**：看我有没有说这句却在接着读 —— 说了才算合规 |
| ③ **一句话刹车** | 主人只说「**复现**」两个字 ⇒ 立刻停止读代码，去跑最小复现 | **主人**：不需要判断，按一下即生效 |

**残留风险（诚实版）**：①② 仍然依赖我的自觉，会失效；**唯一 100% 有效的是 ③** ——
它是一个外部中断键，生效与否不取决于我当时的判断力。

⇒ **保证不在我这边，在主人那一句「复现」上。** 这层是真的；另外两层是降低概率。

（另：`systematic-debugging` 是安装来的第三方 skill，不是我能改的，所以纪律写在 `SOUL.md`
的触发条件里 —— 那里每会话必读。）
